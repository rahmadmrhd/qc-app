# QC App — panduan untuk agen

Aplikasi Quality Control: frontend React + TanStack; backend Bun + Hono + MariaDB di `server/` (`Dockerfile` dan `deploy/compose.yml` ada sejak T26; CI/CD nyata berjalan sejak 2026-11-07 (BuildKit, GHCR, deploy SSH, rollback otomatis, `pull_request_target`); production `qc.rhd.my.id` live sejak cutover 2026-11-07; Google Drive/Sheets diakses LANGSUNG lewat service account sejak T30a). Aplikasi Google Apps Script + Google Sheets lama dan jembatannya sudah dipensiunkan (T35, 2026-11-07): kodenya hanya ada di tag `gas-legacy`; halaman `/exec` lama dialihkan ke `qc.rhd.my.id` lewat proyek `clasp` lokal pemilik di luar repo (spek §19 butir 14).
PRD: `docs/prd/`. Rencana implementasi: `docs/superpowers/plans/`.

## Perintah
- `bun run dev` — server Bun (`server/`, :8788) + Vite (:3000) yang mem-proxy `/api`, `/auth`, `/sync` ke server (`SERVER_DEV_URL`). Prasyarat sekali: salin `server/.env.example` menjadi `server/.env`; jalankan `bun run db:tunnel` di terminal lain dan biarkan terbuka (SSH ke MariaDB dev di VPS, `127.0.0.1:33063`; `bun run dev` memeriksanya dan memberi petunjuk bila mati); lalu `bun run db:seed` (migrasi + data contoh, hanya ke skema `qc_dev`). Login lewat "Masuk sebagai pengguna dev" (`DEV_LOGIN_EMAIL`). Drive/Sheets lokal hanya bila `GOOGLE_SA_KEY_FILE` + `GOOGLE_ROOT_FOLDER_ID` diisi di `server/.env` (`docs/setup-google.md`); tanpa itu = `UNAVAILABLE`. Rincian: `docs/dev-server.md`.
- `bun run db:tunnel` — terowongan SSH ke MariaDB dev/tes di VPS; wajib hidup untuk `dev`, `db:seed`, dan tes server.
- `bun run check` — typecheck + Biome + semua test. Butuh tunnel hidup (tanpa itu GAGAL, bukan dilewati). Tes server (`bun run --cwd server test`) dibagi ke 3 proses `bun test` paralel (bawaan; `QC_TEST_SHARDS`, maks. 4 karena `max_connections` VPS 40), tiap berkas memakai skema MariaDB sementaranya sendiri (di CI dibagi 8 job matrix lewat `QC_TEST_SHARD=<i>/8`, satu proses per job; lokal tak berubah); satu berkas/folder: `bun run --cwd server test src/modules/brand`. Wajib hijau sebelum commit.
- `bun run build` — build web (Vite, potongan JS/CSS dengan lazy load per rute) ke `server/dist` (berkas statis yang dilayani server Bun dengan fallback SPA), lalu `verify-dist`: `index.html` ada, tanpa kode mock, dan tiap potongan JS ≤ 600 KB gzip.
- Desktop (Electron 45, Windows x64): `bun run --cwd desktop test` (vitest di Node, bukan `bun test`), `bun run --cwd desktop typecheck`, `bun run --cwd desktop pack` (build lalu `electron-builder --dir` ke `desktop/dist-app/win-unpacked`; UI dasar diambil dari `server/dist`, jadi jalankan `bun run build` lebih dulu: ia juga menulis `ui-manifest.json` yang dibutuhkan aturan "UI dasar yang lebih baru menang", dan `verify-pack` menolak hasil kemas tanpanya), `bun run --cwd desktop verify-pack` (menjalankan `QC App.exe --smoke`: Node 24, ssh2, `node:sqlite`, UI dasar ikut), dan `bun run build:desktop` (akar: `build` (web + verify-dist + manifest UI) lalu installer NSIS lewat `desktop dist`). Tes `countrylock/`: `bun run --cwd countrylock test` (`bun:test`). Menjalankan langsung tanpa installer (`electron .` di `desktop/` setelah `bun run --cwd desktop build`; set `UI_PUBLIC_KEY_PEM` agar pembaruan UI aktif, `--user-data-dir=<folder>` + `settings.json` berisi `serverUrl` untuk mengarahkan ke staging): login Google butuh `qc://` terdaftar, dan saat pengembangan registri TIDAK ditulis kecuali env `QC_DEV_REGISTER_PROTOCOL=1` (`desktop/src/main/protocol-registration.ts`; menulis `HKCU\Software\Classes\qc` yang menunjuk ke biner Electron + folder aplikasi + folder data yang sama; hapus dengan `reg delete HKCU\Software\Classes\qc /f`; aplikasi terpasang mendaftar ulang saat dijalankan). Tanpa itu peramban menggantung setelah memilih akun Google. `QC App.exe --smoke-ui` memuat `app://qc/country-lock` di jendela tersembunyi dan mencetak `{"bridgeVersion":N}`. Hasil kemas (`desktop/dist`, `desktop/dist-app`) tak dikomit. `bun run build` (akar) juga menulis `server/dist/ui-manifest.json` (`scripts/build-ui-manifest.ts`).
- Rilis berversi (fondasi): server punya `version` di `server/package.json` (dilaporkan `/api/ping` bersama `build` = SHA image) dan changelog ditulis sebagai fragmen `server/changelog.d/<yyyymmdd>-<slug>.md` (desktop: `desktop/changelog.d/`; satu butir per baris bergaya commit `tipe(area): ringkasan` maks. 200 karakter; `feat` = Ditambah, `fix` = Diperbaiki, `change`/`refactor`/`perf` = Diubah, `chore`/`ci`/`docs`/`test`/`build`/`style` = Internal; keputusan pemilik 2026-11-19); PR ke `dev` yang mengubah kode wajib membawa fragmen atau label `tanpa-changelog` (`changelog.yml`; hanya PR ke `dev` yang diperiksa). `bun run changelog validate|compile|extract` dan `bun run release:prepare <server|desktop> <patch|minor|major|X.Y.Z> [--dry-run]` atau `both <bump-server> <bump-desktop>` (rilis gabungan: satu cabang `release/gabungan-server-vX.Y.Z-desktop-vA.B.C`, satu PR; rinci di `docs/ci-cd.md`; rancangan `docs/superpowers/specs/2026-11-17-rilis-semver-design.md` dan `docs/superpowers/specs/2026-11-19-rilis-gabungan-design.md`). Saklar mode rilis (keputusan pemilik 2026-11-18): variabel repo `RELEASE_FLOW` kosong/`langsung` (bawaan, masa pra-resmi) = merge ke `main` tetap men-deploy production tanpa menaikkan versi (versi `0.0.0`, `/api/ping` memuat SHA `build`); `tag` = alur rilis semver (`release.yml`, satu workflow untuk server, desktop, dan gabungan, dari PR `release/server-vX.Y.Z`, `release/desktop-vX.Y.Z`, atau `release/gabungan-server-vX.Y.Z-desktop-vA.B.C`; tag + GitHub Release, merge ke `main` tidak lagi men-deploy server; `release:prepare` untuk `server` dan `both` menolak bila saklar bukan `tag`, desktop saja tidak). Build image dan deploy ke VPS hidup di workflow bersama `server-image.yml` dan `server-deploy.yml`, dipanggil `deploy-server.yml`, `release.yml`, dan `deploy-tag.yml`; ubah langkah keamanannya di sana, bukan menyalin (rinci di `docs/ci-cd.md`). `deploy-tag.yml` (`workflow_dispatch`: `tag` `server-vX.Y.Z`, `environment`, `izinkan_downgrade_skema`) men-deploy versi yang sudah dirilis (naik atau turun) tanpa build: `verify` memeriksa asal tag (SHA leluhur `main`, versi = tag, Release dari `github-actions[bot]`, image ada) dan pagar downgrade skema dini (`scripts/deploy-tag-check.ts`); pagar yang berwenang ada di `deploy/deploy.sh` `schema_guard` (kode keluar 6, ekor perintah ` allow-schema-downgrade`; migrasi berpenanda `-- qc:contract` tak pernah boleh dilewati). `deploy/deploy.sh` tidak dibawa CI: salin manual ke VPS SEBELUM merge PR `deploy-tag.yml` (`docs/deploy-vps.md` bagian 14).
- Bun terpasang di `~/.bun/bin`; bila `bun` tidak ditemukan di shell, tambahkan ke PATH.

## Struktur
- `shared/` — kontrak FE↔server (`contract.ts` DTO, input, dan peta id→tipe `ApiContract`; `api.ts` tabel rute REST) dan model permission. Murni, tanpa API runtime/DOM, import internal relatif.
- `server/` — backend baru: Bun + Hono + MariaDB 11.8 (kabel: REST `/api/v1` untuk aplikasi web). Modul di `server/src/modules/<modul>/` (repo, service, routes, validate). `src/app.ts` (`createApp(routes)`; aplikasi Hono: `/api/ping`, `/api/v1/*`, `/api/public/*` (rute publik bertoken, lihat aturan Kabel REST), `/api/openapi.json`, `/auth/*`, lalu berkas statis + fallback SPA; `/sync` lama = 404 problem+json), `src/server.ts` (`createServer(config)`: `Env` dari konfigurasi + runner job + penjadwal), `src/main.ts` (`prepareDatabase` dari `src/boot.ts`: cek koneksi lalu terapkan migrasi yang belum tercatat SEBELUM `Bun.serve`, gagal = keluar kode 1; shutdown rapi pada SIGTERM/SIGINT), `src/config.ts` (`loadConfig`; variabel di `server/.env.example`), `src/http/` (`proxy.ts` `clientIp`, `security.ts`, `static.ts`, `rest.ts` kernel REST, `problem.ts`, `openapi.ts`), `src/core/` (`db`, `cas`, `router`, `session`, `migrate`, `file-cache`, `bridge-client.ts` = antarmuka `BridgeClient` ke Google (nama warisan era jembatan Apps Script; sengaja tidak diganti, dan `GoogleClient` di `google/client.ts` adalah aliasnya), `google/` = implementasinya), `src/jobs/` (runner job internal + penjadwal), `migrations/` (skema baseline), `test-support/` (harness tes MariaDB, klien Google palsu `fake-bridge.ts`, server Google palsu `fake-google.ts` + `google-rig.ts` untuk tes klien), `scripts/` (`test.ts` runner terpecah, `seed-dev.ts`).
- `Dockerfile` + `.dockerignore` (akar) dan `deploy/` — image server (Bun alpine dipatok; build web + dependensi produksi; migrasi dan `server/dist` ikut; non-root; HEALTHCHECK `/api/ping`; tanpa rahasia) dan `compose.yml` (`qc-db` + `qc-app`; subnet jaringan dipatok lewat `QC_SUBNET`; `qc-app` memakai daftar `environment:` eksplisit, bukan `env_file`, agar rahasia qc-db tak ikut; kunci Google dipasang baca-saja dari `QC_SECRETS_DIR`). Variabel baru di `server/src/config.ts` wajib ditambah di `deploy/compose.yml` DAN `deploy/.env.example` (dijaga `server/src/deploy-files.test.ts`). `deploy/mariadb/qc.cnf` membatasi `aria_pagecache_buffer_size=32M` karena kontainer `qc-db` hanya 500M sejak 2026-11-24, 384M sebelumnya (variabel READ-ONLY: berlaku setelah `docker restart` DB, tidak lewat `SET GLOBAL`; alasan dan langkah manual di `docs/ci-cd.md` bagian "Perubahan berkas deploy"; dijaga `deploy-files.test.ts`). `docker` tidak ada di mesin pengembang: build image diverifikasi di Actions/VPS. Penyebaran: `deploy/deploy.sh` (dipanggil lewat kunci SSH `restrict,command=` terbatas; input `deploy <staging|production> <sha-40-heksa>` divalidasi ketat, tanpa eval; `.env` diparse dengan membuang satu pasang kutip, `QC_IMAGE` non-`ghcr.io` ditolak, keluaran compose masuk `.deploy.log` root di VPS bukan log CI; pull, `up -d`, tunggu sehat, uji `/api/ping`, kembali ke tag sebelumnya bila gagal; tes `server/src/deploy-script.test.ts`), `deploy/nginx/qc.conf.example` (staging `qc-dev.rhd.my.id` port 8790, production `qc.rhd.my.id` port 8791; `client_max_body_size` >= `MAX_REQUEST_BODY_BYTES`), folder instalasi `<INSTALL_DIR>/{staging,production}` (VPS pribadi: `/root/apps/qc-app/...`; `deploy.sh` menurunkan folder dari lokasinya sendiri, bawaan `QC_SECRETS_DIR` = `./secrets`, jadi server kantor non-root dengan folder lain tinggal ganti jalur `command=` dan secret `DEPLOY_USER`; spek §19 butir 11, `docs/deploy-vps.md` bagian 14); prosedur manual dan pembatalan di `docs/deploy-vps.md` (keputusan pemilik 2026-11-06, spek §19 butir 8; akses lewat `root` dikonfirmasi pemilik 2026-11-06). Staging memakai `QC_NAME=qc-staging` agar tak bertabrakan dengan stack dev lama T1 (`qc-dev-db`).
- CI/CD server: `.github/workflows/deploy-server.yml` (job `meta` → `ci` → `image` → `deploy` → `mark-deployed` (satu-satunya job `contents: write`: menulis ref git `refs/deployed/<env>` = commit yang terakhir berhasil di-deploy; ## Checklist rilis panduan interaktif (spek 4.7)

Pertanyaan penentu: apakah pengguna yang sudah paham bisa salah langkah atau melewatkan sesuatu bila tidak diberi tahu? Setiap rilis yang mengubah modul yang punya panduan wajib memilih salah satu tindakan:

| Jenis perubahan | Tindakan | Siapa yang melihat |
|---|---|---|
| Kosmetik (alur sama) | Perbaiki target/teks katalog saja | Tidak ada yang ditawari ulang; pengguna baru dapat versi terbaru |
| Alur berubah | Tambah panduan `baru` 1-2 langkah; rekam ulang klip terkait | Yang sudah menyelesaikan `dasar` modul itu |
| Fitur ditambah | Tambah panduan `baru` | Yang sudah menyelesaikan `dasar` modul itu |
| Perombakan besar | Naikkan versi panduan `dasar` di `GUIDE_VERSIONS` ("Diperbarui"); rekam ulang klip | Semua yang berhak, termasuk yang sudah selesai |

- Tambah id panduan = tambah id di `GUIDE_IDS` (`shared/guides.ts`) dan isinya di `web/src/modules/guide/catalog/`, dalam satu perubahan. Menaikkan versi = ubah `GUIDE_VERSIONS` dan isi katalog bersamaan.

## Aturan server (Bun + MariaDB)
- Kabel REST (`/api/v1`; satu-satunya kabel aplikasi web, `/api/rpc` dan `/api/boot` sudah dihapus): SATU tabel `API_ROUTES` di `shared/api.ts` (verba, jalur, query, `ifMatch`, `etag`, `create`) dipakai klien FE (`web/src/lib/api`, `api(id, input)`), kernel server (`http/rest.ts`: urutan: `authorize` (sesi + izin global, `core/router.ts`) -> baca badan -> `fromRequestParts` (merakit input datar) -> `execute` (validasi, izin berlokasi, handler; `runRoute` = `authorize` + `execute`), jadi validator/handler modul tak berubah), dan OpenAPI (`GET /api/openapi.json`, butuh sesi). Semua id kontrak (`ApiId`) terdaftar (`registerRest(app, routes)` tanpa himpunan; `shared/api.test.ts` menjaga tabel dan kontrak sejalan). Data awal klien = `GET /api/v1/me` (`auth.me`). Amplop `{ ok, data | error }` milik aplikasi Apps Script lama sudah dihapus (T35); nama "RPC" (`shared/rpc.ts`, `RpcMethod`, `RpcInput`, `RpcOutput`, `RpcContract`, `restRpc`) diganti `shared/contract.ts`, `ApiId`, `ApiInput`, `ApiOutput`, `ApiContract`, `restCall` pada 2026-11-08 (keputusan pemilik: kabelnya sudah REST, namanya jangan menyesatkan); `scripts/no-legacy-rpc.test.ts` menjaga web/server/shared bersih dari sisa kabel lama. Galat = `application/problem+json` (`http/problem.ts`; `code` tetap kode kontrak); galat versi usang WAJIB dilempar lewat `staleError(message)` (bukan `appError('CONFLICT', ...)`) agar menjadi 412 bila rute berETag dan permintaan membawa `If-Match`. Rute biner (`binary: 'request' | 'multipart' | 'response'`) memakai badan mentah/multipart/unduhan dengan batas ukuran per rute di tabel (413 tanpa membaca seluruh badan). Urutan di kernel: `authorize` (sesi HMAC, akun aktif, izin global) SEBELUM badan apa pun dibaca, lalu baca badan, `fromRequestParts`, dan `execute` (validasi, izin berlokasi, handler); `runRoute` = `authorize` + `execute` (dipakai juga tes). Respons JSON `Cache-Control: no-store` dan klien memakai `cache: 'no-store'` (ETag `updatedAt` bukan validator isi: komentar/ganti nama merk tak menaikkannya, jadi cache HTTP dapat menyajikan 304 basi); ETag tetap dikirim untuk `If-Match` dan klien yang sendiri mengirim `If-None-Match`. Unduhan biner memakai kebijakan cache tabelnya. Satu-satunya pengecualian kabel ini: rute publik bertoken tanpa sesi di sub-aplikasi `/api/public` (`app.ts`, di luar `API_ROUTES` dan OpenAPI; halaman laporan rusak Serial Number) dan `/api/desktop/catalog` (katalog Tipe offline desktop, sub-aplikasi `desktopApp`, token bersama `DESKTOP_CATALOG_TOKEN`); rute semacam itu wajib memakai token bertanda tangan berkedaluwarsa, 404 seragam untuk semua penolakan, batas laju kegagalan per IP lewat `rate_limits`, DTO daftar putih, `Cache-Control: no-store`, dan tak boleh mencatat token; tautannya diperlakukan sebagai rute klien oleh `static.ts` dan denylist service worker bila tokennya bertitik.
- ID baris basis data = ULID huruf kecil 26 karakter (keputusan pemilik 2026-11-22; spek `docs/superpowers/specs/2026-11-22-id-ulid-design.md`): SELALU `newId()` dari `server/src/core/id.ts` (monotonik, berurutan menurut waktu agar penyisipan di ujung indeks klaster), JANGAN `crypto.randomUUID()` untuk kolom `id`; pemeriksaan bentuk lewat `isUlid` (`shared/ids.ts`, murni, huruf besar ditolak). `crypto.randomUUID()` tetap untuk nilai yang harus tak tertebak (request id, nama berkas sementara, token) dan untuk `clientId` (kunci idempoten klien: UUID huruf kecil, tak ikut ditulis ulang). Data lama (UUID v4/v5) ditulis ulang ke ULID oleh skrip operator LOKAL milik pemilik yang SENGAJA tidak masuk repo (keputusan pemilik 2026-11-22, spek bagian 1 butir 7): jangan menambahkan skrip penulisan ulang ID, migrasi tabel peta `id_ulid_map`, atau kode lain yang hanya melayani migrasi itu ke repo. SATU-SATUNYA pengecualian: lapisan terjemahan ID lama sementara `server/src/core/legacy-ids.ts` (keputusan pemilik 2026-11-23, spek bagian 1 butir 10 dan 4a), dipasang di kernel REST (`http/rest.ts`) dan hanya menerjemahkan nilai string UUID lama dari klien lewat tabel `id_ulid_map` yang dibuat skrip operator (tak ada tabel atau data belum/tidak lagi bergaya ID baru = tanpa pekerjaan); jangan memperluasnya menjadi pembuat tabel peta atau penulis ulang data, dan cabut lewat PR setelah masa pantau satu minggu dan sapu akhir skrip. Tahap `BINARY(16)` dibahas terpisah setelah migrasi data sukses.
- Adaptor `Db` (`server/src/core/db.ts`) berbentuk `prepare/bind/run` di atas mysql2: `prepare(sql).bind(...).run/all/first`, `batch([...])` = SATU transaksi, `transaction(fn)` untuk logika dengan baca-lalu-tulis di dalam transaksi (deadlock mengulang `fn` sekali, jadi `fn` tanpa efek luar basis data), `exec()` multi-pernyataan hanya untuk SQL tepercaya (migrator, harness). Parameter selalu `?` berurutan (bukan `?1`) dan nilai SELALU di-bind. Kolom `key`/`before`/`after` wajib berbacktick. `SUM`/`COUNT` dapat kembali sebagai string/DECIMAL: bungkus `Number()`. Galat driver diterjemahkan menjadi `DbError{errno, kind: duplicate|out_of_range|deadlock|unavailable|other, key}`; `unavailable` (MariaDB tak terjangkau) dipetakan ke `UNAVAILABLE` untuk klien.
- Penjaga CAS (`core/cas.ts`): syarat tulis digabung ke `UPDATE`/`INSERT` (`CAS_UPDATED_AT_SET`, `CAS_VERSION_BUMP_SET`), dan syarat yang gagal mengeluarkan `CAS_FAIL_SQL` (`-9223372036854775807 - 2`, di luar rentang BIGINT: galat 1690, dikenali `isGuardFailure`) sehingga seluruh `batch()` dibatalkan; bukan `SELECT` penjaga terpisah. MariaDB tidak punya `UPDATE ... RETURNING`: nilai baru dibaca lewat `SELECT` di akhir batch yang sama (mis. pembacaan baris merk di akhir batch `setBrandStatusOnce`). Bentrok kunci unik dipetakan lewat NAMA INDEKS baseline (`mapDuplicateError`, peta konflik per modul; nama dasar tanpa akhiran `_live` lewat `baseIndexName`, jadi indeks lama dan `_live` dipetakan ke konflik yang sama; mis. `items_key`, `handovers_number`): jangan mengganti nama indeks tanpa memperbarui peta itu.
- Isolasi: `innodb_snapshot_isolation` dimatikan per sesi (MariaDB ≥ 11.6.2 menyalakannya dan melempar galat 1020 pada penghitung bersama seperti `counters`). Penulisan yang bergantung pada apa yang baru dibaca dijaga SALAH SATU dari: CAS di dalam `batch()` (syarat digabung ke `UPDATE`/`INSERT`, gagal = `CAS_FAIL_SQL`, dibungkus `runCas` yang memuat ulang dan mengulang; nomor berurutan `ST-…` memakai penghitung CAS `INSERT … ON DUPLICATE KEY UPDATE`, BUKAN `FOR UPDATE`) atau kunci baris `SELECT ... FOR UPDATE` (ganti nama merk dan penjaga merk pada penulisan item, `brandKeyGuardStmt`; kunci baris `handovers` di operasi tertentu). Jangan baca lalu tulis tanpa salah satunya. Tes konkurensi memakai `Promise.all` atas permintaan nyata; jangan dilemahkan.
- Kolasi server dan sesi `utf8mb4_nopad_bin`: perbandingan membedakan huruf besar/kecil dan spasi ekor (setara BINARY); kecocokan tak-peka-huruf lewat kolom `key` ternormalisasi (`normalizeKey`/`itemKey` di `shared/`), bukan kolasi. `CHAR_LENGTH` menghitung karakter (emoji = 1), `LENGTH` menghitung byte; pembagian bulat dengan `DIV`; `LOCATE` menggantikan `instr`.
- Migrasi: `server/migrations/NNNN_nama.sql` (urut nama, dicatat di `schema_migrations`). Migrasi yang MENGHAPUS atau MENGGANTI NAMA skema (`DROP COLUMN|TABLE|INDEX|CONSTRAINT|FOREIGN KEY`, `RENAME ...`, `CHANGE COLUMN`; fase contract) WAJIB berbaris pertama `-- qc:contract` (`scripts/migration-contract.ts`, dijaga `scripts/migration-contract.test.ts`; keputusan 2026-11-18, rilis semver bagian 3): pagar downgrade skema (`deploy/deploy.sh` `schema_guard` dan `deploy-tag.yml`) membaca penanda itu dan tak pernah mengizinkan migrasi berpenanda dilewati saat downgrade, walau dengan `allow-schema-downgrade`; menambah komentar tak mengubah perilaku basis data yang sudah menerapkannya (`schema_migrations` hanya menyimpan nama). ## Menambah rute REST
1. Tambah id di `ApiContract` (`shared/contract.ts`, tipe input/output) dan entri di `API_ROUTES` (`shared/api.ts`: verba, jalur, query, `ifMatch`/`etag`/`create` bila perlu).
2. Validator + handler di `server/src/modules/<modul>/`, daftarkan di `<modul>/routes.ts` dengan `permission` yang tepat; `getRoutes()` bertipe `RouteTable` sehingga typecheck gagal bila id belum terdaftar.
3. FE: `queryOptions`/mutation di `web/src/modules/<modul>/queries.ts` memakai `api(id, input)` (`web/src/lib/api`).
4. Tes REST di `<modul>/rest.test.ts` lewat `restClient`/`restCall` (`server/test-support`); OpenAPI (`GET /api/openapi.json`) otomatis memuat id baru.
5. Modul berlokasi: tandai `scope: 'location'` pada izin rute dan pakai `ctx.locationIds` (lihat `docs/adding-a-module.md`). Izin "salah satu dari": pakai `anyOf` (lihat `docs/adding-a-module.md`). Modul ber-BU (daftar `BU_MODULES` di `shared/business-units.ts`; saat ini `item`, `serial`, `serialservice`) tidak memakai `scope: 'location'`; resepnya ada di `docs/adding-a-module.md`, bagian "Modul ber-BU".

Resep modul baru: `docs/adding-a-module.md`.

## Kebijakan versi API (keputusan pemilik 2026-11-20)
- Kontrak API SELALU kompatibel mundur. Perubahan yang merusak = id baru `<idDasar>@<n>` (n >= 2, mis. `qrcodes.save@2`) yang berdampingan dengan v1; versi dibaca dari akhiran id (`parseApiId`, `shared/api-versions.ts`), tanpa field `version` di `ApiRouteDef`. Kelompok (awalan sebelum titik) dinaikkan `latest` di `API_GROUP_VERSIONS`; hanya rute yang berubah yang mendapat salinan v2, sisanya tetap v1.
- Handler v1 menjadi adaptor tipis ke layanan yang sama; tidak ada logika baru di handler versi lama.
- Potret kontrak `shared/api-contract.snapshot.json` diperbarui lewat `bun run api:snapshot` (dicek `--check`) dan dibuat ulang otomatis oleh `release:prepare server`/`both` (ikut commit rilis server; `isMetadataOf` server di `scripts/changelog-check.ts` menganggapnya metadata rilis, desktop tidak).
- Rute yang dipakai antrean offline dan `web/public/sync-sw.js` (memakai `/api/v1` tetap) TIDAK boleh dinaikkan sebelum skrip itu diajari versi.
- Pemilihan versi di klien (`web/src/lib/api/versions.ts`, `pickApi`) belum dipanggil `api()`: pada rute v2 PERTAMA, lapisan compat modul (`web/src/modules/<modul>/compat.ts`) WAJIB memanggil `pickApi` sebelum `toRequestParts`.
- Fase 3 sudah dibangun (spek `docs/superpowers/specs/2026-11-20-versi-api-fase3-design.md`, rencana `docs/superpowers/plans/2026-11-20-versi-api-fase3.md`). Penghapusan rute WAJIB berurutan: tandai versinya `deprecated` di `API_GROUP_VERSIONS` -> rilis server -> (>= 24 jam kemudian) hapus id dari `API_ROUTES` dan catat di `RETIRED_ROUTES` (`{ id, verb, path, removedIn: 'server-vX.Y.Z' }`) -> rilis berikutnya. Tidak ada jalan pintas: `compareContract`/`removalProblems` (`shared/api-snapshot.ts`) menolak id hilang tanpa catatan, tanpa status deprecated di potret lama, atau dengan potret lama berumur < 24 jam.
- Mekanisme di kode: (1) server: `rest.ts` menambah header `Deprecation: true` pada rute versi deprecated dan menjawab rute di `RETIRED_ROUTES` dengan 426 problem+json kode `CLIENT_OUTDATED` SEBELUM `authorize` (tanpa sesi; csrfGuard tetap lebih dulu); `/api/ping` memuat `apis` dan `minClient` (`MIN_CLIENT` di `shared/api-versions.ts`, satu-satunya sumber yang juga dipakai daftar unduhan desktop; nilai awal `0.0.0` = tak memaksa siapa pun, dinaikkan HANYA bersamaan dengan penghapusan versi API yang masih dipakai installer lama dan setelah installer yang cukup baru terbit, lewat PR). 426 hanya dianggap `CLIENT_OUTDATED` bila badan problem+json berkode itu (426 polos = `INTERNAL`). (2) web: `app/pwa/client-outdated.ts` (tingkat `none` < `deprecated` < `outdated`, hanya naik); `lib/api/versions.ts` menyimpan peta `apis` dan `minClient` (`localStorage` `qc.api.apis` dan `qc.api.minClient`, bukan per pemilik, tak dibuang saat logout) dan menaikkan tingkat `deprecated` bila klien memakai versi yang ditandai deprecated (spanduk `api-deprecated-banner.tsx`, tanpa memuat ulang); `outdated` (426) memicu pemuatan ulang lewat alur `update.ts` (`notifyClientOutdated`, menunda bila ada ketikan belum tersimpan lewat `isSafeToReload`). (3) antrean offline: 426 dibuang ke jalur "ditolak" dengan alasan jelas; klasifikasinya ada di DUA tempat (`outbox-flush.ts` dan `web/public/sync-sw.js`, `REJECTION_CODES`), dijaga `outbox-parity.test.ts`. (4) desktop: jembatan v10 (`APP_BRIDGE_VERSION`) menambah kanal `app.version|update|openDownloads` (`UI_MIN_BRIDGE_VERSION` TETAP 8); `app.update` = `AppUpdater.updateNow()` (periksa, unduh, pasang, mulai ulang TANPA dialog; hasil `restarting|up-to-date|busy|unavailable|failed`; `busy` selama inject berjalan), `app.openDownloads` membuka `<serverUrl>/desktop` (alamat dari pengaturan, bukan dari renderer, `update/downloads-url.ts`); layar penahan `web/src/app/shell/desktop-update-gate.tsx` + `use-desktop-block.ts` dipasang di layout `_app` (`app-layout.tsx`) saja, jadi `/country-lock` dan draf lokal tak pernah tertahan; menahan bila tingkat `outdated` ATAU versi terpasang < `minClient.desktop`, hanya di desktop berjembatan >= v10, tanpa tombol "Nanti". (5) rilis: `release:prepare server|both` membaca potret dan umur tag server terakhir, menjalankan `scripts/api-removal-check.ts` di pohon cabang rilis (kontrak dan `RETIRED_ROUTES` milik `origin/dev`), lalu membuat ulang potret; mode `langsung` (bawaan masa pra-resmi) tidak melewati `release:prepare`, jadi jeda 24 jam dijaga manual oleh pemilik (keputusan 2026-11-20).

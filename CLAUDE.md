# QC App — panduan untuk agen

Aplikasi Quality Control: frontend React + TanStack; backend Bun + Hono + MariaDB di `server/` (`Dockerfile` dan `deploy/compose.yml` ada sejak T26; CI/CD nyata berjalan sejak 2026-11-07 (BuildKit, GHCR, deploy SSH, rollback otomatis, `pull_request_target`); production `qc.rhd.my.id` live sejak cutover 2026-11-07; Google Drive/Sheets diakses LANGSUNG lewat service account sejak T30a). Aplikasi Google Apps Script + Google Sheets lama dan jembatannya sudah dipensiunkan (T35, 2026-11-07): kodenya hanya ada di tag `gas-legacy`; halaman `/exec` lama dialihkan ke `qc.rhd.my.id` lewat proyek `clasp` lokal pemilik di luar repo (spek §19 butir 14).
PRD: `docs/prd/`. Rencana implementasi: `docs/superpowers/plans/`.

## Perintah
- `bun run dev` — server Bun (`server/`, :8788) + Vite (:3000) yang mem-proxy `/api`, `/auth`, `/sync` ke server (`SERVER_DEV_URL`). Prasyarat sekali: salin `server/.env.example` menjadi `server/.env`; jalankan `bun run db:tunnel` di terminal lain dan biarkan terbuka (SSH ke MariaDB dev di VPS, `127.0.0.1:33063`; `bun run dev` memeriksanya dan memberi petunjuk bila mati); lalu `bun run db:seed` (migrasi + data contoh, hanya ke skema `qc_dev`). Login lewat "Masuk sebagai pengguna dev" (`DEV_LOGIN_EMAIL`). Drive/Sheets lokal hanya bila `GOOGLE_SA_KEY_FILE` + `GOOGLE_ROOT_FOLDER_ID` diisi di `server/.env` (`docs/setup-google.md`); tanpa itu = `UNAVAILABLE`. Rincian: `docs/dev-server.md`.
- `bun run db:tunnel` — terowongan SSH ke MariaDB dev/tes di VPS; wajib hidup untuk `dev`, `db:seed`, dan tes server.
- `bun run check` — typecheck + Biome + semua test. Butuh tunnel hidup (tanpa itu GAGAL, bukan dilewati). Tes server (`bun run --cwd server test`) dibagi ke 3 proses `bun test` paralel (bawaan; `QC_TEST_SHARDS`, maks. 4 karena `max_connections` VPS 40), tiap berkas memakai skema MariaDB sementaranya sendiri (di CI dibagi 8 job matrix lewat `QC_TEST_SHARD=<i>/8`, satu proses per job; lokal tak berubah); satu berkas/folder: `bun run --cwd server test src/modules/brand`. Wajib hijau sebelum commit.
- `bun run build` — build web (Vite, potongan JS/CSS dengan lazy load per rute) ke `server/dist` (berkas statis yang dilayani server Bun dengan fallback SPA), lalu `verify-dist`: `index.html` ada, tanpa kode mock, dan tiap potongan JS ≤ 600 KB gzip.
- Desktop (Electron 45, Windows x64): `bun run --cwd desktop test` (vitest di Node, bukan `bun test`), `bun run --cwd desktop typecheck`, `bun run --cwd desktop pack` (build lalu `electron-builder --dir` ke `desktop/dist-app/win-unpacked`; UI dasar diambil dari `server/dist`, jadi jalankan `bun run build:web` lebih dulu), `bun run --cwd desktop verify-pack` (menjalankan `QC App.exe --smoke`: Node 24, ssh2, `node:sqlite`, UI dasar ikut), dan `bun run build:desktop` (akar: `build:web` lalu installer NSIS lewat `desktop dist`). Tes `countrylock/`: `bun run --cwd countrylock test` (`bun:test`). Menjalankan langsung tanpa installer (`electron .` di `desktop/` setelah `bun run --cwd desktop build`; set `UI_PUBLIC_KEY_PEM` agar pembaruan UI aktif, `--user-data-dir=<folder>` + `settings.json` berisi `serverUrl` untuk mengarahkan ke staging): login Google butuh `qc://` terdaftar, dan saat pengembangan registri TIDAK ditulis kecuali env `QC_DEV_REGISTER_PROTOCOL=1` (`desktop/src/main/protocol-registration.ts`; menulis `HKCU\Software\Classes\qc` yang menunjuk ke biner Electron + folder aplikasi + folder data yang sama; hapus dengan `reg delete HKCU\Software\Classes\qc /f`; aplikasi terpasang mendaftar ulang saat dijalankan). Tanpa itu peramban menggantung setelah memilih akun Google. `QC App.exe --smoke-ui` memuat `app://qc/country-lock` di jendela tersembunyi dan mencetak `{"bridgeVersion":N}`. Hasil kemas (`desktop/dist`, `desktop/dist-app`) tak dikomit. `bun run build` (akar) juga menulis `server/dist/ui-manifest.json` (`scripts/build-ui-manifest.ts`).
- Rilis berversi (fondasi): server punya `version` di `server/package.json` (dilaporkan `/api/ping` bersama `build` = SHA image) dan changelog ditulis sebagai fragmen `server/changelog.d/<yyyymmdd>-<slug>.md` (desktop: `desktop/changelog.d/`; satu butir per baris bergaya commit `tipe(area): ringkasan` maks. 200 karakter; `feat` = Ditambah, `fix` = Diperbaiki, `change`/`refactor`/`perf` = Diubah, `chore`/`ci`/`docs`/`test`/`build`/`style` = Internal; keputusan pemilik 2026-11-19); PR ke `dev` yang mengubah kode wajib membawa fragmen atau label `tanpa-changelog` (`changelog.yml`; hanya PR ke `dev` yang diperiksa). `bun run changelog validate|compile|extract` dan `bun run release:prepare <server|desktop> <patch|minor|major|X.Y.Z> [--dry-run]` atau `both <bump-server> <bump-desktop>` (rilis gabungan: satu cabang `release/gabungan-server-vX.Y.Z-desktop-vA.B.C`, satu PR; rinci di `docs/ci-cd.md`; rancangan `docs/superpowers/specs/2026-11-17-rilis-semver-design.md` dan `docs/superpowers/specs/2026-11-19-rilis-gabungan-design.md`). Saklar mode rilis (keputusan pemilik 2026-11-18): variabel repo `RELEASE_FLOW` kosong/`langsung` (bawaan, masa pra-resmi) = merge ke `main` tetap men-deploy production tanpa menaikkan versi (versi `0.0.0`, `/api/ping` memuat SHA `build`); `tag` = alur rilis semver (`release.yml`, satu workflow untuk server, desktop, dan gabungan, dari PR `release/server-vX.Y.Z`, `release/desktop-vX.Y.Z`, atau `release/gabungan-server-vX.Y.Z-desktop-vA.B.C`; tag + GitHub Release, merge ke `main` tidak lagi men-deploy server; `release:prepare` untuk `server` dan `both` menolak bila saklar bukan `tag`, desktop saja tidak). Build image dan deploy ke VPS hidup di workflow bersama `server-image.yml` dan `server-deploy.yml`, dipanggil `deploy-server.yml`, `release.yml`, dan `deploy-tag.yml`; ubah langkah keamanannya di sana, bukan menyalin (rinci di `docs/ci-cd.md`). `deploy-tag.yml` (`workflow_dispatch`: `tag` `server-vX.Y.Z`, `environment`, `izinkan_downgrade_skema`) men-deploy versi yang sudah dirilis (naik atau turun) tanpa build: `verify` memeriksa asal tag (SHA leluhur `main`, versi = tag, Release dari `github-actions[bot]`, image ada) dan pagar downgrade skema dini (`scripts/deploy-tag-check.ts`); pagar yang berwenang ada di `deploy/deploy.sh` `schema_guard` (kode keluar 6, ekor perintah ` allow-schema-downgrade`; migrasi berpenanda `-- qc:contract` tak pernah boleh dilewati). `deploy/deploy.sh` tidak dibawa CI: salin manual ke VPS SEBELUM merge PR `deploy-tag.yml` (`docs/deploy-vps.md` bagian 14).
- Bun terpasang di `~/.bun/bin`; bila `bun` tidak ditemukan di shell, tambahkan ke PATH.

## Struktur
- `shared/` — kontrak FE↔server (`contract.ts` DTO, input, dan peta id→tipe `ApiContract`; `api.ts` tabel rute REST) dan model permission. Murni, tanpa API runtime/DOM, import internal relatif.
- `server/` — backend baru: Bun + Hono + MariaDB 11.8 (kabel: REST `/api/v1` untuk aplikasi web). Modul di `server/src/modules/<modul>/` (repo, service, routes, validate). `src/app.ts` (`createApp(routes)`; aplikasi Hono: `/api/ping`, `/api/v1/*`, `/api/public/*` (rute publik bertoken, lihat aturan Kabel REST), `/api/openapi.json`, `/auth/*`, lalu berkas statis + fallback SPA; `/sync` lama = 404 problem+json), `src/server.ts` (`createServer(config)`: `Env` dari konfigurasi + runner job + penjadwal), `src/main.ts` (`prepareDatabase` dari `src/boot.ts`: cek koneksi lalu terapkan migrasi yang belum tercatat SEBELUM `Bun.serve`, gagal = keluar kode 1; shutdown rapi pada SIGTERM/SIGINT), `src/config.ts` (`loadConfig`; variabel di `server/.env.example`), `src/http/` (`proxy.ts` `clientIp`, `security.ts`, `static.ts`, `rest.ts` kernel REST, `problem.ts`, `openapi.ts`), `src/core/` (`db`, `cas`, `router`, `session`, `migrate`, `file-cache`, `bridge-client.ts` = antarmuka `BridgeClient` ke Google (nama warisan era jembatan Apps Script; sengaja tidak diganti, dan `GoogleClient` di `google/client.ts` adalah aliasnya), `google/` = implementasinya), `src/jobs/` (runner job internal + penjadwal), `migrations/` (skema baseline), `test-support/` (harness tes MariaDB, klien Google palsu `fake-bridge.ts`, server Google palsu `fake-google.ts` + `google-rig.ts` untuk tes klien), `scripts/` (`test.ts` runner terpecah, `seed-dev.ts`).
- `Dockerfile` + `.dockerignore` (akar) dan `deploy/` — image server (Bun alpine dipatok; build web + dependensi produksi; migrasi dan `server/dist` ikut; non-root; HEALTHCHECK `/api/ping`; tanpa rahasia) dan `compose.yml` (`qc-db` + `qc-app`; subnet jaringan dipatok lewat `QC_SUBNET`; `qc-app` memakai daftar `environment:` eksplisit, bukan `env_file`, agar rahasia qc-db tak ikut; kunci Google dipasang baca-saja dari `QC_SECRETS_DIR`). Variabel baru di `server/src/config.ts` wajib ditambah di `deploy/compose.yml` DAN `deploy/.env.example` (dijaga `server/src/deploy-files.test.ts`). `docker` tidak ada di mesin pengembang: build image diverifikasi di Actions/VPS. Penyebaran: `deploy/deploy.sh` (dipanggil lewat kunci SSH `restrict,command=` terbatas; input `deploy <staging|production> <sha-40-heksa>` divalidasi ketat, tanpa eval; `.env` diparse dengan membuang satu pasang kutip, `QC_IMAGE` non-`ghcr.io` ditolak, keluaran compose masuk `.deploy.log` root di VPS bukan log CI; pull, `up -d`, tunggu sehat, uji `/api/ping`, kembali ke tag sebelumnya bila gagal; tes `server/src/deploy-script.test.ts`), `deploy/nginx/qc.conf.example` (staging `qc-dev.rhd.my.id` port 8790, production `qc.rhd.my.id` port 8791; `client_max_body_size` >= `MAX_REQUEST_BODY_BYTES`), folder instalasi `<INSTALL_DIR>/{staging,production}` (VPS pribadi: `/root/apps/qc-app/...`; `deploy.sh` menurunkan folder dari lokasinya sendiri, bawaan `QC_SECRETS_DIR` = `./secrets`, jadi server kantor non-root dengan folder lain tinggal ganti jalur `command=` dan secret `DEPLOY_USER`; spek §19 butir 11, `docs/deploy-vps.md` bagian 14); prosedur manual dan pembatalan di `docs/deploy-vps.md` (keputusan pemilik 2026-11-06, spek §19 butir 8; akses lewat `root` dikonfirmasi pemilik 2026-11-06). Staging memakai `QC_NAME=qc-staging` agar tak bertabrakan dengan stack dev lama T1 (`qc-dev-db`).
- CI/CD server: `.github/workflows/deploy-server.yml` (job `meta` → `ci` → `image` → `deploy` → `mark-deployed` (satu-satunya job `contents: write`: menulis ref git `refs/deployed/<env>` = commit yang terakhir berhasil di-deploy; run berikutnya memilih pemeriksaan dari perubahan SEJAK ref itu lewat input `since-deploy` di `ci.yml`, ref hilang = semua dijalankan); PR yang di-merge ke `dev`/`main` men-deploy environment `staging`/`production` (nama yang sama dipakai di kunci deploy `--only`, folder VPS, `QC_ENV`; keputusan pemilik 2026-11-07), tanpa pemicu `push`; `deploy.yml` (Apps Script lama) dan branch kerja sementara dihapus saat cutover T34, 2026-11-07), `test.yml` (PR; gerbang `test` = status check wajib), `ci.yml` (pemeriksaan terpilih yang dipanggil keduanya: `scripts/ci-changes.ts` memilih job menurut bagian yang berubah, tes server 8 job matrix `QC_TEST_SHARD=<i>/8`, uji bangun image PR paralel, build desktop Windows x64+arm64 hanya pemeriksaan dan hanya di PR (input `desktop-check`); PR `desktop/**` atau dokumentasi saja tidak men-deploy; cache lapisan image di GHCR `buildcache-<env>` ditulis job `image` untuk semua event; staging membacanya, PRODUCTION TANPA CACHE (`no-cache`, keputusan pemilik 2026-11-17: cache registry dapat ditimpa penulis branch)), aksi lokal `.github/actions/setup` (Bun + cache + install) dan `.github/actions/mariadb` (MariaDB 11.8 dengan `deploy/mariadb/qc.cnf` lewat `docker run`, bukan service container, agar kolasi/`sql_mode` sama dengan VPS), dokumen `docs/ci-cd.md`. `scripts/ci-workflows.test.ts` menegakkan: aksi pihak ketiga dipatok SHA commit, tanpa `${{ }}` di `run` (nilai lewat `env`), `permissions` minimal, checkout hanya `merge_commit_sha` hasil job `meta` (tak pernah head PR), dan daftar pemicu/branch; ubah workflow = ubah tes itu dan `docs/ci-cd.md`. Perubahan `deploy/compose.yml`, `deploy/deploy.sh`, `deploy/mariadb/qc.cnf`, atau variabel `.env` baru TIDAK dibawa CI: salin/isi manual di VPS SEBELUM push yang men-deploy.
- `web/src/` — `modules/<modul>/` (queries, schemas, components), `routes/` (tipis), `app/` (shell, router, boot), `lib/api/` (klien REST `api()`, `ApiError`, `describeError`), `modules/theme/` (terang/gelap/sistem).

## Aturan server (Bun + MariaDB)
- Kabel REST (`/api/v1`; satu-satunya kabel aplikasi web, `/api/rpc` dan `/api/boot` sudah dihapus): SATU tabel `API_ROUTES` di `shared/api.ts` (verba, jalur, query, `ifMatch`, `etag`, `create`) dipakai klien FE (`web/src/lib/api`, `api(id, input)`), kernel server (`http/rest.ts`: urutan: `authorize` (sesi + izin global, `core/router.ts`) -> baca badan -> `fromRequestParts` (merakit input datar) -> `execute` (validasi, izin berlokasi, handler; `runRoute` = `authorize` + `execute`), jadi validator/handler modul tak berubah), dan OpenAPI (`GET /api/openapi.json`, butuh sesi). Semua id kontrak (`ApiId`) terdaftar (`registerRest(app, routes)` tanpa himpunan; `shared/api.test.ts` menjaga tabel dan kontrak sejalan). Data awal klien = `GET /api/v1/me` (`auth.me`). Amplop `{ ok, data | error }` milik aplikasi Apps Script lama sudah dihapus (T35); nama "RPC" (`shared/rpc.ts`, `RpcMethod`, `RpcInput`, `RpcOutput`, `RpcContract`, `restRpc`) diganti `shared/contract.ts`, `ApiId`, `ApiInput`, `ApiOutput`, `ApiContract`, `restCall` pada 2026-11-08 (keputusan pemilik: kabelnya sudah REST, namanya jangan menyesatkan); `scripts/no-legacy-rpc.test.ts` menjaga web/server/shared bersih dari sisa kabel lama. Galat = `application/problem+json` (`http/problem.ts`; `code` tetap kode kontrak); galat versi usang WAJIB dilempar lewat `staleError(message)` (bukan `appError('CONFLICT', ...)`) agar menjadi 412 bila rute berETag dan permintaan membawa `If-Match`. Rute biner (`binary: 'request' | 'multipart' | 'response'`) memakai badan mentah/multipart/unduhan dengan batas ukuran per rute di tabel (413 tanpa membaca seluruh badan). Urutan di kernel: `authorize` (sesi HMAC, akun aktif, izin global) SEBELUM badan apa pun dibaca, lalu baca badan, `fromRequestParts`, dan `execute` (validasi, izin berlokasi, handler); `runRoute` = `authorize` + `execute` (dipakai juga tes). Respons JSON `Cache-Control: no-store` dan klien memakai `cache: 'no-store'` (ETag `updatedAt` bukan validator isi: komentar/ganti nama merk tak menaikkannya, jadi cache HTTP dapat menyajikan 304 basi); ETag tetap dikirim untuk `If-Match` dan klien yang sendiri mengirim `If-None-Match`. Unduhan biner memakai kebijakan cache tabelnya. Satu-satunya pengecualian kabel ini: rute publik bertoken tanpa sesi di sub-aplikasi `/api/public` (`app.ts`, di luar `API_ROUTES` dan OpenAPI; halaman laporan rusak Serial Number) dan `/api/desktop/catalog` (katalog Tipe offline desktop, sub-aplikasi `desktopApp`, token bersama `DESKTOP_CATALOG_TOKEN`); rute semacam itu wajib memakai token bertanda tangan berkedaluwarsa, 404 seragam untuk semua penolakan, batas laju kegagalan per IP lewat `rate_limits`, DTO daftar putih, `Cache-Control: no-store`, dan tak boleh mencatat token; tautannya diperlakukan sebagai rute klien oleh `static.ts` dan denylist service worker bila tokennya bertitik.
- Adaptor `Db` (`server/src/core/db.ts`) berbentuk `prepare/bind/run` di atas mysql2: `prepare(sql).bind(...).run/all/first`, `batch([...])` = SATU transaksi, `transaction(fn)` untuk logika dengan baca-lalu-tulis di dalam transaksi (deadlock mengulang `fn` sekali, jadi `fn` tanpa efek luar basis data), `exec()` multi-pernyataan hanya untuk SQL tepercaya (migrator, harness). Parameter selalu `?` berurutan (bukan `?1`) dan nilai SELALU di-bind. Kolom `key`/`before`/`after` wajib berbacktick. `SUM`/`COUNT` dapat kembali sebagai string/DECIMAL: bungkus `Number()`. Galat driver diterjemahkan menjadi `DbError{errno, kind: duplicate|out_of_range|deadlock|unavailable|other, key}`; `unavailable` (MariaDB tak terjangkau) dipetakan ke `UNAVAILABLE` untuk klien.
- Penjaga CAS (`core/cas.ts`): syarat tulis digabung ke `UPDATE`/`INSERT` (`CAS_UPDATED_AT_SET`, `CAS_VERSION_BUMP_SET`), dan syarat yang gagal mengeluarkan `CAS_FAIL_SQL` (`-9223372036854775807 - 2`, di luar rentang BIGINT: galat 1690, dikenali `isGuardFailure`) sehingga seluruh `batch()` dibatalkan; bukan `SELECT` penjaga terpisah. MariaDB tidak punya `UPDATE ... RETURNING`: nilai baru dibaca lewat `SELECT` di akhir batch yang sama (mis. pembacaan baris merk di akhir batch `setBrandStatusOnce`). Bentrok kunci unik dipetakan lewat NAMA INDEKS baseline (`mapDuplicateError`, peta konflik per modul; nama dasar tanpa akhiran `_live` lewat `baseIndexName`, jadi indeks lama dan `_live` dipetakan ke konflik yang sama; mis. `items_key`, `handovers_number`): jangan mengganti nama indeks tanpa memperbarui peta itu.
- Isolasi: `innodb_snapshot_isolation` dimatikan per sesi (MariaDB ≥ 11.6.2 menyalakannya dan melempar galat 1020 pada penghitung bersama seperti `counters`). Penulisan yang bergantung pada apa yang baru dibaca dijaga SALAH SATU dari: CAS di dalam `batch()` (syarat digabung ke `UPDATE`/`INSERT`, gagal = `CAS_FAIL_SQL`, dibungkus `runCas` yang memuat ulang dan mengulang; nomor berurutan `ST-…` memakai penghitung CAS `INSERT … ON DUPLICATE KEY UPDATE`, BUKAN `FOR UPDATE`) atau kunci baris `SELECT ... FOR UPDATE` (ganti nama merk dan penjaga merk pada penulisan item, `brandKeyGuardStmt`; kunci baris `handovers` di operasi tertentu). Jangan baca lalu tulis tanpa salah satunya. ## Menambah rute REST
1. Tambah id di `ApiContract` (`shared/contract.ts`, tipe input/output) dan entri di `API_ROUTES` (`shared/api.ts`: verba, jalur, query, `ifMatch`/`etag`/`create` bila perlu).
2. Validator + handler di `server/src/modules/<modul>/`, daftarkan di `<modul>/routes.ts` dengan `permission` yang tepat; `getRoutes()` bertipe `RouteTable` sehingga typecheck gagal bila id belum terdaftar.
3. FE: `queryOptions`/mutation di `web/src/modules/<modul>/queries.ts` memakai `api(id, input)` (`web/src/lib/api`).
4. Tes REST di `<modul>/rest.test.ts` lewat `restClient`/`restCall` (`server/test-support`); OpenAPI (`GET /api/openapi.json`) otomatis memuat id baru.
5. Modul berlokasi: tandai `scope: 'location'` pada izin rute dan pakai `ctx.locationIds` (lihat `docs/adding-a-module.md`). Izin "salah satu dari": pakai `anyOf` (lihat `docs/adding-a-module.md`). Modul ber-BU (daftar `BU_MODULES` di `shared/business-units.ts`; saat ini `item`, `serial`, `serialservice`) tidak memakai `scope: 'location'`; resepnya ada di `docs/adding-a-module.md`, bagian "Modul ber-BU".

# QC App — panduan untuk agen

Aplikasi Quality Control: frontend React + TanStack; backend Bun + Hono + MariaDB di `server/` (`Dockerfile` dan `deploy/compose.yml` ada sejak T26; CI/CD nyata berjalan sejak 2026-11-07 (BuildKit, GHCR, deploy SSH, rollback otomatis, `pull_request_target`); production `qc.rhd.my.id` live sejak cutover 2026-11-07; Google Drive/Sheets diakses LANGSUNG lewat service account sejak T30a). Aplikasi Google Apps Script + Google Sheets lama dan jembatannya sudah dipensiunkan (T35, 2026-11-07): kodenya hanya ada di tag `gas-legacy`; halaman `/exec` lama dialihkan ke `qc.rhd.my.id` lewat proyek `clasp` lokal pemilik di luar repo (spek §19 butir 14).
PRD: `docs/prd/`. Rencana implementasi: `docs/superpowers/plans/`.

## Perintah
- `bun run dev` — server Bun (`server/`, :8788) + Vite (:3000) yang mem-proxy `/api`, `/auth`, `/sync` ke server (`SERVER_DEV_URL`). Prasyarat sekali: salin `server/.env.example` menjadi `server/.env`; jalankan `bun run db:tunnel` di terminal lain dan biarkan terbuka (SSH ke MariaDB dev di VPS, `127.0.0.1:33063`; `bun run dev` memeriksanya dan memberi petunjuk bila mati); lalu `bun run db:seed` (migrasi + data contoh, hanya ke skema `qc_dev`). Login lewat "Masuk sebagai pengguna dev" (`DEV_LOGIN_EMAIL`). Drive/Sheets lokal hanya bila `GOOGLE_SA_KEY_FILE` + `GOOGLE_ROOT_FOLDER_ID` diisi di `server/.env` (`docs/setup-google.md`); tanpa itu = `UNAVAILABLE`. Rincian: `docs/dev-server.md`.
- `bun run db:tunnel` — terowongan SSH ke MariaDB dev/tes di VPS; wajib hidup untuk `dev`, `db:seed`, dan tes server.
- `bun run check` — typecheck + Biome + semua test. Butuh tunnel hidup (tanpa itu GAGAL, bukan dilewati). Tes server (`bun run --cwd server test`) dibagi ke 3 proses `bun test` paralel (bawaan; `QC_TEST_SHARDS`, maks. 4 karena `max_connections` VPS 40), tiap berkas memakai skema MariaDB sementaranya sendiri; satu berkas/folder: `bun run --cwd server test src/modules/sync`. Wajib hijau sebelum commit.
- `bun run build` — build web (Vite, potongan JS/CSS dengan lazy load per rute) ke `server/dist` (berkas statis yang dilayani server Bun dengan fallback SPA), lalu `verify-dist`: `index.html` ada, tanpa kode mock, dan tiap potongan JS ≤ 600 KB gzip.
- Bun terpasang di `~/.bun/bin`; bila `bun` tidak ditemukan di shell, tambahkan ke PATH.

## Aturan server (Bun + MariaDB)
- Kabel REST (`/api/v1`; satu-satunya kabel aplikasi web, `/api/rpc` dan `/api/boot` sudah dihapus): SATU tabel `API_ROUTES` di `shared/api.ts` (verba, jalur, query, `ifMatch`, `etag`, `create`) dipakai klien FE (`web/src/lib/api`, `api(id, input)`), kernel server (`http/rest.ts`: urutan: `authorize` (sesi + izin global, `core/router.ts`) -> baca badan -> `fromRequestParts` (merakit input datar) -> `execute` (validasi, izin berlokasi, handler; `runRoute` = `authorize` + `execute`), jadi validator/handler modul tak berubah), dan OpenAPI (`GET /api/openapi.json`, butuh sesi). Semua id kontrak RPC terdaftar (`registerRest(app, routes)` tanpa himpunan; `shared/api.test.ts` menjaga tabel dan kontrak sejalan). Data awal klien = `GET /api/v1/me` (`auth.me`). Amplop RPC `{ ok, data | error }` milik aplikasi Apps Script lama sudah dihapus (T35); `scripts/no-legacy-rpc.test.ts` menjaga web/server/shared bersih dari sisa kabel lama. Galat = `application/problem+json` (`http/problem.ts`; `code` tetap kode kontrak); galat versi usang WAJIB dilempar lewat `staleError(message)` (bukan `appError('CONFLICT', ...)`) agar menjadi 412 bila rute berETag dan permintaan membawa `If-Match`. Rute biner (`binary: 'request' | 'multipart' | 'response'`) memakai badan mentah/multipart/unduhan dengan batas ukuran per rute di tabel (413 tanpa membaca seluruh badan). Urutan di kernel: `authorize` (sesi HMAC, akun aktif, izin global) SEBELUM badan apa pun dibaca, lalu baca badan, `fromRequestParts`, dan `execute` (validasi, izin berlokasi, handler); `runRoute` = `authorize` + `execute` (dipakai juga tes). Respons JSON `Cache-Control: no-store` dan klien memakai `cache: 'no-store'` (ETag `updatedAt` bukan validator isi: komentar/ganti nama merk tak menaikkannya, jadi cache HTTP dapat menyajikan 304 basi); ETag tetap dikirim untuk `If-Match` dan klien yang sendiri mengirim `If-None-Match`. Unduhan biner memakai kebijakan cache tabelnya.
- Adaptor `Db` (`server/src/core/db.ts`) berbentuk `prepare/bind/run` di atas mysql2: `prepare(sql).bind(...).run/all/first`, `batch([...])` = SATU transaksi, `transaction(fn)` untuk logika dengan baca-lalu-tulis di dalam transaksi (deadlock mengulang `fn` sekali, jadi `fn` tanpa efek luar basis data), `exec()` multi-pernyataan hanya untuk SQL tepercaya (migrator, harness). Parameter selalu `?` berurutan (bukan `?1`) dan nilai SELALU di-bind. Kolom `key`/`before`/`after` wajib berbacktick. `SUM`/`COUNT` dapat kembali sebagai string/DECIMAL: bungkus `Number()`. Galat driver diterjemahkan menjadi `DbError{errno, kind: duplicate|out_of_range|deadlock|unavailable|other, key}`; `unavailable` (MariaDB tak terjangkau) dipetakan ke `UNAVAILABLE` untuk klien.
- Penjaga CAS (`core/cas.ts`): syarat tulis digabung ke `UPDATE`/`INSERT` (`CAS_UPDATED_AT_SET`, `CAS_VERSION_BUMP_SET`), dan syarat yang gagal mengeluarkan `CAS_FAIL_SQL` (`-9223372036854775807 - 2`, di luar rentang BIGINT: galat 1690, dikenali `isGuardFailure`) sehingga seluruh `batch()` dibatalkan; bukan `SELECT` penjaga terpisah. MariaDB tidak punya `UPDATE ... RETURNING`: nilai baru dibaca lewat `SELECT` di akhir batch yang sama (mis. `readSyncRevStmt`). Bentrok kunci unik dipetakan lewat NAMA INDEKS baseline (`mapDuplicateError`, peta konflik per modul, mis. `items_key`, `handovers_number`): jangan mengganti nama indeks tanpa memperbarui peta itu.
- Isolasi: `innodb_snapshot_isolation` dimatikan per sesi (MariaDB ≥ 11.6.2 menyalakannya dan melempar galat 1020 pada penghitung bersama seperti `sync_state`/`counters`). Penulisan yang bergantung pada apa yang baru dibaca dijaga SALAH SATU dari: CAS di dalam `batch()` (syarat digabung ke `UPDATE`/`INSERT`, gagal = `CAS_FAIL_SQL`, dibungkus `runCas` yang memuat ulang dan mengulang; nomor berurutan `ST-…` memakai penghitung CAS `INSERT … ON DUPLICATE KEY UPDATE`, BUKAN `FOR UPDATE`) atau kunci baris `SELECT ... FOR UPDATE` (ganti nama merk dan penjaga merk pada penulisan item, `brandKeyGuardStmt`; kunci baris `handovers` di operasi tertentu). Jangan baca lalu tulis tanpa salah satunya. Tes konkurensi memakai `Promise.all` atas permintaan nyata; jangan dilemahkan.
- Kolasi server dan sesi `utf8mb4_nopad_bin`: perbandingan membedakan huruf besar/kecil dan spasi ekor (setara BINARY); kecocokan tak-peka-huruf lewat kolom `key` ternormalisasi (`normalizeKey`/`itemKey` di `shared/`), bukan kolasi. `CHAR_LENGTH` menghitung karakter (emoji = 1), `LENGTH` menghitung byte; pembagian bulat dengan `DIV`; `LOCATE` menggantikan `instr`.
- Migrasi: `server/migrations/NNNN_nama.sql` (urut nama, dicatat di `schema_migrations`). DDL MariaDB TIDAK transaksional (implicit commit): tulis idempoten (`IF NOT EXISTS`) dan hindari DDL non-idempoten; mengubah skema = migrasi baru, bukan menyunting yang sudah diterapkan. Hash migrasi memperbarui templat tes otomatis. Migrasi WAJIB kompatibel mundur dengan image sebelumnya (expand → contract: tambah kolom/tabel dulu, hapus/ganti nama hanya di rilis berikutnya setelah tak ada image yang memakainya): `qc-app` menerapkan migrasi saat start dan pengembalian otomatis `deploy.sh` hanya mengganti image, TIDAK membatalkan migrasi, sehingga image lama berjalan di atas skema baru (`docs/ci-cd.md`, "Migrasi basis data dan pengembalian").
- Tes memakai MariaDB sungguhan lewat tunnel (`bun run db:tunnel`, `QC_TEST_DB_URL` di `server/.env.test`). Harness `server/test-support/`: templat `qc_test_template`; satu skema `qc_test_<epoch>_<hex>` per PROSES `bun test` (dikloning dari templat sekali, dipakai semua berkas di proses itu, dihapus di `afterAll` preload yang berlaku untuk seluruh proses; skema yatim > 6 jam disapu); `createTestEnv` mengosongkan tabel tiap tes dan memberi jam terkendali (`env.clock`) serta klien Google palsu (`env.BRIDGE`). Pool ≤ 8 koneksi per proses tes (`max_connections` VPS 40, runner ≤ 4 proses). Batas waktu tes 30 dtk (latensi tunnel).
- Google langsung (T30a; keputusan pemilik 2026-11-06, spek §10 dan §19 butir 5-6; menggantikan jembatan Apps Script): `server/src/core/google/` (`auth.ts` JWT RS256 via Web Crypto + cache token, `request.ts` aturan ulang: 401 -> perbarui token SEKALI, 429/5xx/galat jaringan diulang bertahap HANYA untuk operasi idempoten dan pembuatan berkas/folder/salinan TIDAK diulang, `drive.ts` Drive v3, `sheets.ts` Sheets v4, `client.ts` `createGoogleClient`) di belakang antarmuka `BridgeClient` (`core/bridge-client.ts`; metode lama tak berubah, ditambah `uploadFile` (Blob/byte, resumable di atas 5 MiB, mengembalikan md5), `listFolder`, `downloadFile` (aliran), `deleteFile` (permanen, hanya milik sendiri), `storageQuota`). Kunci service account HANYA dari BERKAS (`GOOGLE_SA_KEY_FILE`, bawaan compose `/run/secrets/google-sa.json`; tak pernah dari env, log, atau galat: ada tes sentinel). Penjaga folder: folder harus tercantum (`ATTACHMENTS_FOLDER_ID`, `QR_FOLDER_ID`, `QR_DOC_FOLDER_ID`, `BACKUP_FOLDER_ID`, `ALLOWED_FOLDER_IDS`) atau subfolder langsung `GOOGLE_ROOT_FOLDER_ID` (diverifikasi lewat API); berkas harus anak folder yang diminta (bukan anak = galat akses `UNAVAILABLE`, bukan `null`); `createFolder` SELALU di bawah induk; id folder fungsi dari `.env` hanya diverifikasi (`folderIdOf` di `core/settings.ts`; kosong = dibuat di bawah induk dan dicatat di tabel `settings` seperti semula). Id Drive di jalur URL divalidasi `^[A-Za-z0-9_-]{10,100}$` (`isDriveId`; id lain = `null`/NOT_FOUND tanpa permintaan). `GOOGLE_*` wajib hanya di produksi. Tes klien: `fetch` palsu (`test-support/fake-google.ts`), kunci RSA uji dibangkitkan di tes. Uji manual terhadap Google sungguhan: `scripts/google-sa-check/qc-integration.ts` (`docs/setup-google.md` S7).
- Cadangan dan peringatan (T30-T32; spek §10, §19 butir 6 dan 9): `server/src/modules/backup/` (`names.ts` nama berkas dan waktu WIB di satu tempat, `retention.ts` fungsi murni 7 harian + 4 mingguan menurut tanggal di NAMA berkas dan tak pernah menghapus bila < 3 salinan, `dump.ts` `mariadb-dump` -> gzip lewat `.partial` + baris penutup "Dump completed" wajib, kata sandi hanya lewat env `MYSQL_PWD` dan nama DB posisional, `upload.ts` unggah idempoten + verifikasi MD5, `service.ts` job `db_backup` (dump -> unggah -> retensi) dan `scheduleBackupJob` (jatuh tempo bila WIB >= 02:00 dan `BACKUP_LAST_SUCCESS_DATE` bukan hari ini), `alert.ts` email cadangan basi > 36 jam dan kuota Drive > `QUOTA_ALERT_PERCENT`, maks. sekali per 12 jam per jenis, `restore.ts` pemulihan ke skema BARU dengan verifikasi penuh SEBELUM impor). Penjadwal jam-an menjalankannya hanya bila `Env.BACKUP_ENABLED` (produksi + Google terkonfigurasi + sakelar `BACKUP_ENABLED` bukan `false`; staging memakai `false`, spek §19 butir 17; `envFromConfig`; CLI pemulihan tak bergantung padanya), jadi dev dan tes tak pernah men-dump/mengirim email kecuali menyuntik `BACKUP_DUMP`/`MAILER`. Dump lokal di volume `qc-backups` (`BACKUP_LOCAL_DIR`, 3 salinan). `core/mail.ts` = `nodemailer` generik (transport disuntik; `SMTP_PASS` hanya di closure, galat dibersihkan lewat `core/redact.ts`); `SMTP_*`/`ALERT_TO` tak pernah menggagalkan `loadConfig` (tak valid = peringatan dinonaktifkan). Pemulihan: `docker exec <app> bun /app/scripts/restore-backup.ts --target qc_restore_check ...` lewat pengguna DB berhak terbatas `qc_restore` (bukan URL admin); `--folder-id <idDrive>` untuk skenario bencana (`docs/setup-google.md` S8).
- Konfigurasi: `Env` (`core/env.ts`) = koneksi `DB` + rahasia dari `loadConfig` + pengaturan Google (`NOW`, `FILE_CACHE`, dan klien palsu `BRIDGE` hanya disuntik tes; `createServer` mengisi `BRIDGE` dengan klien Google nyata, satu per proses agar token tercache). Jangan membaca `process.env` di luar `config.ts` dan `main.ts`. IP klien lewat `clientIp(request, peerAddress, trustedProxy)` (`http/proxy.ts`): `CF-Connecting-IP` dipercaya HANYA bila peer ada di dalam daftar CIDR `TRUSTED_PROXY` (`parseTrustedProxy`, ketat; bawaan loopback `127.0.0.1/32,::1/128`; di Docker ditambah subnet compose `QC_SUBNET`, karena peer nginx host di dalam container adalah gateway bridge; entri rusak = `loadConfig` gagal; keputusan I5 2026-11-05); pembatas percobaan salah sync dihitung per IPv4 / per /64 IPv6 (`limiterAddress`; `sync:fails:<id>`, `sync:blocked:<id>`) dan barisnya yang kedaluwarsa dibuang penjadwal tiap jam (`purgeExpiredRateLimits`). Origin publik dan atribut `Secure` cookie diturunkan dari `APP_ORIGIN` (wajib https di produksi), bukan dari header Host; `DEV_LOGIN_EMAIL` ditolak `loadConfig` di produksi atau bila `APP_ORIGIN` bukan localhost. Badan permintaan: JSON REST dibatasi 2 MB (`MAX_JSON_BODY_BYTES`, `http/body.ts`; 413 problem+json VALIDATION; alasan: base64 sudah hilang dari kabel dan muatan JSON sah terbesar < 1 MB, jadi batas kecil memperkecil permukaan serangan memori; keputusan pemilik 2026-11-06), rute biner oleh `maxBytes` masing-masing di `API_ROUTES`, push sinkron QC Desktop 5 MB (`SYNC_MAX_BODY_BYTES` = `SYNC_LIMITS.bodyBytes`, dibaca SETELAH token sah; sengaja bukan batas JSON 2 MB karena 25 item berdetail 20.000 karakter dapat mendekatinya), dan batas global `Bun.serve` (`MAX_REQUEST_BODY_BYTES`) = rute biner terbesar di `API_ROUTES` + overhead kecil (tanpa 16 MB lama). Batas gambar: `MAX_IMAGE_BYTES` = 10 MB (batas TERIMA di tepi, `files.upload`; spek §19 butir 5), sedangkan target pengecilan di FE `IMAGE_TARGET_BYTES` tetap 1 MB (`shared/files.ts`); PDF sumber 10 MB dan ekspor 8 MB tak berubah. Semuanya dibaca bertahap (`readTextLimited`/`readBytesLimited`). Tes `http/body.test.ts` mengukur muatan sah terbesar tiap rute JSON; rute JSON baru wajib ditambahkan ke tabel tesnya. Jangan membaca header itu langsung.
- Bentuk kabel item/merk untuk QC Desktop disusun di aplikasi oleh `toWireItem` (`sync/items.ts`, satu-satunya definisi; tanpa JSON di SQL). Mengubah field kabel WAJIB memperbarui `toWireItem` dan tes bentuk kabelnya; perubahan field sinkron item/merk WAJIB menaikkan `sync_rev` (`itemSyncSignature`). Kontrak: `docs/api/desktop-sync.md`.
- Sinkron QC Desktop = REST `/api/v1/sync/*` (T25, kontrak versi 2, keputusan pemilik 2026-11-05/06; `POST /sync` dan amplop `{ v, method, token, payload }` DIHAPUS, jawabannya 404): tabel `SYNC_API_ROUTES` (`shared/api.ts`; `GET /sync/ping`, `GET /sync/brands`, `POST /sync/brands/push`, `GET /sync/items`, `POST /sync/items/push`, `GET /sync/files/{id}`) + `syncInputFromParts` merakit input handler dari jalur/query/badan; `registerSyncRest` (`modules/sync/rest.ts`) mendaftarkannya pada sub-aplikasi `/api/v1` SEBELUM `registerRest`; id `sync.*` tetap nama handler/`operationId`; handler lewat tabel `syncRoutes()`/`syncRoute` (`createApp(routes, syncTable)` menerima tabel pengganti untuk tes). Otentikasi HANYA `Authorization: Bearer <SYNC_API_TOKEN>` (`bearerToken` + `authenticateSync`: banding waktu-konstan, pembatas 10 salah/10 menit per IP klien lewat `rate_limits`: token dibandingkan DULU, lalu satu transaksi atomik berbentuk sama untuk benar/salah (`settleAttempt`: +1 bila salah, +0 bila benar; kegagalan ke-10 menulis blokir di transaksi yang sama; blokir dibaca di dalam transaksi). HANYA kegagalan yang dihitung: permintaan sah tidak dihitung dan tidak ditolak karena serentak (spek FS2); jangan memperkenalkan pemesanan-lalu-lepas jatah); cookie sesi TIDAK dibaca di rute ini dan `csrfGuard` melewatinya (`isSyncApiPath`); token tidak pernah di badan/URL dan header Authorization tidak pernah dicatat. SEMUA kegagalan pra-otentikasi (header hilang, bukan Bearer, token salah, diblokir, token server belum diset; juga rute `/sync/*` tak dikenal) = 401 problem+json yang sama ("Token tidak valid", `WWW-Authenticate: Bearer`), satu-satunya pengecualian badan > ±10 MB (`MAX_REQUEST_BODY_BYTES`) yang ditolak 413 polos oleh server HTTP sebelum aplikasi dan token diperiksa; badan baru dibaca setelah token sah (`readJsonBody(request, SYNC_MAX_BODY_BYTES)`). Sukses = badan JSON apa adanya (bukan amplop), hasil push per item (`created|updated|unchanged|conflict|invalid|error`, `conflict` membawa `current`) selalu di badan 200; tanpa ETag/If-Match pada item/merk (pull berbasis `sinceRev`); `GET /sync/files/{id}` = byte mentah + `Content-Type` + `ETag` = id Drive + 304, 413 > 10 MB, 404 di luar folder (`getSyncFile` mengembalikan `bytes`, bukan base64). `UNAVAILABLE` kini 503 + `Retry-After` (versi 1 memetakannya ke INTERNAL). Batas: pull 500 (200 dengan detail), push 50 (25 bila ada `detail`), badan 5 MB, berkas 10 MB (`SYNC_LIMITS`; dinaikkan dari 8 MB agar sama dengan batas gambar `MAX_IMAGE_BYTES`, keputusan pemilik 2026-11-06; batas peninggalan platform sebelumnya 50/5 DIBUANG, spek §19 butir 7). Versi API REST = `SYNC_REST_API_VERSION` (2). Tes lewat `server/test-support/sync-rest.ts` (`syncSend`/`syncCall`, memanggil `app` nyata); rute atau perilaku baru wajib masuk tabel, OpenAPI (`syncBearer`, otomatis), dan `docs/api/desktop-sync.md`.
- Isi berkas dibaca lewat `cachedFileContent` (`core/file-cache.ts`, cache memori LRU 32 MB per proses); izin/folder diperiksa SEBELUM cache; setiap `trashFile`/`replaceFileContent` baru wajib diikuti `dropCachedFile`.
- Runner job (`src/jobs/runner.ts`, poll 2 dtk, satu job pada satu waktu, langkah dikuasai atomik lewat lease) dan penjadwal (pembersihan QR tiap jam) dijalankan `createServer`; `stop()` menunggu putaran berjalan lalu menutup pool.
- Parsing checklist catatan memakai `server/src/modules/handover/checklist.ts` (memo kecil per proses) dan `matchChecksToEntries`; jangan memanggil `extractChecklist`/`matchChecks` berulang per baris.


## Aturan `shared/` dan cache frontend
- `shared/` dipakai server dan web: murni (tanpa API runtime/DOM: `URL`, `fetch`, `atob`, dll.), import internal relatif. Batas ukuran di `shared/api.ts`/`shared/sync.ts` sengaja literal; tes (`api.test.ts`, `sync-api.test.ts`) menjaganya sama dengan konstanta sumbernya.
- Cache data (frontend): mutasi QR dan item memasang hasil server langsung ke cache (`web/src/lib/query-cache.ts`: `upsertInList`, `removeFromList`, `markStale`) dan TIDAK menunggu muat ulang (sebelumnya simpan + muat ulang daftar berurutan); `app/prefetch.ts` mem-prefetch daftar yang boleh dibaca sekali saat beranda diam (batch); `app/query-persist.ts` menyimpan query whitelist (me, items, brands, qrcodes) di localStorage per pemilik token, dipulihkan sebelum router dibuat (tampil instan lalu dimuat ulang), dibuang saat keluar. Jangan menambah Log Audit, user, atau isi berkas ke whitelist.

## Aturan frontend
- Komponen UI dari shadcn (`web/src/components/ui`, dikecualikan dari lint). Tambah lewat `bunx --bun shadcn@latest add <komponen>` dari folder `web/`. shadcn 4 memakai paket `cn` (shadcn-ui/cn), bukan `clsx`+`tailwind-merge`.
- Server state: TanStack Query; form: TanStack Form + zod; filter/halaman: search params Router. Tanpa library state global.
- Tema: `modules/theme` (kelas `dark` di `<html>`); skrip anti-kedip di `web/index.html` harus selaras dengan `theme.ts`.
- Jangan menaruh kode mock di build produksi (dicek `scripts/verify-dist.ts`).

## Menambah rute REST
1. Tambah id di `RpcContract` (`shared/rpc.ts`, tipe input/output) dan entri di `API_ROUTES` (`shared/api.ts`: verba, jalur, query, `ifMatch`/`etag`/`create` bila perlu).
2. Validator + handler di `server/src/modules/<modul>/`, daftarkan di `<modul>/routes.ts` dengan `permission` yang tepat; `getRoutes()` bertipe `RouteTable` sehingga typecheck gagal bila id belum terdaftar.
3. FE: `queryOptions`/mutation di `web/src/modules/<modul>/queries.ts` memakai `api(id, input)` (`web/src/lib/api`).
4. Tes REST di `<modul>/rest.test.ts` lewat `restClient`/`restRpc` (`server/test-support`); OpenAPI (`GET /api/openapi.json`) otomatis memuat id baru.
5. Modul berlokasi: tandai `scope: 'location'` pada izin rute dan pakai `ctx.locationIds` (lihat `docs/adding-a-module.md`). Izin "salah satu dari": pakai `anyOf` (lihat `docs/adding-a-module.md`).

Resep modul baru: `docs/adding-a-module.md`.

# CI/CD (GitHub Actions)

Workflow di `.github/workflows/`: `ci.yml` (pemeriksaan terpilih yang dapat dipanggil, dipakai keduanya di bawah), `test.yml` (PR; gerbang `test`), dan `deploy-server.yml` (server Bun + MariaDB di VPS). Workflow deploy Apps Script lama (`deploy.yml`) dihapus saat cutover 2026-11-07; versinya tetap ada di tag `gas-legacy`. Aksi lokal bersama: `.github/actions/mariadb` (MariaDB 11.8 dengan `deploy/mariadb/qc.cnf` untuk tes server) dan `.github/actions/setup` (Bun + cache + `bun install`). Pemilihan pekerjaan menurut bagian yang berubah, tes server 8 shard, dan build desktop: lihat "CI selektif" di bawah.

## Server di VPS (`deploy-server.yml`)

Alur satu run: **`meta`** (menentukan environment dan commit yang dibangun, menolak kombinasi terlarang) -> **`ci`** (memanggil `ci.yml`: pemeriksaan terpilih menurut bagian yang berubah, tes server dengan MariaDB sungguhan di runner tanpa tunnel; lihat "CI selektif") -> **`image`** (dilewati bila isi image tak berubah; `docker buildx build` + dorong ke `ghcr.io/<pemilik>/qc-app:<SHA commit penuh>`; build web `bun run build` + `verify-dist` terjadi di dalam Dockerfile; cache lapisan di registry GHCR) -> **`deploy`** (SSH ke VPS: `deploy.sh` menarik image, `up -d`, menunggu sehat, menguji `/api/ping` lokal LALU lewat nginx dari dalam VPS, rollback bila gagal; lalu uji asap publik dari runner yang hanya informatif) -> **`mark-deployed`** (hanya bila `deploy` sukses: mencatat commit itu sebagai ref git `refs/deployed/<environment>`; dasar pemilihan pemeriksaan run berikutnya, lihat "CI selektif").

| Kejadian | Environment | Catatan |
|---|---|---|
| PR **di-merge** ke `dev` (`pull_request_target`, closed + merged) | `staging` (`qc-dev.rhd.my.id`) | membangun commit hasil merge (`merge_commit_sha`); PR yang ditutup tanpa merge dilewati |
| PR **di-merge** ke `main` (`pull_request_target`, closed + merged) | `production` (`qc.rhd.my.id`) | sama; PR rilis `dev` -> `main` itu sendiri adalah deploy production |
| push langsung ke `main` atau `dev` | tidak ada | tidak memicu deploy (keputusan pemilik 2026-11-06, spek §11/§13.2: hanya PR yang di-merge) |
| Manual (Actions -> Deploy Server -> Run workflow) | pilihan `staging`/`production` | `production` hanya dari `main`; `staging` dari `main` atau `dev`; ref lain ditolak oleh job `meta` sebelum checkout dan sebelum rahasia dibaca |

Perubahan hanya di `docs/**` dan `**/*.md` tidak memicu deploy (tidak masuk ke image).

**Label `skip-deploy`** (dibuat 2026-11-07): PR yang diberi label ini SEBELUM di-merge tidak men-deploy (job `meta` dilewati, semua job lain ikut dilewati; run tampil "skipped"). Berguna untuk PR yang hanya mengubah hal yang tak perlu sampai ke server sekarang (mis. tes, dokumen kode, atau perubahan yang ingin digabung dengan PR berikutnya). Kodenya tidak hilang: deploy berikutnya membangun commit hasil merge terbaru sehingga ikut ter-deploy, dan karena pemeriksaan dipilih menurut perubahan SEJAK DEPLOY TERAKHIR (`refs/deployed/<env>`, bukan menurut berkas PR pemicu saja), perubahan PR yang dilewati itu ikut memilih pemeriksaan dan image deploy berikutnya (keputusan pemilik 2026-11-17). Label dibaca dari payload saat PR ditutup, jadi memasangnya setelah merge tidak berpengaruh; `workflow_dispatch` (deploy manual) selalu jalan. Label hanya dapat mengurangi deploy, tidak pernah menambahnya, jadi aman walau dipasang pihak lain.

### CI selektif, shard, dan build desktop (keputusan pemilik 2026-11-17)

Spek: `docs/superpowers/specs/2026-11-17-ci-selektif-shard-design.md`; rencana: `docs/superpowers/plans/2026-11-17-ci-selektif-shard.md`. Monorepo ini punya FE, BE, dan desktop; pipeline kini mengerjakan hanya yang berubah.

- **Deteksi perubahan** (`scripts/ci-changes.ts`, job `changes` di `ci.yml`): daftar berkas diambil lewat API (termasuk `previous_filename` untuk rename; token `pull-requests: read`, tanpa checkout kode PR) lalu dipetakan ke keluaran boolean. Sumber daftar: di `test.yml` (PR) = `pulls/{n}/files`; di `deploy-server.yml` pada PR yang di-merge = perbandingan `refs/deployed/<environment>...<commit yang dibangun>` (input `since-deploy`, lihat butir "Penunjuk deploy terakhir"); `workflow_dispatch` tanpa keduanya = semua dijalankan. Aturan: `server/**` -> tes server + image; `web/**` -> tes web + pemeriksaan kemas desktop + image; `shared/**` -> server, web, shared, desktop (di `dev` desktop mengimpor `@shared/desktop-catalog`; ditemukan tes pemindai impor di CI PR 102), kemas desktop, image; `countrylock/**` -> web, desktop, kemas desktop, image; `desktop/**` -> tes desktop + kemas desktop, **tanpa image** (PR desktop saja tidak men-deploy server), kecuali `desktop/package.json` yang memicu image (Dockerfile menyalinnya; keputusan pemilik 2026-11-17); `deploy/**` -> tes server (tes `deploy-files`/`deploy-script`); dokumentasi (`docs/**`, `**/*.md`, `.superpowers/**`, `.claude/**`) -> tak menyalakan apa pun, kecuali `docs/ci-cd.md` (dibaca tes `ci-workflows`) yang menyalakan lint + tes scripts (keputusan pemilik 2026-11-17). Jalur lain (`.github/**`, `scripts/**`, `package.json`, `bun.lock`, berkas atau folder baru) menyalakan SEMUA; begitu pula daftar kosong, lebih dari 2.900 berkas, API gagal, `refs/deployed/<env>` belum ada atau tak terbaca, dan `workflow_dispatch` (tanpa nomor PR dan tanpa `since-deploy`). Konservatif: lebih baik menjalankan berlebih daripada melewatkan.
- **Tes web 4 shard** (keputusan pemilik 2026-11-17): matrix 4 job `web` (`vitest run --shard=<i>/4`, nilai lewat env `WEB_TEST_SHARD`; vitest membagi berkas tes sendiri). Alasan: satu job memakan ~7,6 menit pada run PR 102 (2.795 tes, jsdom per berkas); lokal satu shard menjalankan ~683 tes. Tiap job menginstal dependensi sendiri, dan tes web tak butuh basis data.
- **Tes server 8 shard**: matrix 8 job `server` (`QC_TEST_SHARD=<i>/8`, `server/scripts/test.ts` + `partition.ts`); tiap job punya runner dan MariaDB sendiri, satu proses per job. Menambah proses di satu runner tidak membantu (terikat CPU 2 vCPU repo privat, dan 8 proses x 8 koneksi melebihi `max_connections` 40). Lokal tak berubah (3 proses, tunnel).
- **Gerbang `test`**: job `test` di `test.yml` (status check wajib branch protection) menunggu `ci`; `success` dan `skipped` lulus (PR hanya dokumentasi tetap hijau), `failure`/`cancelled` gagal. Gerbang sengaja di pemanggil: nama check dari workflow yang dipanggil menjadi `<job pemanggil> / <job>`.
- **Uji bangun image PR** (`image-check` di `ci.yml`, input `build-image`): paralel dengan tes (output workflow yang dipanggil baru tersedia setelah seluruh `ci.yml` selesai, jadi job di pemanggil akan serial). Hanya membaca cache registry; tak pernah mendorong image atau menulis cache.
- **Cache lapisan registry** (`deploy-server.yml` job `image`): `cache-to` = `<image>:buildcache-<environment>` (`mode=max`) untuk SEMUA event. Alasan: token `pull_request_target` ditolak menulis cache GHA, sehingga cache lama hanya ditulis dispatch dan merge PR hampir selalu membangun ulang web. **Yang dibaca ditentukan langkah `cache`** (keputusan pemilik 2026-11-17): **staging** membaca `buildcache-staging` dan `buildcache-production`, sehingga tahap `web-build` Dockerfile dipakai dari cache bila `web/`, `shared/`, `countrylock/`, `scripts/`, atau manifest tak berubah (perubahan server saja tak membangun ulang aset web); **production tanpa cache** (`no-cache: true`, `cache-from` kosong). Alasan: siapa pun yang boleh mendorong branch di repositori ini dapat menulis tag `buildcache-*` dengan lapisan berisi lain (peracunan cache), dan production tak boleh membangun dari lapisan yang tak dihasilkan dirinya. Dipilih `no-cache` penuh, bukan hanya tahap `web-build`, karena lapisan `RUN` lain (`bun install`, `apk add`) juga berakhir di image runtime; biayanya production membangun ulang seluruh image (lebih lambat). Staging tetap menanggung risiko peracunan itu (dicatat; image staging bukan production). Tag `buildcache-*` menambah paket `qc-app` di GHCR dan tak disentuh `QC_KEEP_IMAGES` (itu hanya untuk image di VPS).
- **Penunjuk deploy terakhir** (`refs/deployed/<environment>`, job `mark-deployed`; keputusan pemilik 2026-11-17): masalahnya, pemilihan pemeriksaan hanya dari berkas PR pemicu membuat perubahan terlewat bila run sebelumnya dilewati (label `skip-deploy`), dibuang antrean `concurrency`, atau gagal; image yang di-deploy lalu tak memuat perubahan itu. Solusinya mencatat commit yang BERHASIL di-deploy sebagai ref git (bukan tag atau release: tak muncul di daftar rilis dan tak bentrok dengan tag semver `server-v*` kelak), lalu run berikutnya membandingkan commit yang dibangun dengan ref itu (SATU panggilan `gh api repos/<repo>/compare/<ref>...<sha>` tanpa `--paginate`, termasuk `previous_filename`). Semua dijalankan (peringatan di log) bila: ref belum ada (deploy pertama sesudah perubahan ini) atau tak terbaca, perbandingan gagal, **status perbandingan bukan `ahead`** (tiga-titik menghitung dari merge-base, jadi bila deploy terakhir bukan leluhur commit ini, mis. staging pernah di-dispatch dari `main` lalu PR `dev` hanya-desktop di-merge, selisih sebenarnya lebih besar dari daftar itu), atau **300 berkas atau lebih** (batas API compare: daftar berkas hanya di halaman pertama dan maksimum 300 untuk seluruh perbandingan, sisanya terpotong diam-diam; hasil review independen 2026-11-17). Pengaman 2.900 berkas di `ci-changes.ts` untuk sumber berkas PR tak berlaku di sini. Job `mark-deployed` hanya jalan bila `deploy` sukses, adalah SATU-SATUNYA job berizin `contents: write`, tanpa checkout, aksi pihak ketiga, dan rahasia; ia memvalidasi `TARGET` dan `SHA` sebelum memanggil `gh api` (PATCH bila ada, POST bila belum) dan hanya menulis jalur `refs/deployed/staging|production`. Gagal menulis = peringatan, bukan kegagalan (deploy sudah sukses; akibatnya hanya run berikutnya memeriksa lebih banyak). Ref ini dapat dilihat dengan `git ls-remote origin 'refs/deployed/*'` dan dipulihkan manual dengan `git push -f origin <sha>:refs/deployed/<env>` bila perlu. Deploy manual (`workflow_dispatch`) memeriksa semuanya dan, bila sukses, ikut menggeser ref lewat job yang sama. Keamanan: namespace `refs/deployed/*` tidak dilindungi branch protection/ruleset branch dan tag, jadi siapa pun berizin tulis dapat menimpanya (`git push -f origin <sha>:refs/deployed/<env>`) untuk menyempitkan pemeriksaan pasca-merge; mereka tak dapat men-deploy kode yang melewati gerbang PR (gerbang `test` memakai berkas PR, dan image selalu dibangun dari `merge_commit_sha`), jadi risiko sisanya kecil dan diterima (aktor berizin tulis sudah lebih berkuasa).
- **Build desktop** (job `desktop` di `ci.yml`, `windows-latest`): hanya PEMERIKSAAN build dan HANYA di PR (input `desktop-check` di `ci.yml`, dinyalakan `test.yml`; `deploy-server.yml` tak menjalankannya agar kegagalan kemas desktop tak menahan deploy server) (tanpa artefak dan tanpa installer, bukan rilis; keputusan pemilik 2026-11-17: Windows x64 + Windows arm64, tanpa Linux). `bun run build:web` -> `bun run --cwd desktop pack:all` (x64 dan arm64) -> `verify-pack --arch x64` (asap `--smoke` penuh) dan `--arch arm64` (hanya pemeriksaan statis: exe, `app.asar`, `ui-baseline` ada). arm64 dikemas silang dari x64 dan tak dapat diasapkan karena runner Windows arm64 (`windows-11-arm`) setahu kami hanya gratis untuk repo publik; bila tersedia kelak, ganti `runs-on` untuk menjalankan asap arm64. `desktop/electron-builder.yml` tak diubah (NSIS tetap x64); installer arm64 menunggu workflow rilis. `UI_PUBLIC_KEY_PEM` tak dipakai (bukan build rilis).
- **Gerbang fragmen changelog** (`changelog.yml`, job `fragmen`; rancangan `docs/superpowers/specs/2026-11-17-rilis-semver-design.md` bagian 5.2): PR yang mengubah `server/`, `web/`, `shared/`, atau `countrylock/` harus membawa fragmen baru di `server/changelog.d/`; yang mengubah `desktop/`, `shared/`, atau `countrylock/` di `desktop/changelog.d/` (`shared/` dan `countrylock/` mewajibkan keduanya). Satu fragmen = berkas `<yyyymmdd>-<slug>.md`, baris pertama `jenis: ditambah|diubah|diperbaiki|internal`, lalu SATU paragraf untuk pengguna (`internal` hanya tampil di GitHub Release). Label **`tanpa-changelog`** melewatkan pemeriksaan; PR rilis (semua berkas adalah metadata: versi, `bun.lock`, `CHANGELOG.md`, fragmen) dikenali dari ISI diff, bukan nama cabang. Pemicu `pull_request` termasuk `labeled`/`unlabeled`, dipisah dari `test.yml` agar label tak mengulang seluruh CI. Ini penanda di PR, bukan penghalang merge yang dipaksakan (branch protection tak tersedia di paket repo ini). Perkakas: `bun run changelog validate|compile|extract <server|desktop>` (`scripts/changelog.ts`); `CHANGELOG.md` server ikut ke image untuk halaman "Pembaruan" di web.
- **Rencana rilis terpisah** (belum dibangun; keputusan pemilik 2026-11-17: image dan desktop dirilis terpisah dengan versi masing-masing): tag `server-v<semver>` untuk image dan `desktop-v<semver>` untuk installer (versi desktop dari `desktop/package.json`). UI web sampai ke desktop lewat manifest bertanda tangan, jadi perubahan `web/` atau `shared/` cukup merilis server; desktop dirilis hanya untuk `desktop/**`, `countrylock/**`, atau perubahan endpoint desktop di server (`/auth/desktop/*`, `/api/desktop/*`, aliran notifikasi), yang wajib kompatibel mundur (expand -> kontrak). Keluaran `image` dan `desktop_pack` dari `ci-changes.ts` dipakai ulang untuk memilih apa yang dirilis. Kompatibilitas UI baru terhadap desktop lama dijaga `BRIDGE_VERSION`/`UI_MIN_BRIDGE_VERSION` (`minBridge` di manifest).
- **Belum terverifikasi sampai run pertama di GitHub**: cache registry (termasuk izin tulis paket `qc-app` untuk repo ini), kemas silang arm64 di runner, nama check `test` di branch protection, dan lamanya tiap job (belum diukur; catat angka run pertama di sini). Dijaga lokal oleh `scripts/ci-workflows.test.ts` dan `scripts/ci-changes.test.ts`; `pack:all` + `verify-pack` x64/arm64 sudah dijalankan di Windows x64 pengembang.

### Cutover (T34), selesai 2026-11-07

Sebelum cutover, GitHub hanya menjalankan `workflow_dispatch` dan `pull_request_target` bila berkas workflow ada di branch default (`main`, dibekukan sebagai jalur GAS), sehingga staging di-deploy lewat `push` ke `feat/migrasi-cloudflare`. Pemicu `push` itu, branch kerja itu di job `meta` dan di dispatch, serta `deploy.yml` (GAS) dihapus dalam PR cutover (spek §13 butir 1, §19 butir 14); `scripts/ci-workflows.test.ts` menegakkan daftar pemicu dan branch yang baru. Dua hal tetap pekerjaan pemilik di GitHub: aturan *Deployment branches* environment `staging` menjadi hanya `dev` dan `main`, dan *Required reviewers* pada `production` (disarankan, bukan wajib; keputusan pemilik 2026-11-06). Merge PR ke `main` otomatis men-deploy production. Perubahan `deploy/compose.yml`, `deploy/deploy.sh`, `deploy/mariadb/qc.cnf`, dan variabel `.env` baru tetap harus dipasang manual di VPS sebelum merge (lihat "Perubahan berkas deploy").

### Yang HARUS dibuat pemilik di GitHub (workflow tidak dapat mengaturnya sendiri)

Repositori -> Settings -> Environments:

1. **Environment `staging`**: *Deployment branches and tags* -> *Selected branches* -> hanya `dev` dan `main` (setelah cutover; `feat/migrasi-cloudflare` dikeluarkan) (teramati 2026-11-07: run `pull_request_target` SELALU berjalan dengan `REF=refs/heads/main`, juga untuk PR yang bertujuan `dev`; yang dinilai aturan environment adalah `main`, bukan `dev` dan bukan `refs/pull/N/merge`. Branch tujuan PR hanya ada di `github.event.pull_request.base.ref`, yang dipakai job `meta` untuk memilih `staging` (dev) atau `production` (main); `dev` dalam aturan environment boleh tetap ada untuk `workflow_dispatch` dari `dev`).
2. **Environment `production`**: *Selected branches* -> hanya `main`. *Required reviewers* **disarankan** untuk production (tidak diwajibkan pemilik).
3. **Secret environment** (BUKAN secret repositori; buat di KEDUA environment dengan nilai milik masing-masing):

| Nama | Isi |
|---|---|
| `DEPLOY_SSH_KEY` | kunci PRIVAT SSH khusus deploy (ed25519) untuk environment itu, hasil langkah 9 `docs/deploy-vps.md` (satu pasang per environment; publiknya dipasang di `authorized_keys` VPS sebagai `restrict,command="<INSTALL_DIR>/deploy.sh --only <env>" ssh-ed25519 AAAA...` di `authorized_keys` milik pengguna deploy; `<INSTALL_DIR>` = jalur mutlak `deploy.sh` yang sebenarnya, VPS pribadi `/root/apps/qc-app`; `restrict` sudah mencakup no-pty, no-port-forwarding, no-agent-forwarding, no-X11-forwarding, dan no-user-rc, jadi opsi `no-*` terpisah tak perlu) |
| `DEPLOY_HOST_KEY` | baris `known_hosts` host VPS, mis. `[<host>]:<port> ssh-ed25519 AAAA...` dari `ssh-keyscan -p <port> -t ed25519 <host>`; bandingkan sidik jarinya dengan `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` di VPS SEBELUM menyimpan (kunci host dipatok: koneksi ke host lain ditolak, tanpa `StrictHostKeyChecking=no`) |
| `DEPLOY_HOST` | alamat VPS (IP atau nama) |
| `DEPLOY_PORT` | port SSH VPS (non-standar) |
| `DEPLOY_USER` | pengguna deploy di server. VPS pribadi: `root` (akses lewat kunci `command=` terbatas, dikonfirmasi pemilik 2026-11-06). Server kantor nanti: pengguna non-root di grup `docker` (keputusan pemilik 2026-11-07, spek §19 butir 11; lihat `docs/deploy-vps.md` bagian 14) |

4. **Variabel environment** (Variables, bukan Secrets): `APP_URL` = `https://qc-dev.rhd.my.id` (environment `staging`) dan `https://qc.rhd.my.id` (environment `production`), tanpa garis miring penutup. Dipakai uji asap publik informatif `GET <APP_URL>/api/ping` dari runner (tidak menggagalkan job; lihat "Uji asap").

Penamaan (keputusan pemilik 2026-11-07, spek §19 butir 10): nama environment GitHub, kunci deploy (`--only`, perintah `deploy <env> <sha>`), folder instalasi (`<INSTALL_DIR>/<env>`; VPS pribadi `/root/apps/qc-app/<env>`), dan `QC_ENV` sama: `staging` | `production` (sebelumnya `dev` | `exec`). Environment GitHub tidak dapat diganti nama: buat `staging` dan `production`, salin secret/variabel dan aturan branch dari `dev`/`exec`, lalu hapus yang lama. `deploy.sh` memakai kunci per lingkungan, jadi baris `authorized_keys` juga harus `--only staging` / `--only production`.
5. **Token baca GHCR di VPS** (bukan di GitHub): paket `qc-app` dibuat privat bila repositori privat. Pilihan: (a) **PAT classic dengan scope `read:packages`** milik pemilik, `docker login ghcr.io -u <pengguna>` sekali di server SEBAGAI pengguna deploy (tersimpan di `~/.docker/config.json` pengguna itu; VPS pribadi `/root/.docker/config.json`, izin 600): paket tetap privat, tetapi token berumur panjang di VPS dan terkait akun pemilik, jadi buat khusus untuk ini dan atur kedaluwarsa; (b) **jadikan paket publik** (Package settings -> Change visibility): tanpa token di VPS, tetapi isi image (kode aplikasi; rahasia tak ada di image) dapat diunduh siapa pun. Rekomendasi: (a). Image tidak memuat rahasia (tes `server/src/deploy-files.test.ts`).
6. Tidak ada rahasia lain di GitHub: `GITHUB_TOKEN` otomatis (izin `packages: write` hanya di job `image`); rahasia aplikasi (`.env`, kunci service account) hanya di VPS.
7. **sshd di server**: kunci deploy hanya boleh menjalankan `deploy.sh`, bukan shell. Bila pengguna deploy = `root` (VPS pribadi), periksa `PermitRootLogin prohibit-password` (atau `forced-commands-only`) di `/etc/ssh/sshd_config`; untuk pengguna non-root pastikan `PasswordAuthentication no`.

### Perubahan berkas deploy (salin manual di VPS SEBELUM push yang men-deploy)

**Catatan 2026-11-07 (spek §19 butir 19):** `deploy.sh` berubah (salinan `.env` sementara dan pemulihan apa adanya saat `pull` gagal). Salin `deploy/deploy.sh` terbaru ke `<INSTALL_DIR>/deploy.sh` (izin 700) di VPS SEBELUM merge yang membawanya; skrip lama tetap berfungsi, hanya tanpa perbaikan itu.

**Catatan 2026-11-07 (spek §19 butir 15):** `compose.yml` kini memberi `MARIADB_DATABASE`/`MARIADB_USER`/`MARIADB_PASSWORD` ke `qc-db` (skema dan pengguna aplikasi dibuat otomatis pada volume BARU; pada volume lama diabaikan). Konfigurasi `qc-db` berubah, jadi pada staging `qc-db` DIBUAT ULANG pada `docker compose up -d` berikutnya setelah `compose.yml` baru disalin (beberapa detik; data aman di volume). Langkah manual: salin `compose.yml` baru SEBELUM push yang men-deploy, lalu jalankan `docker compose up -d` sekali di folder lingkungan itu.

**Catatan 2026-11-16 (bukti foto QC Serial Number, bagian 2):** `compose.yml` menambah volume `qc-proofs` (berkas sementara foto bukti di `/var/lib/qc/proofs`, `PROOF_STAGING_DIR`) dan variabel `PROOF_STAGING_MAX_BYTES` (opsional; kosong = 2 GiB). Prasyarat manual: salin `deploy/compose.yml` dan `deploy/.env.example` terbaru ke `<INSTALL_DIR>/<env>/` SEBELUM push yang men-deploy (tanpa compose baru, foto sementara ditulis ke lapisan kontainer dan hilang saat kontainer dibuat ulang); `docker compose up -d` membuat volume `qc-proofs` sendiri. Lihat `docs/deploy-vps.md` bagian 4. Migrasi `0019_bukti_foto_qc.sql` hanya menambah tabel (expand-only), jadi skemanya aman bagi image lama. Namun job `serial_proof` yang sudah antre tidak punya handler di image sebelumnya: setelah foto pertama tersimpan, jangan mengembalikan image secara manual ke versi sebelum fitur ini; perbaiki ke depan.

CI hanya mengganti tag image (`QC_IMAGE_TAG`): berkas di folder instalasi server (`<INSTALL_DIR>/<env>/compose.yml`; VPS pribadi `/root/apps/qc-app/<env>/...`, `deploy.sh`, `mariadb/qc.cnf`, `.env`) TIDAK ikut ter-deploy dari repositori. Bila sebuah komit mengubah `deploy/compose.yml`, `deploy/deploy.sh`, `deploy/mariadb/qc.cnf`, atau menambah variabel `.env` baru (mis. variabel wajib baru di `server/src/config.ts` + `compose.yml` + `.env.example`), **salin/isi manual di VPS sebelum push yang men-deploy komit itu** (langkah 4-5 `docs/deploy-vps.md`). Bila terlupa, image baru gagal `loadConfig` atau `compose config` di VPS dan deploy berakhir kode 1 (dikembalikan) atau 2 (tidak ada yang diubah): aman, tetapi memakan satu siklus deploy.

### Pembersihan image lama (`QC_KEEP_IMAGES`)

VPS dipakai bersama aplikasi lain, jadi tiap deploy yang SUKSES PENUH (tag baru sehat dan `/api/ping` lolos) diakhiri pembersihan image lama oleh `deploy.sh` (`cleanup_images`). Tidak pernah berjalan pada deploy gagal atau pengembalian (image tag sebelumnya adalah target pengembalian). Aturan:

- Hanya repositori image stack ini (`QC_IMAGE` di `.env`, bawaan yang tertulis di `compose.yml`) dan hanya tag `<sha-40-heksa>` atau `local-<sha>`; tag lain dibiarkan. Daftar dibaca dari `docker image ls <repo>` (terurut dari yang terbaru dibuat), dihapus satu per satu dengan `docker image rm <repo>:<tag>` (tanpa `-f`; image yang masih dipakai gagal dengan aman dan diabaikan).
- Dipertahankan: `QC_KEEP_IMAGES` tag terbaru (variabel opsional di `.env`, bawaan 3; harus `^[1-9][0-9]?$`, nilai lain = 3), tag baru, tag sebelumnya, tag yang dipakai kontainer ini, dan tag `QC_IMAGE_TAG` di `.env` lingkungan LAIN (`$ROOT/*/.env`; staging dan production memakai satu repositori GHCR, jadi deploy satu lingkungan tidak menghapus image yang lain).
- TIDAK pernah: `docker system prune`, `docker image prune`, `docker volume prune`, atau menyentuh image, volume, dan kontainer di luar daftar di atas (termasuk image dangling).
- Kegagalan pembersihan hanya dicatat; kode keluar deploy tetap 0. Keluaran docker masuk `.deploy.log` di VPS; log skrip hanya ringkasan (`dihapus=N gagal/dilewati=M`). `--dry-run` mencetak rencananya.
- `QC_KEEP_IMAGES` hanya dibaca `deploy.sh` dari `.env` (bukan `config.ts`), jadi tidak ada di `compose.yml`. Berkas `deploy.sh` baru wajib disalin manual ke VPS (bagian di atas).

### Kesehatan database saat deploy

Butir spek "uji asap ... (dan kesehatan database)" dipenuhi oleh gerbang migrasi saat start: kontainer yang `healthy` berarti basis data terjangkau saat start dan migrasi sudah diterapkan. `/api/ping` sengaja tidak memeriksa basis data (endpoint publik tanpa batas); ia tidak mendeteksi basis data yang hilang SETELAH start.

### Urutan uji pertama (setelah pemilik mengatur di atas)

1. Pastikan VPS siap (`docs/deploy-vps.md`, termasuk kunci SSH deploy langkah 9). Khusus staging yang kini memakai image lokal: **hapus atau komentari `QC_IMAGE`** di `.env` staging (`deploy.sh` menolak dengan kode 2 bila `QC_IMAGE` bukan `ghcr.io/...`; tanpanya compose memakai `ghcr.io/<pemilik>/qc-app`), dan jalankan `docker login ghcr.io` (lihat butir 5 di atas) agar `compose pull` berhasil. Catatan: `QC_IMAGE_TAG=local-<sha>` lama menunjuk `ghcr.io/...:local-<sha>` yang tak ada, jadi **deploy GHCR pertama tidak punya target pengembalian**: bila `pull` gagal, `.env` dipulihkan dan kontainer lokal yang berjalan tidak tersentuh (kode 1); bila gagal sesudah `up -d` (tak sehat, ping gagal), pengembalian ke tag `local-<sha>` tak mungkin dan skrip berakhir kode 4: pulihkan manual (kembalikan `QC_IMAGE=qc-app` dan tag lokal, `docker compose up -d`).
2. Setelah cutover: merge PR ke `dev` (atau Run workflow dari `dev`/`main` dengan target `staging`). Perhatikan tab Actions: `meta` -> `ci` -> `image` -> `deploy`.
3. Bila `image` gagal di `buildx`, perbaiki Dockerfile (build BuildKit di Actions belum pernah dijalankan; yang terbukti hanya pembangun klasik di VPS).
4. Bila `deploy` gagal "Secret environment ... belum diisi" atau "Host key verification failed", periksa daftar di atas. Kode keluar skrip VPS: 0 sukses, 1 gagal dan dikembalikan ke tag sebelumnya, 4 gagal dan pengembalian juga gagal (periksa VPS manual), 2 ditolak (input, `QC_IMAGE` non-GHCR, kredensial DB di `.env` tak cocok dengan database yang berjalan = preflight) atau `.env`/`compose.yml` tidak valid (`compose config` gagal; tidak ada yang diubah), 3 deploy lain sedang berjalan, 5 versi baru sehat dan aktif tetapi nginx tidak terjangkau (tidak dikembalikan; periksa nginx). Keluaran `docker compose` TIDAK muncul di log Actions (dapat memuat potongan rahasia dari `.env`): lihat `<INSTALL_DIR>/<env>/.deploy.log` di server (VPS pribadi `/root/apps/qc-app/<env>/.deploy.log`) (izin 600, ditimpa tiap deploy).
5. Uji pemulihan sekali di staging **setelah deploy GHCR kedua sukses** (baru saat itu ada tag GHCR sebelumnya yang dapat dikembalikan): dorong komit yang memecahkan `/api/ping` dan pastikan job gagal dan VPS kembali ke tag lama.

### Keamanan workflow (ditegakkan `scripts/ci-workflows.test.ts`)

- `pull_request_target` (menerima rahasia walau PR dari fork) hanya `types: [closed]` untuk `dev`/`main`, dan hanya setelah PR **di-merge**: job `meta` punya `if` merged dan skripnya menolak selain `merged == true`, menolak bila `REF` bukan `refs/heads/main` (run selalu dari branch default), dan memetakan `PR_BASE_REF` `main` -> production, `dev` -> staging (branch lain ditolak). Yang dibangun dan di-checkout HANYA commit dari output `sha` job `meta` (= `merge_commit_sha`, kode yang sudah masuk ke branch tujuan; divalidasi 40 heksa); tak ada `pull_request.head`, `head_ref`, atau `refs/pull/` di mana pun. Tanpa `pull_request` biasa. PR fork yang belum di-merge tidak pernah mendapat rahasia maupun menjalankan kodenya. Jangan menambah langkah yang meng-checkout head PR. Push langsung ke `main`/`dev` tidak memicu deploy, dan tidak ada pemicu `push` sama sekali.
- PR yang ditutup tanpa merge dilewati dan memakai grup `concurrency` sendiri (tidak menggantikan run deploy yang menunggu).
- Semua aksi pihak ketiga pada `deploy-server.yml`, `test.yml`, `ci.yml`, dan aksi lokal (`mariadb`, `setup`) dipatok ke SHA commit (tag mayor di komentar; diambil 2026-11-06, `actions/cache` v4.2.4 diambil 2026-11-17). Perbarui dengan sengaja, bukan otomatis.
- `permissions` minimal: `contents: read` di tingkat atas; hanya job `image` yang `packages: write`; hanya job `mark-deployed` yang `contents: write` (menulis `refs/deployed/*`); job `deploy` `permissions: {}` dan tanpa checkout. `ci.yml` tanpa rahasia (tak ada `secrets.*`, tak ada kunci tanda tangan UI); hanya job `changes` yang `pull-requests: read` (membaca daftar berkas PR), `image-check` `packages: read` (cache), dan pemanggil `ci` wajib memberi izin yang sama walau `build-image` false.
- Tidak ada `${{ }}` di dalam skrip `run`: nilai lewat `env`, sehingga tak ada injeksi ekspresi.
- Antrean serial per environment (`concurrency` `deploy-server-<env>`, tanpa membatalkan yang berjalan; GitHub hanya menyimpan satu run menunggu, yang lebih lama dibatalkan). Pengaman kedua: `deploy.sh` memakai kunci per lingkungan (kode 3).
- Kunci host dipatok; kunci privat ditulis ke runner dengan izin 600 dan dihapus di langkah `always()`.
- Tag yang boleh diminta ke VPS hanya SHA commit 40 heksa huruf kecil (`deploy.sh` menolak `latest` dan sejenisnya); keluaran `docker compose` tak diteruskan ke log Actions (lihat di atas); `.env`/`compose.yml` rusak berhenti di `compose config` tanpa mengubah apa pun.
- Preflight kredensial DB (keputusan pemilik 2026-11-07, spek §19 butir 13): setelah `compose config` lulus dan SEBELUM `.env`/pull/up disentuh, bila kontainer DB lingkungan itu berjalan `deploy.sh` menjalankan `mariadb ... SELECT 1` di dalamnya dengan `QC_DB_USER`/`QC_DB_PASSWORD`/`QC_DB_NAME` dari `.env` (kata sandi lewat env `MYSQL_PWD`, bukan argumen; keluaran ke `.deploy.log`). Gagal = kode keluar 2 ("kredensial DB di .env tidak cocok dengan database yang berjalan"), tidak ada yang diubah dan tidak ada rollback. Alasan: `.env` yang berubah tak sengaja atau rotasi dengan urutan terbalik membuat aplikasi baru gagal login dan rollback (hanya mengganti tag) tak menolong. Deploy pertama (DB belum berjalan) dilewati. Prosedur rotasi: `docs/deploy-vps.md` 12b.
- Uji asap (keputusan pemilik 2026-11-07, spek §19 butir 12): yang MENENTUKAN adalah `deploy.sh` di dalam VPS. Setelah kontainer sehat dan `/api/ping` lokal lulus, `deploy.sh` menguji nginx: `curl -k --resolve <host>:443:127.0.0.1 https://<host>/api/ping` dengan `<host>` dari `APP_ORIGIN` di `.env` (dilewati bila `APP_ORIGIN` bukan `https://<host>` polos, mis. dev lokal). Dua jenis kegagalan dibedakan setelah 5 percobaan: nginx MENJAWAB tetapi bukan 2xx (mis. 502/503/404; curl exit 22; dapat terkait versi) = rollback otomatis ke tag sebelumnya (kode keluar 1; 4 bila rollback gagal); nginx TIDAK TERJANGKAU (ditolak, timeout, putus sebelum respons HTTP; mis. nginx mati) = masalah infrastruktur, bukan versi: TIDAK dikembalikan, versi baru tetap aktif, pembersihan image tidak dijalankan, kode keluar 5 dan job CI merah dengan pesan jelas (periksa `systemctl status nginx`). Rollback sendiri hanya mensyaratkan sehat + ping lokal, bukan nginx. `-k` hanya untuk uji ini: sertifikat origin Cloudflare bukan CA publik; yang diuji "nginx menjawab", verifikasi sertifikat dilakukan Cloudflare (SSL Full strict). Langkah "Uji asap publik" dari runner GitHub hanya INFORMATIF (`continue-on-error`, `::warning::` bila gagal): Cloudflare memblokir IP datacenter runner (403) dan origin hanya menerima IP Cloudflare, jadi kegagalannya tidak mencerminkan kesehatan aplikasi dan tidak menggagalkan job.

### Manifest UI bertanda tangan (pembaruan UI aplikasi desktop; rencana `2026-11-12-qc-desktop-penuh-login-bearer-ui-hibrid`, Task H6)

- `bun run build` (akar) menjalankan `scripts/build-ui-manifest.ts` SESUDAH `verify-dist`: menulis `server/dist/ui-manifest.json` (`uiVersion`, `minBridge`, daftar semua berkas build dengan `sha256` dan `size`, urut abjad, `createdAt`). Berkas manifest sendiri dan `ui-manifest.sig` tidak masuk daftar; symlink di `server/dist` ditolak. Tanda tangan lama dibuang tiap manifest dibuat ulang. `minBridge` = `UI_MIN_BRIDGE_VERSION` (`countrylock/src/ui-manifest.ts`), dinaikkan hanya bila UI memakai fungsi jembatan baru.
- Tanda tangan (Ed25519 atas BYTE persis `ui-manifest.json`, disimpan base64url di `ui-manifest.sig`) dibuat `scripts/sign-ui-manifest.ts --key <berkas PEM>` (atau env `UI_SIGNING_KEY_FILE`; isi kunci tidak pernah dicetak). Di `Dockerfile` langkah ini hanya berjalan bila secret BuildKit `ui_signing_key` diberikan (`RUN --mount=type=secret,id=ui_signing_key,required=false`); tanpa secret langkah dilewati dengan pesan di log build dan `GET /api/desktop/ui-manifest` menjawab 404 (desktop tetap memakai UI dasar yang dibundel). Bila `UI_PUBLIC_KEY_PEM` (build-arg) diberikan, kecocokan privat↔publik diperiksa langsung sebelum `.sig` ditulis; `--require-public-key` (dipakai Dockerfile) menjadikannya wajib bila menandatangani.
- `GET /api/desktop/ui-file/<jalur>` publik: menyajikan HANYA berkas yang tercantum di manifest bertanda tangan, sebagai `application/octet-stream` + `Cache-Control: no-cache, no-transform` (desktop mengunduh bundel dari sini). Alasannya: Cloudflare di depan staging/production menyisipkan skrip deteksi bot ke respons `text/html` (`index.html` menjadi 6677 byte, bukan 5563) sehingga unduhan lewat jalur statis selalu gagal verifikasi ukuran/sha256; tipe non-HTML tak disentuh.
- `GET /api/desktop/ui-manifest` publik (tanpa sesi), `Cache-Control: no-cache`, `ETag` dari manifest + tanda tangan (304 pada `If-None-Match`), isi `{ manifest, signature }`. Server hanya MENYAJIKAN; ia tidak memegang kunci apa pun dan tidak memverifikasi tanda tangan (desktop memverifikasi `JSON.stringify(manifest)` dengan kunci publik yang tertanam di aplikasi).
- **Langkah pemilik** (workflow sudah dipasang 2026-11-16; yang tersisa hanya membuat dan mengisi kunci; rinci di `docs/desktop-ui-signing.md`). Tanpa langkah ini build tetap hijau, hanya tanpa tanda tangan (peringatan di log):
  1. Bangkitkan pasangan kunci SEKALI di mesin pribadi: `bun run scripts/gen-ui-signing-key.ts C:\jalur\pribadi\qc.ui-signing-key.pem` (kunci privat ditulis ke berkas itu, tidak dicetak, tidak menimpa; kunci publik ditulis ke `qc.ui-signing-key.pub.pem` dan dicetak, termasuk nilai SATU baris untuk Variable). Nama berakhiran `.ui-signing-key.pem` ditangkap `.gitignore`; jangan dikomit. Simpan cadangan kunci privat di tempat aman (hilang = rilis aplikasi desktop baru dengan kunci publik baru).
  2. Simpan ISI berkas privat sebagai **secret environment** `UI_SIGNING_KEY` pada environment `staging` DAN `production` (Settings > Environments; job `image` memakai environment yang sama dengan target deploy, jadi nilainya harus ada di keduanya; penempatan pemilik 2026-11-16, menggantikan environment terpisah `ui-signing` yang semula dirancang). BUKAN secret repositori biasa: itu terbaca oleh workflow mana pun, termasuk yang diubah di branch PR; aturan branch environment itulah yang membatasi pembacanya.
  3. Simpan kunci publik sebagai **Variable** (bukan secret) `UI_PUBLIC_KEY_PEM` pada kedua environment itu (atau di repositori). Bentuk apa pun yang lazim diterima (PEM berbaris banyak berakhir baris Unix/Windows, PEM satu baris, atau isi base64 saja): langkah persiapan menormalkannya menjadi SATU baris isi base64 karena `build-args` berformat satu entri per baris; nilai yang bukan kunci publik terbaca = GAGAL tanpa mencetak isinya. Nilai yang sama dipakai build desktop (`UI_PUBLIC_KEY_PEM` di env shell build; `docs/desktop-ui-signing.md`).
  4. Job `image` (workflow sudah dipasang): `environment: ${{ needs.meta.outputs.target }}`; langkah "Siapkan kunci tanda tangan UI" menulis `UI_SIGNING_KEY` ke berkas sementara di `runner.temp` (izin 0600) dan meneruskannya lewat `secret-files` (bukan `secrets:`, karena nilainya berbaris banyak), kunci publik yang sudah dinormalkan (output `public_key`) lewat `build-args`, lalu langkah terakhir menghapus berkas itu (`if: always()`). Aturannya (ditegakkan `scripts/ci-workflows.test.ts`, termasuk dengan menjalankan skrip langkah itu): secret dan variabel sama-sama kosong = lolos dengan `::warning::` tanpa tanda tangan (perilaku lama, rollout aman); hanya salah satu terisi atau Variable bukan kunci publik yang terbaca = GAGAL. Di Dockerfile `sign-ui-manifest.ts --require-public-key` memeriksa kunci privat berpasangan dengan `UI_PUBLIC_KEY_PEM` (uji tanda tangan sungguhan + sidik) SEBELUM `ui-manifest.sig` ditulis; tidak berpasangan = build gagal. Sidik SHA-256 kunci publik dicetak di log build.
  5. **LARANGAN: jangan memberi `UI_SIGNING_KEY` ke `test.yml` atau workflow lain yang berjalan pada `pull_request`** (tes menegakkannya: hanya `deploy-server.yml` yang boleh menyebutnya, dan hanya job `image`). Job itu membangun Dockerfile dan `scripts/` dari HEAD PR yang belum ditinjau: siapa pun yang dapat mendorong branch dapat mengubah `scripts/sign-ui-manifest.ts` atau langkah Dockerfile untuk membocorkan kunci atau menandatangani bundel UI pilihannya, sehingga pertahanan spek §3.4 (server atau pipeline yang disusupi tak boleh menyajikan UI yang memegang jembatan SSH) gugur. Kunci HANYA untuk job `image` di `deploy-server.yml`, yang membangun kode hasil merge (`merge_commit_sha`). Image hasil `test.yml` memang tak ditandatangani (itu benar dan diinginkan).
  6. Build lokal untuk uji: `docker build --secret id=ui_signing_key,src=<berkas PEM> --build-arg UI_PUBLIC_KEY_PEM=<satu baris> -t qc-app .`. Rotasi kunci membutuhkan rilis aplikasi desktop baru (spek §3.4).
- Alasan secret BuildKit, bukan `ARG`/`ENV`, untuk kunci PRIVAT: nilainya tidak masuk lapisan image atau riwayat build; `.dockerignore` juga menyingkirkan `**/*.pem` dari konteks build. Kunci PUBLIK memang lewat `ARG` karena bukan rahasia.
- **Cache BuildKit**: kunci cache `RUN --mount=type=secret` tidak memuat ISI secret, tetapi nilai `ARG` ikut kunci cache. Karena `UI_PUBLIC_KEY_PEM` (ARG) berubah saat kunci pertama kali dipasang dan saat diputar (kunci publik baru), langkah tanda tangan otomatis dibangun ulang pada kedua peristiwa itu, jadi `.sig` lama tidak diambil dari cache. Tetap pastikan setelah memasang atau memutar kunci bahwa `GET /api/desktop/ui-manifest` menjawab 200 dengan `signature` baru.
- Dockerfile: tahap `manifests` menyalin `package.json` SEMUA workspace akar (`countrylock` dan `desktop` selain shared/web/server) agar `bun install --frozen-lockfile` konsisten dengan `bun.lock`; instalasi web-build memakai `--filter '!@qc/desktop'` sehingga Electron dan dependensi desktop tidak terpasang di image (disimulasikan dengan Bun 1.4.2 di folder sementara berisi hanya `package.json`: tanpa filter `electron`/`ssh2` terpasang, dengan filter tidak; tahap `prod-deps` (`--production --filter @qc/server`) tak berubah). Build Docker sungguhan tak dapat dijalankan di mesin pengembang; yang terbukti di CI hanya setelah job `image` merah/hijau.

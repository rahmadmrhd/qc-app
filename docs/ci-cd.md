# CI/CD (GitHub Actions)

Workflow di `.github/workflows/`: `ci.yml` (pemeriksaan terpilih yang dapat dipanggil, dipakai `test.yml`, `deploy-server.yml`, dan `release.yml`), `test.yml` (PR; gerbang `test`), `deploy-server.yml` (PR yang di-merge ke `dev`/`main` atau dispatch; server Bun + MariaDB di VPS), `changelog.yml` (PR ke `dev`; gerbang fragmen changelog), `release.yml` (PR rilis semver `release/...` yang di-merge ke `main`, atau dispatch pemulihan/penarikan; server, desktop, atau gabungan: butir-butir rilis di bagian "CI selektif, shard, dan build desktop" di bawah), `deploy-tag.yml` (dispatch; men-deploy versi yang sudah dirilis, naik atau turun: "Deploy versi tertentu lewat tag"), `server-image.yml` dan `server-deploy.yml` (workflow bersama `workflow_call`, build image dan deploy VPS + `mark-deployed`, dipanggil `deploy-server.yml`, `release.yml`, dan `deploy-tag.yml`), serta `sync-dev.yml` (workflow bersama; dipanggil `release.yml` untuk menyinkronkan `main` ke `dev` setelah rilis). Workflow deploy Apps Script lama (`deploy.yml`) dihapus saat cutover 2026-11-07; versinya tetap ada di tag `gas-legacy`. Aksi lokal bersama: `.github/actions/mariadb` (MariaDB 11.8 dengan `deploy/mariadb/qc.cnf` untuk tes server) dan `.github/actions/setup` (Bun + cache + `bun install`). Pemilihan pekerjaan menurut bagian yang berubah, tes server 8 shard, dan build desktop: lihat "CI selektif" di bawah.

## Server di VPS (`deploy-server.yml`)

Struktur workflow (rencana rilis semver 2): langkah **build image** hidup di `server-image.yml` dan langkah **deploy ke VPS + `mark-deployed`** di `server-deploy.yml`, keduanya workflow yang dapat dipanggil (`workflow_call`) dan dipakai bersama oleh `deploy-server.yml` (PR/dispatch) serta `release.yml` dan `deploy-tag.yml`, jadi jaminan keamanannya (kunci tanda tangan UI hanya di job image, production tanpa cache, tanpa checkout di job deploy, `contents: write` hanya di `mark-deployed`) tak punya salinan. Pemanggil memakai `secrets: inherit` (keputusan pemilik 2026-11-19; tanpanya secret environment menjadi string kosong di workflow terpanggil walau variabel environment terbaca: bug GitHub actions/runner#4453, teramati pada deploy production pertama struktur ini): rahasia environment tetap dibaca job terpanggil lewat `environment:`-nya sendiri. Aman karena repositori tak punya secret tingkat repositori/organisasi; `ci.yml` tetap tanpa rahasia (dijaga `scripts/ci-workflows.test.ts`). Masukan (`target`, `sha` 40 heksa, `extra-tags` hanya `server-vX.Y.Z`, `allow-schema-downgrade`) divalidasi di workflow terpanggil.

Alur satu run: **`meta`** (menentukan environment dan commit yang dibangun, menolak kombinasi terlarang) -> **`ci`** (memanggil `ci.yml`: pemeriksaan terpilih menurut bagian yang berubah, tes server dengan MariaDB sungguhan di runner tanpa tunnel; lihat "CI selektif") -> **`image`** (dilewati bila isi image tak berubah; `docker buildx build` + dorong ke `ghcr.io/<pemilik>/qc-app:<SHA commit penuh>`; build web `bun run build` + `verify-dist` terjadi di dalam Dockerfile; cache lapisan di registry GHCR) -> **`deploy`** (SSH ke VPS: `deploy.sh` menarik image, `up -d`, menunggu sehat, menguji `/api/ping` lokal LALU lewat nginx dari dalam VPS, rollback bila gagal; lalu uji asap publik dari runner yang hanya informatif) -> **`mark-deployed`** (hanya bila `deploy` sukses: mencatat commit itu sebagai ref git `refs/deployed/<environment>`; dasar pemilihan pemeriksaan run berikutnya, lihat "CI selektif").

| Kejadian | Environment | Catatan |
|---|---|---|
| PR **di-merge** ke `dev` (`pull_request_target`, closed + merged) | `staging` (`qc-dev.rhd.my.id`) | membangun commit hasil merge (`merge_commit_sha`); PR yang ditutup tanpa merge dilewati |
| PR **di-merge** ke `main` (`pull_request_target`, closed + merged) | `production` (`qc.rhd.my.id`) | sama; PR rilis `dev` -> `main` itu sendiri adalah deploy production |
| push langsung ke `main` atau `dev` | tidak ada | tidak memicu deploy (keputusan pemilik 2026-11-06, spek §11/§13.2: hanya PR yang di-merge) |
| Manual (Actions -> Deploy Server -> Run workflow) | pilihan `staging`/`production` | `production` hanya dari `main`; `staging` dari `main` atau `dev`; ref lain ditolak oleh job `meta` sebelum checkout dan sebelum rahasia dibaca |

Perubahan hanya di `docs/**` dan `**/*.md` tidak memicu deploy (tidak masuk ke image).

**Label `skip-deploy`** (dibuat 2026-11-07): PR yang diberi label ini SEBELUM di-merge tidak men-deploy (job `meta` dilewati, semua job lain ikut dilewati; run tampil "skipped"). Berguna untuk PR yang hanya mengubah hal yang tak perlu sampai ke server sekarang (mis. tes, dokumen kode, atau perubahan yang ingin digabung dengan PR berikutnya). Kodenya tidak hilang: deploy berikutnya membangun commit hasil merge terbaru sehingga ikut ter-deploy, dan karena pemeriksaan dipilih menurut perubahan SEJAK DEPLOY TERAKHIR (`refs/deployed/<env>`, bukan menurut berkas PR pemicu saja), perubahan PR yang dilewati itu ikut memilih pemeriksaan dan image deploy berikutnya (keputusan pemilik 2026-11-17). Label dibaca dari payload saat PR ditutup, jadi memasangnya setelah merge tidak berpengaruh; `workflow_dispatch` (deploy manual) selalu jalan. Label hanya dapat mengurangi deploy, tidak pernah menambahnya, jadi aman walau dipasang pihak lain.

### CI selektif, shard, dan build desktop (keputusan pemilik 2026-11-17)

Spek: `docs/superpowers/specs/2026-11-17-ci-selektif-shard-design.md`; rencana: `docs/superpowers/plans/2026-11-17-ci-selektif-shard.md`. Monorepo ini punya FE, BE, dan desktop; pipeline kini mengerjakan hanya yang berubah.

- **Deteksi perubahan** (`scripts/ci-changes.ts`, job `changes` di `ci.yml`): daftar berkas diambil lewat API (termasuk `previous_filename` untuk rename; token `pull-requests: read`, tanpa checkout kode PR) lalu dipetakan ke keluaran boolean. Sumber daftar: di `test.yml` (PR) = `pulls/{n}/files`; di `deploy-server.yml` pada PR yang di-merge = perbandingan `refs/deployed/<environment>...<commit yang dibangun>` (input `since-deploy`, lihat butir "Penunjuk deploy terakhir"); `workflow_dispatch` tanpa keduanya = semua dijalankan. Aturan: `server/**` -> tes server + image; `web/**` -> tes web + image, **tanpa** kemas desktop (keputusan pemilik 2026-11-20: UI dasar desktop diperbarui saat desktop dirilis dan UI terbarunya lewat manifest bertanda tangan); `shared/**` -> server, web, shared, desktop (di `dev` desktop mengimpor `@shared/desktop-catalog`; ditemukan tes pemindai impor di CI PR 102), kemas desktop, image; `countrylock/**` -> web, desktop, kemas desktop, image; `desktop/**` -> tes desktop + kemas desktop, **tanpa image** (PR desktop saja tidak men-deploy server), kecuali `desktop/package.json` yang memicu image (Dockerfile menyalinnya; keputusan pemilik 2026-11-17); `deploy/**` -> tes server (tes `deploy-files`/`deploy-script`); dokumentasi (`docs/**`, `**/*.md`, `.superpowers/**`, `.claude/**`) -> tak menyalakan apa pun, kecuali `docs/ci-cd.md` (dibaca tes `ci-workflows`) yang menyalakan lint + tes scripts (keputusan pemilik 2026-11-17). `.github/workflows/**` -> hanya lint + tes `scripts/` (`code`; keputusan pemilik 2026-11-20: PR #139 yang hanya menyentuh workflow dan fragmen changelog sebelumnya memicu seluruh CI dan deploy staging; tes `scripts/ci-workflows.test.ts` tetap berjalan; `.github` ada di `.dockerignore` sehingga tak masuk image). Jalur lain (`.github/actions/**` dan `.github/` lain, karena aksi lokal `mariadb`/`setup` dipakai tes server/web; `scripts/**`, yang ikut ke image lewat `COPY scripts scripts`; `package.json`, `bun.lock`, berkas atau folder baru) menyalakan SEMUA; begitu pula daftar kosong, lebih dari 2.900 berkas, API gagal, `refs/deployed/<env>` belum ada atau tak terbaca, dan `workflow_dispatch` (tanpa nomor PR dan tanpa `since-deploy`). Konservatif: lebih baik menjalankan berlebih daripada melewatkan.
- **Cache build web untuk kemas desktop** (job `desktop` di `ci.yml`; keputusan pemilik 2026-11-20): PR yang hanya mengubah `desktop/**` tak perlu membangun ulang web. `server/dist` (UI dasar yang dibawa installer) di-cache lewat `actions/cache` (dipatok SHA) dengan kunci persis `web-dist-<os>-<hash>`, hash atas `web/**`, `shared/**`, `countrylock/**`, `package.json`, `bun.lock`, `tsconfig.base.json` (tanpa `node_modules`; `scripts/` tak ikut karena `bun run build:web` = `vite build` di `web/` dan tak membacanya). Tanpa `restore-keys` agar tak pernah memakai build basi; langkah "Build web" hanya jalan bila `cache-hit != 'true'`. Dua langkah sesudahnya SELALU jalan (juga saat cache kena): "Verifikasi build web" (`scripts/verify-dist.ts`) dan "Manifest UI dasar" (`scripts/build-ui-manifest.ts`, menulis ulang `server/dist/ui-manifest.json` dengan `createdAt` baru), karena `bun run build` (akar) yang biasa menjalankannya terlewat saat cache kena dan `verify-pack` menolak UI dasar tanpa manifest (aturan "UI dasar yang lebih baru menang"). **Batas**: cache yang ditulis di PR hanya terbaca oleh PR itu sendiri dan oleh cache branch dasar/default; job `desktop` hanya jalan di PR sehingga tak ada cache di `dev`/`main`: hit baru terjadi pada push berikutnya di PR yang sama (push pertama tetap membangun web). Tidak ada workflow/pemicu pemanas cache (dijaga `scripts/ci-workflows.test.ts`); usulan bila ingin hit lintas PR: job pemanas di `deploy-server.yml`/`workflow_dispatch` pada `dev` yang menulis kunci yang sama, atau mengambil `server/dist` dari artefak job `image`.
- **Risiko aturan 2026-11-20**: mengubah `.github/workflows/ci.yml` sendiri kini hanya memicu lint + tes `scripts/` (tes struktur `ci-workflows.test.ts`), bukan menjalankan jobnya; kesalahan yang hanya muncul saat job berjalan baru ketahuan pada PR berikutnya. Merge PR yang hanya menyentuh workflow ke `dev`/`main` tidak membangun image dan tak men-deploy ulang (`image=false` -> job `image` dilewati -> job `deploy` bersyarat `needs.image.result == 'success'` ikut dilewati); `refs/deployed/<env>` tak maju.
- **Tes web 4 shard** (keputusan pemilik 2026-11-17): matrix 4 job `web` (`vitest run --shard=<i>/4`, nilai lewat env `WEB_TEST_SHARD`; vitest membagi berkas tes sendiri). Alasan: satu job memakan ~7,6 menit pada run PR 102 (2.795 tes, jsdom per berkas); lokal satu shard menjalankan ~683 tes. Tiap job menginstal dependensi sendiri, dan tes web tak butuh basis data.
- **Tes server 8 shard**: matrix 8 job `server` (`QC_TEST_SHARD=<i>/8`, `server/scripts/test.ts` + `partition.ts`); tiap job punya runner dan MariaDB sendiri, satu proses per job. Menambah proses di satu runner tidak membantu (terikat CPU 2 vCPU repo privat, dan 8 proses x 8 koneksi melebihi `max_connections` 40). Lokal tak berubah (3 proses, tunnel).
- **Gerbang `test`**: job `test` di `test.yml` (status check wajib branch protection) menunggu `ci`; `success` dan `skipped` lulus (PR hanya dokumentasi tetap hijau), `failure`/`cancelled` gagal. Gerbang sengaja di pemanggil: nama check dari workflow yang dipanggil menjadi `<job pemanggil> / <job>`.
- **Uji bangun image PR** (`image-check` di `ci.yml`, input `build-image`): paralel dengan tes (output workflow yang dipanggil baru tersedia setelah seluruh `ci.yml` selesai, jadi job di pemanggil akan serial). Hanya membaca cache registry; tak pernah mendorong image atau menulis cache.
- **Cache lapisan registry** (`deploy-server.yml` job `image`): `cache-to` = `<image>:buildcache-<environment>` (`mode=max`) untuk SEMUA event. Alasan: token `pull_request_target` ditolak menulis cache GHA, sehingga cache lama hanya ditulis dispatch dan merge PR hampir selalu membangun ulang web. **Yang dibaca ditentukan langkah `cache`** (keputusan pemilik 2026-11-17): **staging** membaca `buildcache-staging` dan `buildcache-production`, sehingga tahap `web-build` Dockerfile dipakai dari cache bila `web/`, `shared/`, `countrylock/`, `scripts/`, atau manifest tak berubah (perubahan server saja tak membangun ulang aset web); **production tanpa cache** (`no-cache: true`, `cache-from` kosong). Alasan: siapa pun yang boleh mendorong branch di repositori ini dapat menulis tag `buildcache-*` dengan lapisan berisi lain (peracunan cache), dan production tak boleh membangun dari lapisan yang tak dihasilkan dirinya. Dipilih `no-cache` penuh, bukan hanya tahap `web-build`, karena lapisan `RUN` lain (`bun install`, `apk add`) juga berakhir di image runtime; biayanya production membangun ulang seluruh image (lebih lambat). Staging tetap menanggung risiko peracunan itu (dicatat; image staging bukan production). Tag `buildcache-*` menambah paket `qc-app` di GHCR dan tak disentuh `QC_KEEP_IMAGES` (itu hanya untuk image di VPS).
- **Penunjuk deploy terakhir** (`refs/deployed/<environment>`, job `mark-deployed`; keputusan pemilik 2026-11-17): masalahnya, pemilihan pemeriksaan hanya dari berkas PR pemicu membuat perubahan terlewat bila run sebelumnya dilewati (label `skip-deploy`), dibuang antrean `concurrency`, atau gagal; image yang di-deploy lalu tak memuat perubahan itu. Solusinya mencatat commit yang BERHASIL di-deploy sebagai ref git (bukan tag atau release: tak muncul di daftar rilis dan tak bentrok dengan tag semver `server-v*` kelak), lalu run berikutnya membandingkan commit yang dibangun dengan ref itu (SATU panggilan `gh api repos/<repo>/compare/<ref>...<sha>` tanpa `--paginate`, termasuk `previous_filename`). Semua dijalankan (peringatan di log) bila: ref belum ada (deploy pertama sesudah perubahan ini) atau tak terbaca, perbandingan gagal, **status perbandingan bukan `ahead`** (tiga-titik menghitung dari merge-base, jadi bila deploy terakhir bukan leluhur commit ini, mis. staging pernah di-dispatch dari `main` lalu PR `dev` hanya-desktop di-merge, selisih sebenarnya lebih besar dari daftar itu), atau **300 berkas atau lebih** (batas API compare: daftar berkas hanya di halaman pertama dan maksimum 300 untuk seluruh perbandingan, sisanya terpotong diam-diam; hasil review independen 2026-11-17). Pengaman 2.900 berkas di `ci-changes.ts` untuk sumber berkas PR tak berlaku di sini. Job `mark-deployed` hanya jalan bila `deploy` sukses, adalah SATU-SATUNYA job berizin `contents: write`, tanpa checkout, aksi pihak ketiga, dan rahasia; ia memvalidasi `TARGET` dan `SHA` sebelum memanggil `gh api` (PATCH bila ada, POST bila belum) dan hanya menulis jalur `refs/deployed/staging|production`. Gagal menulis = peringatan, bukan kegagalan (deploy sudah sukses; akibatnya hanya run berikutnya memeriksa lebih banyak). Ref ini dapat dilihat dengan `git ls-remote origin 'refs/deployed/*'` dan dipulihkan manual dengan `git push -f origin <sha>:refs/deployed/<env>` bila perlu. Deploy manual (`workflow_dispatch`) memeriksa semuanya dan, bila sukses, ikut menggeser ref lewat job yang sama. Keamanan: namespace `refs/deployed/*` tidak dilindungi branch protection/ruleset branch dan tag, jadi siapa pun berizin tulis dapat menimpanya (`git push -f origin <sha>:refs/deployed/<env>`) untuk menyempitkan pemeriksaan pasca-merge; mereka tak dapat men-deploy kode yang melewati gerbang PR (gerbang `test` memakai berkas PR, dan image selalu dibangun dari `merge_commit_sha`), jadi risiko sisanya kecil dan diterima (aktor berizin tulis sudah lebih berkuasa).
- **Build desktop** (job `desktop` di `ci.yml`, `windows-latest`): hanya PEMERIKSAAN build dan HANYA di PR (input `desktop-check` di `ci.yml`, dinyalakan `test.yml`; `deploy-server.yml` tak menjalankannya agar kegagalan kemas desktop tak menahan deploy server) (tanpa artefak dan tanpa installer, bukan rilis; keputusan pemilik 2026-11-17: Windows x64 + Windows arm64, tanpa Linux). build web (`bun run build:web`, hanya bila cache `server/dist` meleset; lihat butir cache di atas) + `verify-dist` + manifest UI dasar (`scripts/build-ui-manifest.ts` -> `ui-manifest.json`, selalu) -> `bun run --cwd desktop pack:all` (x64 dan arm64) -> `verify-pack --arch x64` (asap `--smoke` penuh) dan `--arch arm64` (hanya pemeriksaan statis: exe, `app.asar`, `ui-baseline` beserta `ui-manifest.json` yang sah ada; keduanya menolak hasil kemas tanpa manifest karena aturan "UI dasar yang lebih baru menang" bergantung padanya). arm64 dikemas silang dari x64 dan tak dapat diasapkan karena runner Windows arm64 (`windows-11-arm`) setahu kami hanya gratis untuk repo publik; bila tersedia kelak, ganti `runs-on` untuk menjalankan asap arm64. Pada PR, `UI_PUBLIC_KEY_PEM` tak dipakai (bukan build rilis). Installer NSIS x64 dan arm64 sungguhan dibuat jalur desktop `release.yml` (bullet "Rilis aplikasi desktop" di bawah), yang memanggil `ci.yml` ini dengan `desktop-check`.
- **Gerbang fragmen changelog** (`changelog.yml`, job `fragmen`; rancangan `docs/superpowers/specs/2026-11-17-rilis-semver-design.md` bagian 5.2): PR yang mengubah `server/`, `web/`, `shared/`, atau `countrylock/` harus membawa fragmen baru di `server/changelog.d/`; yang mengubah `desktop/`, `shared/`, atau `countrylock/` di `desktop/changelog.d/` (`shared/` dan `countrylock/` mewajibkan keduanya). Satu fragmen = berkas `<yyyymmdd>-<slug>.md`, isi = satu butir per baris bergaya commit `tipe(area): ringkasan` (maks. 200 karakter; area boleh dihilangkan; `feat` = Ditambah, `fix` = Diperbaiki, `change`/`refactor`/`perf` = Diubah, `chore`/`ci`/`docs`/`test`/`build`/`style` = Internal yang hanya tampil di GitHub Release); hasil kompilasi dikelompokkan per area. Label **`tanpa-changelog`** melewatkan pemeriksaan; PR rilis dikenali dari ISI diff, bukan nama cabang: `<komponen>/package.json` DAN `<komponen>/CHANGELOG.md` sama-sama berubah (versi naik + bagian versi baru); rilis hanya membebaskan komponennya sendiri (PR `release/server-vX` membawa seluruh kode `dev` sejak rilis lalu, dan fragmennya sudah dihapus `changelog compile`, jadi tak muncul di diff), dan PR yang berisi semua-berkas-metadata dengan `CHANGELOG.md` (mis. sinkron `main` -> `dev`) lolos seluruhnya; kenaikan dependensi biasa (`package.json` + `bun.lock` tanpa `CHANGELOG.md`) BUKAN rilis. Hanya fragmen berstatus `added` di PR yang dihitung fragmen baru. Langkah pertama job memegang token baca-saja untuk mengambil daftar berkas PR lewat API; langkah yang menjalankan skrip dari checkout PR tidak diberi token. Pemicu `pull_request` hanya untuk PR yang bertujuan ke `dev` (keputusan pemilik 2026-11-19: fragmen menumpuk di `dev` sampai `release:prepare`; PR ke cabang kerja lain dan PR rilis ke `main` tidak diperiksa) dan termasuk `labeled`/`unlabeled`, dipisah dari `test.yml` agar label tak mengulang seluruh CI. Ini penanda di PR, bukan penghalang merge yang dipaksakan (branch protection tak tersedia di paket repo ini). Perkakas: `bun run changelog validate|compile|extract <server|desktop>` (`scripts/changelog.ts`); `CHANGELOG.md` server ikut ke image untuk halaman "Pembaruan" di web.
- **Siapkan rilis** (`bun run release:prepare <server|desktop> <patch|minor|major|X.Y.Z> [--dry-run]`, `scripts/release-prepare.ts`; dijalankan pemilik secara lokal dengan kredensial `git` dan `gh` miliknya): memeriksa pohon kerja bersih, `origin/main` adalah leluhur `origin/dev`, ada minimal satu fragmen di `origin/dev`, dan (server) `refs/deployed/staging` adalah leluhur `origin/dev` dengan selisih `staging..dev` hanya berkas metadata rilis atau berkas di luar image server (dokumentasi, kode desktop; rilis hanya membawa kode image yang sudah berjalan di staging; selisih fragmen/versi tidak dihitung kode); hanya `--dry-run` yang diterima sebagai opsi (flag lain ditolak); menghitung versi (rilis pertama server memakai versi eksplisit `1.0.0` karena `server/package.json` dimulai di `0.0.0`); memotong `release/<komponen>-vX.Y.Z` dari `origin/dev`, menaikkan `version`, `bun install --lockfile-only`, menyusun `CHANGELOG.md` dari fragmen (tanggal WIB), commit hanya berisi berkas metadata, push, lalu membuka PR ke `main` dengan badan = bagian changelog. Kegagalan sebelum push (termasuk pohon kerja tidak bersih setelah commit) membatalkan cabang lokal dan kembali ke cabang asal; setelah push sukses skrip kembali ke cabang asal sebelum membuka PR (PR gagal dibuka = cabang di origin dibiarkan, buat PR manual); `--dry-run` hanya memeriksa dan mencetak perintah. Skrip menolak berjalan bila variabel repositori `RELEASE_FLOW` bukan `tag` (lihat bagian berikut). **Potret kontrak API dan pagar 24 jam** (fase 3 versi API, keputusan pemilik 2026-11-20; hanya rilis yang memuat server: `server` dan `both`): pada prasyarat baca-saja skrip membaca potret pada tag server terbaru (`git show <tag>:shared/api-contract.snapshot.json`) dan umur tag (`git log -1 --format=%cI <tag>` terhadap waktu sekarang); tak terbaca = berhenti sebelum membuat cabang. Pada tahap perubahan, SESUDAH memotong cabang dari `origin/dev` dan sebelum `package.json` diubah, skrip menulis potret tag ke berkas sementara di luar pohon kerja dan menjalankan `bun run scripts/api-removal-check.ts <berkas> <umur-ms|none>` (di pohon cabang rilis, jadi yang dibandingkan adalah kontrak dan `RETIRED_ROUTES` milik `origin/dev`): rute dihapus tanpa dicatat di `RETIRED_ROUTES`, tanpa status deprecated di potret lama, atau dihapus padahal rilis yang menandainya berumur kurang dari 24 jam (`REMOVAL_MIN_AGE_MS`) = rilis dibatalkan (cabang lokal dibuang, tanpa push); lolos = `bun run api:snapshot` membuat ulang `shared/api-contract.snapshot.json`, yang ikut `git add` dan commit rilis (potret ini kini metadata rilis SERVER: `isMetadataOf('server')` di `scripts/changelog-check.ts`, sehingga `isReleaseChange`, `unverifiedFiles`, dan guard CI menerimanya; rilis desktop saja tak menyentuhnya). `--dry-run` tetap membaca potret dan umur tetapi tidak menjalankan pagar (butuh pohon cabang `origin/dev`); langkahnya dicetak. Rilis pertama (belum ada tag server) memakai potret kosong dan umur `none`. Mode `langsung` tidak melewati `release:prepare`, jadi jeda 24 jam di sana dijaga manual oleh pemilik.

Rekomendasi: (a). Image tidak memuat rahasia (tes `server/src/deploy-files.test.ts`).

### Pembersihan image lama (`QC_KEEP_IMAGES`)

VPS dipakai bersama aplikasi lain, jadi tiap deploy yang SUKSES PENUH (tag baru sehat dan `/api/ping` lolos) diakhiri pembersihan image lama oleh `deploy.sh` (`cleanup_images`). Tidak pernah berjalan pada deploy gagal atau pengembalian (image tag sebelumnya adalah target pengembalian). Aturan:

- Hanya repositori image stack ini (`QC_IMAGE` di `.env`, bawaan yang tertulis di `compose.yml`) dan hanya tag `<sha-40-heksa>` atau `local-<sha>`; tag lain dibiarkan. Daftar dibaca dari `docker image ls <repo>` (terurut dari yang terbaru dibuat), dihapus satu per satu dengan `docker image rm <repo>:<tag>` (tanpa `-f`; image yang masih dipakai gagal dengan aman dan diabaikan).
- Dipertahankan: `QC_KEEP_IMAGES` tag terbaru (variabel opsional di `.env`, bawaan 3; harus `^[1-9][0-9]?$`, nilai lain = 3), tag baru, tag sebelumnya, tag yang dipakai kontainer ini, dan tag `QC_IMAGE_TAG` di `.env` lingkungan LAIN (`$ROOT/*/.env`; staging dan production memakai satu repositori GHCR, jadi deploy satu lingkungan tidak menghapus image yang lain).
- TIDAK pernah: `docker system prune`, `docker image prune`, `docker volume prune`, atau menyentuh image, volume, dan kontainer di luar daftar di atas (termasuk image dangling).
- Kegagalan pembersihan hanya dicatat; kode keluar deploy tetap 0. Keluaran docker masuk `.deploy.log` di VPS; log skrip hanya ringkasan (`dihapus=N gagal/dilewati=M`). `--dry-run` mencetak rencananya.
- `QC_KEEP_IMAGES` hanya dibaca `deploy.sh` dari `.env` (bukan `config.ts`), jadi tidak ada di `compose.yml`. Berkas `deploy.sh` baru wajib disalin manual ke VPS (bagian di atas).

### Migrasi basis data dan pengembalian

Migrasi diterapkan otomatis saat server start (gerbang `prepareDatabase`, sebelum `Bun.serve`). Pengembalian otomatis (`deploy.sh`) hanya mengganti image ke tag sebelumnya; **pengembalian TIDAK membatalkan migrasi**. Karena itu migrasi wajib kompatibel mundur dengan image sebelumnya: pola expand -> kontrak (tambah kolom/tabel dulu; hapus atau ganti nama kolom hanya di rilis berikutnya, setelah image yang tak lagi memakainya stabil). Migrasi destruktif yang membuat image lama rusak menjadikan pengembalian "sehat" di `/api/ping` tetapi galat di rute nyata, atau berakhir kode 4.

**Rencana terjadwal: migrasi diringkas saat pindah ke server kantor (keputusan pemilik 2026-11-23, spek migrasi VPS §19 butir 25).** Sampai saat itu aturan di atas tidak berubah: skema berubah lewat file migrasi baru, tidak menyunting yang sudah diterapkan, dan tidak ada DDL langsung ke database tanpa file migrasi. Atas permintaan pemilik pada tahap perpindahan, seluruh rantai diringkas menjadi migrasi dasar yang hanya berisi `CREATE`, tetap per tabel atau fitur (bukan satu file tunggal); syaratnya (tes perbandingan `SHOW CREATE TABLE`, migrasi dasar tidak boleh sampai ke VPS yang `schema_migrations`-nya berisi nama lama, tag sebelum ringkasan, cara memuat data) ada di `docs/deploy-vps.md` bagian 14.

**Pengecualian tercatat: soft delete (keputusan pemilik 11, 2026-11-20).** Migrasi `0027_soft_delete.sql` bersifat expand (kolom `deleted_at`/`deleted_by` dan indeks `_live` di samping indeks lama), jadi sendirian aman di-rollback. Migrasi contract yang membuang indeks unik lama (`0030_soft_delete_contract.sql`, berpenanda `-- qc:contract`; `DROP INDEX IF EXISTS` untuk 15 indeks, `users_email` dipertahankan) ikut PR yang SAMA dengan redesain (spek soft delete §5 butir 7 dan keputusan 11), sehingga setelah PR itu dirilis, rollback image ke versi sebelum soft delete TIDAK aman: image lama tak mengenal `deleted_at` (record terhapus muncul kembali, dan dua record berkunci sama dapat terlihat). Bila deploy gagal, perbaiki ke depan, jangan rollback image (seperti pengecualian 0002/0003/0010/0017). Pagar downgrade skema tak pernah melewati migrasi berpenanda contract. Penjaga keunikan serial (`serials_serial_live`) dipasang oleh `ensureSerialUniqueIndex` saat start (bukan migrasi); indeks `serials_serial` dan `serials_bu_serial` lama dibuang oleh fungsi itu HANYA setelah indeks `_live` ada, sehingga data lama dengan serial ganda lintas BU tetap dijaga `serials_bu_serial` sampai skrip penyatuan dijalankan. Serial ganda yang sama-sama TERHAPUS pada `deleted_at` yang sama juga menahan indeks `serials_serial_live` (peringatan "belum dibuat" muncul tiap start) dan TIDAK ditangani skrip penyatuan (ia mengabaikan serial terhapus): bedakan `deleted_at` salah satunya lewat SQL manual (mis. geser 1 ms) lalu mulai ulang server. Keputusan pemilik 2026-11-22 ("biarkan"): kasus ini DIBIARKAN dan diselesaikan manual oleh operator bila terjadi; skrip penyatuan dan indeks tidak diubah (spek `2026-11-22-revisi-tampilan-lanjutan-design.md` §1 butir 2).

**Pengembalian OTOMATIS `deploy.sh` tetap dapat terjadi di atas skema contract (soft delete).** Pagar skema (`schema_guard`) hanya dipanggil pada deploy/downgrade manual, TIDAK pada pengembalian otomatis (`rollback()` di `deploy/deploy.sh`). Bila image baru menerapkan 0027-0030 saat start lalu gagal uji sehat, `deploy.sh` mengembalikan ke image sebelumnya (pra-soft delete) di atas skema yang sudah bercontract. Akibatnya: image lama memetakan galat duplikat menurut nama indeks persis (`items_key`, `customers_key`, `handovers_number`, ...), sehingga galat `*_live` tidak terpetakan (konflik merk/tipe, nama, kode menjadi 500 alih-alih `CONFLICT` berpesan) dan simpan task Serah Terima serentak tidak diulang (`RETRYABLE_UNIQUE_KEYS` lama tak cocok dengan `handovers_number_live`). Integritas data AMAN: image lama menulis `deleted_at = ''`, jadi indeks `_live` tetap menolak kunci hidup ganda, dan belum ada record terhapus bila image baru tak pernah sehat. Arahan: perbaiki ke depan dan deploy ulang image perbaikan (jangan menunggu pengembalian); membuat `deploy.sh` menolak pengembalian otomatis bila image baru membawa migrasi `-- qc:contract` yang tak ada di `PREV_TAG` TIDAK dilakukan. Keputusan pemilik 2026-11-22 ("biarkan"): `deploy/deploy.sh` tidak diubah; risiko ini cukup didokumentasikan di sini (spek `2026-11-22-revisi-tampilan-lanjutan-design.md` §1 butir 1).

Penyatuan tidak dapat dibatalkan otomatis (pemulihan lewat cadangan harian). **Kapan:** jalankan secepatnya setelah deploy `0026` bila start server melaporkan peringatan "Indeks unik serials_serial belum dibuat: ada N Serial Number ganda" (`ensureSerialUniqueIndex` = `duplicates`). Skrip boleh diulang (kelompok yang sudah disatukan tidak ditemukan lagi). Selama indeks belum ada, keunikan hanya dijaga baca-lalu-tulis di aplikasi: dua pencatat serentak masih dapat membuat serial ganda baru, dan aplikasi memilih catatan dengan aturan yang sama dengan pemenang penyatuan (laporan aktif, Rusak, terbaru). **Jalankan saat sepi** (aplikasi dihentikan atau jendela perawatan): penulis aplikasi yang berjalan serentak pada catatan yang kalah dapat menulis kejadian atau potongan stok yatim (menunjuk catatan yang sudah dihapus), dan job `serial_alert` yang tertunda untuk serial yang kalah kehilangan kejadiannya. **Tempat menjalankan:** `server/scripts` tidak ikut image Docker (`.dockerignore`), jadi skrip dijalankan dari checkout repo di mesin yang punya akses ke DB target (mis. lewat terowongan SSH), BUKAN di dalam kontainer. **Pengembalian image:** skema aman bagi image sebelumnya (kolom/tabel baru diabaikan). Efek yang perlu diketahui: (1) image lama menulis serial tanpa baris penghubung; backfill saat start berikutnya dan bacaan dua jalan memulihkannya, jadi serial tidak menjadi tak terlihat setelah maju lagi; (2) selama indeks `serials_serial` sudah ada, image lama tidak dapat mencatat serial yang sama di BU lain (bentrok pada indeks yang tak dikenalnya, hasilnya galat penyimpanan biasa; belum diuji); (3) image lama hanya membaca `serials.bu_id`, jadi serial yang sudah berpindah BU hanya terlihat oleh BU saat ini; (4) image lama menulis nomor laporan format lama (`LP-YYYYMMDD-NNN`) dengan penghitung terpisah dari yang baru, tanpa tabrakan; (5) bila `serials_serial` belum ada (karena ada serial ganda), image lama dapat membuat serial ganda lintas BU lagi; jalankan skrip penyatuan setelah maju kembali. Tidak ada tindakan manual selain perbaikan ke depan.

**ID baris ULID (keputusan pemilik 2026-11-22; spek `docs/superpowers/specs/2026-11-22-id-ulid-design.md`).** Image yang memuat perubahan ini membuat ID baris BARU berbentuk ULID huruf kecil (`newId()`); TIDAK ada migrasi skema, kolom, atau indeks baru, jadi tidak ada yang perlu dikhawatirkan pada deploy maupun pengembalian image: kolom `id` semua `VARCHAR(100)` dan tak ada validator ID baris yang memeriksa bentuk UUID (hanya `clientId` yang divalidasi UUID dan memang tak diubah). Setelah deploy, ID lama (UUID) dan baru (ULID) hidup berdampingan. Penulisan ulang data lama dilakukan skrip operator LOKAL milik pemilik yang sengaja tidak masuk repo (spek bagian 1 butir 7): ia membuat tabel petanya sendiri, dan tabel itu dibuang manual (`DROP TABLE id_ulid_map`) setelah masa pantau. Syarat operasional yang tetap berlaku bagi siapa pun yang menjalankannya: `qc-app` BERHENTI selama skrip berjalan, cadangan segar dibuat setelah aplikasi berhenti, produksi sudah menerapkan `0027`-`0030`, dan JANGAN men-deploy atau me-merge PR yang memicu deploy (`dev`/`main`) selama jendela (`deploy.sh` menjalankan `compose up -d` dan menyalakan `qc-app` di tengah penulisan ulang); tahan juga `deploy-tag.yml` sampai verifikasi lolos. Efek bagi pengguna (antrean offline, draf, foto bukti di draf, `.qcsn`, tautan lama): spek bagian 5. Tabel `id_ulid_map` ikut dump cadangan dan aman bagi `restore.ts` (ia membandingkan dengan skema sumber, tidak memakai daftar tabel dari migrasi). **Lapisan terjemahan ID lama sementara** (`server/src/core/legacy-ids.ts`, dipasang di kernel REST `http/rest.ts`; keputusan pemilik 2026-11-23, spek bagian 1 butir 10 dan 4a): ia membaca `id_ulid_map` dan tidak bekerja apa-apa bila tabel itu tidak ada; jangan `DROP TABLE id_ulid_map` atau menjalankan `--revert` skrip operator tanpa tahu lapisan ini membacanya. Urutan pencabutan (setelah masa pantau satu minggu): (1) sapu akhir skrip operator, (2) `DROP TABLE id_ulid_map`, (3) PR yang menghapus `legacy-ids.ts` beserta pemasangannya, supaya kode sementara tidak tertinggal selamanya. Mengosongkan antrean offline dan draf sebelum jendela migrasi kini disarankan, bukan wajib (spek butir 10).

### Kesehatan database saat deploy

Butir spek "uji asap ... (dan kesehatan database)" dipenuhi oleh gerbang migrasi saat start: kontainer yang `healthy` berarti basis data terjangkau saat start dan migrasi sudah diterapkan. `/api/ping` sengaja tidak memeriksa basis data (endpoint publik tanpa batas); ia tidak mendeteksi basis data yang hilang SETELAH start.

### Urutan uji pertama (setelah pemilik mengatur di atas)

1. Pastikan VPS siap (`docs/deploy-vps.md`, termasuk kunci SSH deploy langkah 9). Khusus staging yang kini memakai image lokal: **hapus atau komentari `QC_IMAGE`** di `.env` staging (`deploy.sh` menolak dengan kode 2 bila `QC_IMAGE` bukan `ghcr.io/...`; tanpanya compose memakai `ghcr.io/<pemilik>/qc-app`), dan jalankan `docker login ghcr.io` (lihat butir 5 di atas) agar `compose pull` berhasil. Catatan: `QC_IMAGE_TAG=local-<sha>` lama menunjuk `ghcr.io/...:local-<sha>` yang tak ada, jadi **deploy GHCR pertama tidak punya target pengembalian**: bila `pull` gagal, `.env` dipulihkan dan kontainer lokal yang berjalan tidak tersentuh (kode 1); bila gagal sesudah `up -d` (tak sehat, ping gagal), pengembalian ke tag `local-<sha>` tak mungkin dan skrip berakhir kode 4: pulihkan manual (kembalikan `QC_IMAGE=qc-app` dan tag lokal, `docker compose up -d`).
2. Setelah cutover: merge PR ke `dev` (atau Run workflow dari `dev`/`main` dengan target `staging`). Perhatikan tab Actions: `meta` -> `ci` -> `image` -> `deploy`.
3. Bila `image` gagal di `buildx`, perbaiki Dockerfile (build BuildKit di Actions sudah berjalan sejak cutover 2026-11-07; periksa log job `image`).
4. Bila `deploy` gagal "Secret environment ... belum diisi" atau "Host key verification failed", periksa daftar di atas. Kode keluar skrip VPS: 0 sukses, 1 gagal dan dikembalikan ke tag sebelumnya, 4 gagal dan pengembalian juga gagal (periksa VPS manual), 2 ditolak (input, `QC_IMAGE` non-GHCR, kredensial DB di `.env` tak cocok dengan database yang berjalan = preflight) atau `.env`/`compose.yml` tidak valid (`compose config` gagal; tidak ada yang diubah), 3 deploy lain sedang berjalan, 5 versi baru sehat dan aktif tetapi nginx tidak terjangkau (tidak dikembalikan; periksa nginx), 6 downgrade skema ditolak pagar (tidak ada yang diubah, `.env` dipulihkan persis; lihat bagian "Deploy versi tertentu lewat tag dan pagar downgrade skema" di atas). Keluaran `docker compose` TIDAK muncul di log Actions (dapat memuat potongan rahasia dari `.env`): lihat `<INSTALL_DIR>/<env>/.deploy.log` di server (VPS pribadi `/root/apps/qc-app/<env>/.deploy.log`) (izin 600, ditimpa tiap deploy).
5. Uji pemulihan sekali di staging **setelah deploy GHCR kedua sukses** (baru saat itu ada tag GHCR sebelumnya yang dapat dikembalikan): dorong komit yang memecahkan `/api/ping` dan pastikan job gagal dan VPS kembali ke tag lama.

### Keamanan workflow (ditegakkan `scripts/ci-workflows.test.ts`)

- `pull_request_target` (menerima rahasia walau PR dari fork) hanya `types: [closed]` untuk `dev`/`main`, dan hanya setelah PR **di-merge**: job `meta` punya `if` merged dan skripnya menolak selain `merged == true`, menolak bila `REF` bukan `refs/heads/main` (run selalu dari branch default), dan memetakan `PR_BASE_REF` `main` -> production, `dev` -> staging (branch lain ditolak). Yang dibangun dan di-checkout HANYA commit dari output `sha` job `meta` (= `merge_commit_sha`, kode yang sudah masuk ke branch tujuan; divalidasi 40 heksa); tak ada `pull_request.head`, `head_ref`, atau `refs/pull/` di mana pun. Tanpa `pull_request` biasa. PR fork yang belum di-merge tidak pernah mendapat rahasia maupun menjalankan kodenya. Jangan menambah langkah yang meng-checkout head PR. Push langsung ke `main`/`dev` tidak memicu deploy, dan tidak ada pemicu `push` sama sekali.
- PR yang ditutup tanpa merge dilewati dan memakai grup `concurrency` sendiri (tidak menggantikan run deploy yang menunggu).
- Semua aksi pihak ketiga pada `deploy-server.yml`, `test.yml`, `ci.yml`, dan aksi lokal (`mariadb`, `setup`) dipatok ke SHA commit (tag mayor di komentar; diambil 2026-11-06, `actions/cache` v4.2.4 diambil 2026-11-17). Perbarui dengan sengaja, bukan otomatis.
- `permissions` minimal: `contents: read` di tingkat atas; hanya job `image` yang `packages: write`; hanya job `mark-deployed` yang `contents: write` (menulis `refs/deployed/*`); job `deploy` `permissions: {}` dan tanpa checkout. `ci.yml` tanpa rahasia (tak ada `secrets.*`, tak ada kunci tanda tangan UI); hanya job `changes` yang `pull-requests: read` (membaca daftar berkas PR), `image-check` `packages: read` (cache), dan pemanggil `ci` wajib memberi izin yang sama walau `build-image` false.
- Tidak ada `${{ }}` di dalam skrip `run`: nilai lewat `env`, sehingga tak ada injeksi ekspresi.
- Antrean serial per environment (`concurrency` `deploy-server-<env>`, tanpa membatalkan yang berjalan; GitHub hanya menyimpan satu run menunggu, yang lebih lama dibatalkan). Pengaman kedua: `deploy.sh` memakai kunci per lingkungan (kode 3).
- Kunci host dipatok; kunci privat ditulis ke runner dengan izin 600 dan dihapus di langkah `always()`.
- Tag yang boleh diminta ke VPS hanya SHA commit 40 heksa huruf kecil (`deploy.sh` menolak `latest` dan sejenisnya); keluaran `docker compose` tak diteruskan ke log Actions (lihat di atas); `.env`/`compose.yml` rusak berhenti di `compose config` tanpa mengubah apa pun.
- Preflight kredensial DB (keputusan pemilik 2026-11-07, spek §19 butir 13): setelah `compose config` lulus dan SEBELUM `.env`/pull/up disentuh, bila kontainer DB lingkungan itu berjalan `deploy.sh` menjalankan `mariadb ... SELECT 1` di dalamnya dengan `QC_DB_USER`/`QC_DB_PASSWORD`/`QC_DB_NAME` dari `.env` (kata sandi lewat env `MYSQL_PWD`, bukan argumen; keluaran ke `.deploy.log`). Gagal = kode keluar 2 ("kredensial DB di .env tidak cocok dengan database yang berjalan"), tidak ada yang diubah dan tidak ada rollback. Alasan: `.env` yang berubah tak sengaja atau rotasi dengan urutan terbalik membuat aplikasi baru gagal login dan rollback (hanya mengganti tag) tak menolong. Deploy pertama (DB belum berjalan) dilewati. Prosedur rotasi: `docs/deploy-vps.md` 12b.
- Uji asap (keputusan pemilik 2026-11-07, spek §19 butir 12): yang MENENTUKAN adalah `deploy.sh` di dalam VPS. Setelah kontainer sehat dan `/api/ping` lokal lulus, `deploy.sh` menguji nginx: `curl -k --resolve <host>:443:127.0.0.1 https://<host>/api/ping` dengan `<host>` dari `APP_ORIGIN` di `.env` (dilewati bila `APP_ORIGIN` bukan `https://<host>` polos, mis. dev lokal). Dua jenis kegagalan dibedakan setelah 5 percobaan: nginx MENJAWAB tetapi bukan 2xx (mis. 502/503/404; curl exit 22; dapat terkait versi) = rollback otomatis ke tag sebelumnya (kode keluar 1; 4 bila rollback gagal); nginx TIDAK TERJANGKAU (ditolak, timeout, putus sebelum respons HTTP; mis. nginx mati) = masalah infrastruktur, bukan versi: TIDAK dikembalikan, versi baru tetap aktif, pembersihan image tidak dijalankan, kode keluar 5 dan job CI merah dengan pesan jelas (periksa `systemctl status nginx`). Rollback sendiri hanya mensyaratkan sehat + ping lokal, bukan nginx. `-k` hanya untuk uji ini: sertifikat origin Cloudflare bukan CA publik; yang diuji "nginx menjawab", verifikasi sertifikat dilakukan Cloudflare (SSL Full strict). Langkah "Uji asap publik" dari runner GitHub hanya INFORMATIF (`continue-on-error`, `::warning::` bila gagal): Cloudflare memblokir IP datacenter runner (403) dan origin hanya menerima IP Cloudflare, jadi kegagalannya tidak mencerminkan kesehatan aplikasi dan tidak menggagalkan job.
- **Tag SHA image dibagi staging dan production (audit 2026-11-23, lead S2).** `ghcr.io/<pemilik>/qc-app:<sha>` dipakai kedua target, jadi build staging (ber-cache) berpotensi menimpa artefak production (tanpa cache) di bawah tag yang sama dan lolos `deploy-tag.yml`. Pagar: (1) `server-image.yml` memberi label OCI `qc.build-target=<target>` pada image; (2) langkah "Pagar tag SHA" menolak build STAGING yang akan menimpa tag SHA yang sudah ada kecuali tag itu berlabel `staging` (image lama tanpa label = tak terbukti staging, ditolak: gagal tertutup; tag belum ada = aman; galat registri selain "tidak ada" menggagalkan langkah); build production boleh menimpa (membangun ulang tanpa cache); (3) `deploy-tag.yml` `verify` membaca label itu (fakta `image_target`) dan `scripts/deploy-tag-check.ts` mensyaratkan `production` (image tanpa label atau berlabel `staging` ditolak, walau tag Release dan SHA sah). Batas yang diketahui: tag tetap dapat berpindah (yang dicegah hanya penimpaan oleh staging); pengikatan ke DIGEST tidak dikerjakan karena `deploy.sh` menarik berdasarkan tag dan perubahan itu butuh salinan manual `deploy.sh` ke VPS serta akses GHCR di job deploy; job `image` mengeluarkan output `digest` sebagai fondasi. Image production yang dibangun SEBELUM perubahan ini tak berlabel, jadi `deploy-tag.yml` menolaknya sampai production dibangun ulang (merge/rilis berikutnya) atau pemilik membangun ulang tag itu; langkah `jq`/`imagetools` untuk label belum teruji di GitHub (tes lokal `scripts/deploy-tag-facts.test.ts` butuh `jq`).
- **Guard rilis memverifikasi isi manifest, bukan hanya jalurnya (audit 2026-11-23, lead S3).** `<komponen>/package.json` dan `bun.lock` diklasifikasikan metadata rilis menurut jalur, padahal dependensi di dalamnya masuk image lewat `Dockerfile`. `scripts/release-guard.ts` kini membebaskannya hanya bila isinya terbukti hanya berubah versi: `package.json` yang sama persis kecuali `version`, dan `bun.lock` yang sama persis kecuali baris `version` entri workspace; format tak dikenali, berkas hilang di satu sisi, atau tanpa isi = tak terverifikasi (ditolak, gagal tertutup). `release.yml` job `guard` mengambil isi kedua sisi (staging dan commit rilis) lewat API ke `MANIFESTS_DIR` (404 = berkas tak ada di sisi itu; galat API lain menggagalkan), dan `release:prepare` memakai definisi yang sama (`unverifiedFiles`, isi lewat `git show`). Kenaikan dependensi yang belum jalan di staging kini menghentikan rilis.

### Manifest UI bertanda tangan (pembaruan UI aplikasi desktop; rencana `2026-11-12-qc-desktop-penuh-login-bearer-ui-hibrid`, Task H6)

- `bun run build` (akar) menjalankan `scripts/build-ui-manifest.ts` SESUDAH `verify-dist`: menulis `server/dist/ui-manifest.json` (`uiVersion`, `minBridge`, daftar semua berkas build dengan `sha256` dan `size`, urut abjad, `createdAt`). Berkas manifest sendiri dan `ui-manifest.sig` tidak masuk daftar; symlink di `server/dist` ditolak. Tanda tangan lama dibuang tiap manifest dibuat ulang. `minBridge` = `UI_MIN_BRIDGE_VERSION` (`countrylock/src/ui-manifest.ts`), dinaikkan hanya bila UI memakai fungsi jembatan baru.
- Tanda tangan (Ed25519 atas BYTE persis `ui-manifest.json`, disimpan base64url di `ui-manifest.sig`) dibuat `scripts/sign-ui-manifest.ts --key <berkas PEM>` (atau env `UI_SIGNING_KEY_FILE`; isi kunci tidak pernah dicetak). Di `Dockerfile` langkah ini hanya berjalan bila secret BuildKit `ui_signing_key` diberikan (`RUN --mount=type=secret,id=ui_signing_key,required=false`); tanpa secret langkah dilewati dengan pesan di log build dan `GET /api/desktop/ui-manifest` menjawab 404 (desktop tetap memakai UI dasar yang dibundel). Bila `UI_PUBLIC_KEY_PEM` (build-arg) diberikan, kecocokan privat↔publik diperiksa langsung sebelum `.sig` ditulis; `--require-public-key` (dipakai Dockerfile) menjadikannya wajib bila menandatangani.
- `GET /api/desktop/ui-file/<jalur>` publik: menyajikan HANYA berkas yang tercantum di manifest bertanda tangan, sebagai `application/octet-stream` + `Cache-Control: no-cache, no-transform` (desktop mengunduh bundel dari sini). Alasannya: Cloudflare di depan staging/production menyisipkan skrip deteksi bot ke respons `text/html` (`index.html` menjadi 6677 byte, bukan 5563) sehingga unduhan lewat jalur statis selalu gagal verifikasi ukuran/sha256; tipe non-HTML tak disentuh.
- `GET /api/desktop/ui-manifest` publik (tanpa sesi), `Cache-Control: no-cache`, `ETag` dari manifest + tanda tangan (304 pada `If-None-Match`), isi `{ manifest, signature }`. Server hanya MENYAJIKAN; ia tidak memegang kunci apa pun dan tidak memverifikasi tanda tangan (desktop memverifikasi `JSON.stringify(manifest)` dengan kunci publik yang tertanam di aplikasi).
- **Langkah pemilik** (workflow sudah dipasang 2026-11-16; yang tersisa hanya membuat dan mengisi kunci; rinci di `docs/desktop-ui-signing.md`). Tanpa langkah ini build tetap hijau, hanya tanpa tanda tangan (peringatan di log):
  1. Bangkitkan pasangan kunci SEKALI di mesin pribadi: `bun run scripts/gen-ui-signing-key.ts C:\jalur\pribadi\qc.ui-signing-key.pem` (kunci privat ditulis ke berkas itu, tidak dicetak, tidak menimpa; kunci publik ditulis ke `qc.ui-signing-key.pub.pem` dan dicetak, termasuk nilai SATU baris untuk Variable). Nama berakhiran `.ui-signing-key.pem` ditangkap `.gitignore`; jangan dikomit. Simpan cadangan kunci privat di tempat aman (hilang = rilis aplikasi desktop baru dengan kunci publik baru).
  2. Simpan ISI berkas privat sebagai **secret environment** `UI_SIGNING_KEY` pada environment `staging` DAN `production` (Settings > Environments; job `image` memakai environment yang sama dengan target deploy, jadi nilainya harus ada di keduanya; penempatan pemilik 2026-11-16, menggantikan environment terpisah `ui-signing` yang semula dirancang). BUKAN secret repositori biasa: itu terbaca oleh workflow mana pun, termasuk yang diubah di branch PR; aturan branch environment itulah yang membatasi pembacanya.
  3. Simpan kunci publik sebagai **Variable** (bukan secret) `UI_PUBLIC_KEY_PEM` pada kedua environment itu (atau di repositori). Bentuk apa pun yang lazim diterima (PEM berbaris banyak berakhir baris Unix/Windows, PEM satu baris, atau isi base64 saja): langkah persiapan menormalkannya menjadi SATU baris isi base64 karena `build-args` berformat satu entri per baris; nilai yang bukan kunci publik terbaca = GAGAL tanpa mencetak isinya. Nilai yang sama dipakai build desktop (`UI_PUBLIC_KEY_PEM` di env shell build; `docs/desktop-ui-signing.md`).
  4. Job `image` (di workflow bersama `server-image.yml`, dipanggil `deploy-server.yml` dan `release.yml`): `environment: ${{ inputs.target }}`; langkah "Siapkan kunci tanda tangan UI" menulis `UI_SIGNING_KEY` ke berkas sementara di `runner.temp` (izin 0600) dan meneruskannya lewat `secret-files` (bukan `secrets:`, karena nilainya berbaris banyak), kunci publik yang sudah dinormalkan (output `public_key`) lewat `build-args`, lalu langkah terakhir menghapus berkas itu (`if: always()`). Aturannya (ditegakkan `scripts/ci-workflows.test.ts`, termasuk dengan menjalankan skrip langkah itu): secret dan variabel sama-sama kosong = lolos dengan `::warning::` tanpa tanda tangan (perilaku lama, rollout aman); hanya salah satu terisi atau Variable bukan kunci publik yang terbaca = GAGAL. Di Dockerfile `sign-ui-manifest.ts --require-public-key` memeriksa kunci privat berpasangan dengan `UI_PUBLIC_KEY_PEM` (uji tanda tangan sungguhan + sidik) SEBELUM `ui-manifest.sig` ditulis; tidak berpasangan = build gagal. Sidik SHA-256 kunci publik dicetak di log build.
  5. **LARANGAN: jangan memberi `UI_SIGNING_KEY` ke `test.yml` atau workflow lain yang berjalan pada `pull_request`** (tes menegakkannya: hanya `server-image.yml` yang boleh menyebutnya, dan hanya job `image`; `deploy-server.yml` dan `release.yml` hanya memanggilnya lewat `secrets: inherit`). Job itu membangun Dockerfile dan `scripts/` dari HEAD PR yang belum ditinjau: siapa pun yang dapat mendorong branch dapat mengubah `scripts/sign-ui-manifest.ts` atau langkah Dockerfile untuk membocorkan kunci atau menandatangani bundel UI pilihannya, sehingga pertahanan spek §3.4 (server atau pipeline yang disusupi tak boleh menyajikan UI yang memegang jembatan SSH) gugur. Kunci HANYA untuk job `image` di `server-image.yml`, yang membangun kode hasil merge (`merge_commit_sha`) atau commit rilis. Image hasil `test.yml` memang tak ditandatangani (itu benar dan diinginkan).
  6. Build lokal untuk uji: `docker build --secret id=ui_signing_key,src=<berkas PEM> --build-arg UI_PUBLIC_KEY_PEM=<satu baris> -t qc-app .`. Rotasi kunci membutuhkan rilis aplikasi desktop baru (spek §3.4).
- Alasan secret BuildKit, bukan `ARG`/`ENV`, untuk kunci PRIVAT: nilainya tidak masuk lapisan image atau riwayat build; `.dockerignore` juga menyingkirkan `**/*.pem` dari konteks build. Kunci PUBLIK memang lewat `ARG` karena bukan rahasia.
- **Cache BuildKit**: kunci cache `RUN --mount=type=secret` tidak memuat ISI secret, tetapi nilai `ARG` ikut kunci cache. Karena `UI_PUBLIC_KEY_PEM` (ARG) berubah saat kunci pertama kali dipasang dan saat diputar (kunci publik baru), langkah tanda tangan otomatis dibangun ulang pada kedua peristiwa itu, jadi `.sig` lama tidak diambil dari cache. Tetap pastikan setelah memasang atau memutar kunci bahwa `GET /api/desktop/ui-manifest` menjawab 200 dengan `signature` baru.
- Dockerfile: tahap `manifests` menyalin `package.json` SEMUA workspace akar (`countrylock` dan `desktop` selain shared/web/server) agar `bun install --frozen-lockfile` konsisten dengan `bun.lock`; instalasi web-build memakai `--filter '!@qc/desktop'` sehingga Electron dan dependensi desktop tidak terpasang di image (disimulasikan dengan Bun 1.4.2 di folder sementara berisi hanya `package.json`: tanpa filter `electron`/`ssh2` terpasang, dengan filter tidak; tahap `prod-deps` (`--production --filter @qc/server`) tak berubah). Build Docker sungguhan tak dapat dijalankan di mesin pengembang; yang terbukti di CI hanya setelah job `image` merah/hijau.

### Yang belum terbukti

Pipeline `deploy-server.yml`, `server-image.yml`, `server-deploy.yml`, dan `.github/actions/mariadb` sudah berjalan nyata di GitHub sejak cutover 2026-11-07 (production live), jadi MariaDB + `qc.cnf` di runner, build BuildKit, dorong ke GHCR, SSH dengan kunci host dipatok, `concurrency`/`environment`, dan pemicu `pull_request_target` tidak lagi berstatus belum terbukti.

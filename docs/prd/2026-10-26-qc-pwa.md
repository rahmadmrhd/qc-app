## 1. Ringkasan

QC App dapat **dipasang di layar utama ponsel dan komputer** (Android, iOS, desktop) dan terbuka seperti aplikasi: ikon sendiri, tanpa bilah alamat, dan **mulai lebih cepat pada kunjungan berikutnya** karena cangkang aplikasi (HTML, JS, CSS) tersimpan di perangkat. Data tetap selalu diambil dari server; PWA tidak menjadikan aplikasi bekerja offline penuh.

Pekerjaan dibagi dua fase:

- **Fase 1 (disetujui):** dapat dipasang + cangkang aplikasi di-cache + pembaruan versi yang jelas. Tidak mengubah perilaku data.
- **Fase 2 (disetujui dikerjakan 2026-11-13, §11):** ketahanan saat server atau jaringan tidak tersedia: spanduk "data terakhir", dan antrean centang di perangkat yang terkirim otomatis saat server pulih.

## 2. Latar Belakang & Tujuan

### 2.1 Kondisi sekarang
Aplikasi web ini dilayani server Bun di VPS (HTTPS lewat nginx, satu origin) dengan aset statis berpotongan (lazy load per rute). Belum ada manifest, ikon aplikasi, maupun service worker. Pengguna (8–10 orang, sebagian memakai ponsel di gudang/QC) membuka aplikasi lewat bilah alamat peramban. Frontend sudah menyimpan sebagian data referensi di `localStorage` (`app/query-persist.ts`: `auth/me`, merk, QR; maks. 12 jam) dan memakai pembaruan optimistis untuk centang (`usePendingIds`, antrean serial per task).

### 2.2 Tujuan
- **G1.** Pengguna memasang aplikasi dengan satu langkah dan membukanya dari ikon di layar utama.
- **G2.** Kunjungan berikutnya terbuka cepat: cangkang aplikasi dari cache perangkat, tanpa menunggu unduhan ulang.
- **G3.** Setelah ada versi baru, pengguna tidak terjebak di cangkang lama yang kontrak API-nya sudah berubah: ada pemberitahuan dan satu klik untuk memuat versi baru.
- **G4.** (Fase 2) Gangguan server sementara (mis. kuota harian basis data habis, `UNAVAILABLE`) tidak membuat layar kosong atau centang hilang diam-diam.
- **G5.** Tidak menambah beban server (CPU atau kueri database) dan tidak melemahkan keamanan sesi atau pencabutan akses.

### 2.3 Non-goals
- Bukan aplikasi offline penuh: data (task, item, audit) tidak dapat dibuat atau dibaca tanpa server pada Fase 1. Pengecualian sejak Fase 3 Tahap B (2026-11-14): papan dan detail task Serah Terima dapat dibaca dari perangkat saat server tak terjangkau (FR-P21); membuat atau mengubah data tetap butuh server (centang offline: Fase 2; komentar dan task baru: Tahap C, FR-P22; mengubah, membatalkan, menyelesaikan, dan membuka ulang task: belum); item dan audit tetap tidak dibaca offline.
- Tidak ada Background Sync, share target, atau pintasan aplikasi. **Notifikasi push dikecualikan dari non-goal ini sejak 2026-11-12** (keputusan pemilik): push dikerjakan sebagai proyek terpisah, `docs/superpowers/specs/2026-11-12-notifikasi-serah-terima-design.md`, dan bergantung pada Fase 1 PRD ini (service worker dan aplikasi terpasang). Fase 1 tidak berubah dan tidak memuat kode push. Tahap klien push dikerjakan 2026-11-13 di atas Fase 1: skrip `web/public/push-sw.js` ditambahkan lewat `workbox.importScripts` (titik perluasan yang sudah dicatat di `pwa-config.ts`), tanpa mengubah strategi cache atau pembaruan.
- Tidak mem-cache respons `/api/*`, `/auth/*`, atau `/sync` di service worker.
- Tidak ada toko aplikasi (Play Store/App Store) atau pembungkus native.
- Tidak mengubah alur login Google atau masa berlaku sesi.

## 3. Pengguna & Peran

Tidak ada modul izin baru: PWA hanya mengemas aplikasi yang sama dan tidak menambah kemampuan data. Semua izin tetap ditegakkan server pada setiap permintaan (`server/src/core/router.ts`).

## 4. Kebutuhan Fungsional

### 4.1 Pemasangan (Fase 1)
| ID | Kebutuhan | Kriteria penerimaan |
|---|---|---|
| FR-P1 | Manifest aplikasi | `/manifest.webmanifest` valid: `name` "QC App", `short_name` "QC", `lang` `id`, `start_url` `/`, `scope` `/`, `display` `standalone`, `theme_color` dan `background_color` selaras tema |
| FR-P2 | Ikon | PNG 192 × 192 dan 512 × 512, ikon `maskable` 512 × 512, `apple-touch-icon` 180 × 180, favicon; tampil benar di layar utama Android dan iOS |
| FR-P3 | Warna bilah sistem mengikuti tema | `<meta name="theme-color">` berubah terang/gelap sesuai tema aktif (kelas `dark` di `<html>`), termasuk saat tema diganti di dalam aplikasi |
| FR-P4 | Dapat dipasang | Android Chrome menawarkan pemasangan (atau "Tambahkan ke layar utama"); iOS Safari "Tambahkan ke Layar Utama" menghasilkan aplikasi mandiri (`standalone`) yang membuka halaman aplikasi, bukan peramban |
| FR-P5 | Ajakan pasang opsional | Bila peramban mendukung `beforeinstallprompt`, menu pengguna memuat butir "Pasang aplikasi"; tidak ada pop-up yang mengganggu. Di iOS, butir yang sama menampilkan petunjuk singkat |

### 4.2 Cangkang aplikasi dan service worker (Fase 1)
| ID | Kebutuhan | Kriteria penerimaan |
|---|---|---|
| FR-P6 | Pra-cache cangkang | Service worker `/sw.js` (scope `/`) menyimpan `index.html` dan potongan JS/CSS/ikon hasil build (nama berhash) saat pemasangan; kunjungan berikutnya tidak mengunduh ulang berkas yang tidak berubah |
| FR-P7 | Navigasi rute klien | Membuka alamat rute (`/handover`, refresh, bookmark) saat jaringan lambat atau mati tetap memuat cangkang dari cache, lalu aplikasi menampilkan keadaan galat jaringan sendiri |
| FR-P8 | Jalur dinamis tidak pernah dilayani dari cache | Permintaan `/api/*`, `/auth/*`, `/sync` selalu ke jaringan; navigasi ke `/auth/*` (callback OAuth) TIDAK pernah dijawab `index.html` oleh service worker |
| FR-P9 | Potongan berat dimuat sesuai kebutuhan | Potongan besar yang jarang dipakai (mis. halaman QR dengan `pdf-lib`, ±1,15 MB tidak terkompres) tidak dipra-cache bila melebihi ambang ukuran per berkas 1.000.000 byte tidak terkompres (§6.1, keputusan 2026-11-12) sehingga membuat unduhan pertama melewati anggaran §5 NFR-P2; ia dicache saat pertama dipakai (cache-first, berhash) |
| FR-P10 | Berkas yang tidak berhash | `/sw.js` dan `/manifest.webmanifest` tidak di-cache lama oleh peramban atau CDN (`Cache-Control: no-cache`), agar pembaruan segera terdeteksi |

### 4.3 Pembaruan versi (Fase 1)
| ID | Kebutuhan | Kriteria penerimaan |
|---|---|---|
| FR-P11 | Deteksi versi baru | Aplikasi memeriksa pembaruan service worker saat dibuka, saat kembali fokus, dan berkala (≤ 1 jam); versi baru siap diproses menurut kondisi aman (FR-P12, keputusan 2026-11-13): bila aman, dimuat ulang otomatis pada saat wajar; bila tidak aman, ditampilkan sebagai spanduk "Ada versi baru — Muat ulang" yang dapat ditutup dengan tombol "Nanti" (keputusan 2026-11-12). Spanduk itu muncul lagi bila ada pemicu baru (versi baru terdeteksi lagi, atau kegagalan memuat potongan rute) dan setelah aplikasi dimuat ulang; ia hilang sendiri bila kondisi menjadi aman. Kegagalan memuat potongan rute lazy yang sudah tidak ada di server (event `vite:preloadError` atau kegagalan impor dinamis) juga menampilkan spanduk yang sama, tanpa muat ulang seketika (pada pemicu berikutnya, yaitu perpindahan halaman atau tab kembali terlihat, halaman dimuat ulang otomatis HANYA bila aman; keputusan 2026-11-13), sehingga pengguna tidak terjebak pada galat muat rute (keputusan 2026-11-12, §11). Bila halaman rusak seperti itu dan tombol "Muat ulang" ditekan tanpa ada service worker baru yang menunggu atau dipasang, aplikasi menunggu hasil pemeriksaan pembaruan (paling lama 8 detik), memakai service worker baru bila muncul, dan bila tidak melepas pendaftaran service worker lama serta menghapus cache Workbox (`workbox-precache*`, `qc-assets`) sebelum memuat ulang, agar cangkang baru diambil dari jaringan, bukan dari pra-cache lama (keputusan 2026-11-14, §11) |
| FR-P12 | Pembaruan saat aman, atas persetujuan saat tidak aman | "Aman" = tidak ada formulir dengan perubahan belum tersimpan dan tidak ada penulisan yang sedang berjalan (mis. centang checklist yang sedang dikirim). Bila versi baru siap dan aman, aplikasi memuat ulang otomatis saat pengguna berpindah halaman (memuat halaman tujuan) atau saat tab kembali terlihat; kondisi aman diperiksa saat pemicu itu; satu percobaan otomatis per versi; tanpa spanduk. Bila versi baru siap tetapi tidak aman, versi baru TIDAK mengambil alih halaman yang sedang dipakai: spanduk "Ada versi baru — Muat ulang" tampil dengan tombol "Muat ulang" dan "Nanti", dan baru aktif setelah pengguna menekan "Muat ulang" atau menutup semua jendela aplikasi; spanduk hilang sendiri bila kondisi menjadi aman. Tombol "Nanti" hanya menyembunyikan spanduk selama pemuatan halaman itu (tidak disimpan; tanpa muat ulang; versi baru tetap menunggu, termasuk penunggu service worker yang masih terpasang/installing dan tidak dibatalkan). Tombol "Nanti" tidak aktif selama fase pengambilalihan setelah "Muat ulang" ditekan, sampai sekitar 25 detik (menunggu pemasangan sampai 15 dtk ditambah pengambilalihan sampai 10 dtk) (keputusan 2026-11-12, 2026-11-13) |
| FR-P13 | Tidak ada isian yang hilang | Tidak pernah ada muat ulang otomatis bila ada formulir dengan perubahan belum disimpan (draf task, catatan) atau penulisan yang sedang berjalan (keputusan 2026-11-13). Dalam kondisi tidak aman, spanduk menyebut ada formulir belum tersimpan, dan tombol "Muat ulang" menyebut hal itu. Kondisi aman DIPERIKSA ULANG tepat sebelum muat ulang otomatis; bila sudah tidak aman, muat ulang dibatalkan dan spanduk tampil. Muat ulang otomatis tidak terjadi bila penyimpanan sesi tidak tersedia atau percobaan sebelumnya macet (spanduk saja). Pengecilan gambar sebelum unggah, pengiriman centang, persiapan ekspor QR (memuat logo dan merender PDF/PNG sebelum dikirim), dan keluar (logout) dihitung sebagai penulisan berjalan. Keadaan sibuk yang berlangsung kurang dari sekitar 1 detik tidak menampilkan spanduk; formulir belum tersimpan tetap menampilkannya seketika; penundaan ini tidak berlaku untuk pemeriksaan aman (keputusan 2026-11-13) |
| FR-P14 | Keluar (logout) membersihkan data perangkat | Saat keluar: cache query tersimpan (`PERSISTED_CACHE_KEY`) dan (Fase 2) antrean centang dihapus; (Fase 3 Tahap B) papan dan detail task di IndexedDB `qc-device` dihapus; (Fase 3 Tahap C) keluar disiarkan ke tab lain milik akun yang sama (`qc-session`); tab itu berhenti menulis dan, sejak 2026-11-14 (A3), memuat ulang sekali saat kembali fokus atau terlihat bila sesinya sah (akun apa pun; sesi tak sah atau server tak terjangkau = tetap tertahan dan dicoba lagi); masukan formulir yang belum disimpan di tab itu hilang, entri antrean tetap aman; cache cangkang aplikasi boleh tetap (tidak berisi data pengguna) |

### 4.4 Ketahanan saat server tidak tersedia (Fase 2, disetujui dikerjakan 2026-11-13)
| ID | Kebutuhan | Kriteria penerimaan |
|---|---|---|
| FR-P15 | Galat jaringan dipetakan ke `UNAVAILABLE` | `fetch` yang gagal (offline, DNS, timeout) di transport HTTP menghasilkan galat `UNAVAILABLE` "Tidak ada koneksi" (kontrak galat tidak berubah) |
| FR-P16 | Spanduk status | Saat permintaan baca gagal `UNAVAILABLE`: spanduk "Server sedang tidak tersedia — menampilkan data terakhir (hh:mm)" bila ada data tersimpan; spanduk hilang otomatis saat permintaan berikutnya berhasil. Berlaku untuk data yang memang sudah disimpan di perangkat (whitelist `query-persist`, serta papan dan detail task sejak Fase 3 Tahap B, FR-P21); data lain menampilkan galat biasa dengan tombol "Coba lagi" |
| FR-P17 | Antrean centang di perangkat | `handovers.setCheck` yang gagal karena `UNAVAILABLE` ditahan di perangkat (per pemilik akun), ditandai "Belum terkirim" (dan "Mengirim…" selama permintaannya berjalan) pada butir terkait, lalu dikirim berurutan per task saat jaringan/server pulih (`online`, aplikasi kembali fokus, atau permintaan lain berhasil). Hanya centang (idempoten) pada Fase 2; sejak Tahap C komentar dan task baru juga diantrekan (FR-P22). Aksi lain (simpan item, ganti nama merk) menampilkan galat dan dapat diulang manual |
| FR-P18 | Penolakan saat dikirim ulang | Entri yang ditolak server (mis. task sudah selesai/dibatalkan, izin dicabut) dibuang dengan pemberitahuan "N perubahan centang tidak dapat dikirim" beserta alasannya; tidak diulang tanpa batas. Sejak Fase 3 Tahap C (FR-P22) berlaku juga untuk komentar dan task baru, dengan toast yang bertahan sampai ditutup dan tombol "Salin teks" |
| FR-P19 | Kedaluwarsa antrean | Entri yang lebih tua dari 24 jam dibuang dengan pemberitahuan; antrean dibuang saat keluar atau saat pemilik akun berbeda login. Sejak Tahap C berlaku untuk semua jenis entri (centang, komentar, task baru) |
| FR-P20 | Penanda status, penghitung, dan peringatan keluar (Fase 3 Tahap A) | Butir yang diantrekan ditandai "Belum terkirim"/"Mengirim…"; chip di header menghitung perubahan belum terkirim dengan daftar singkat; keluar saat masih ada antrean menampilkan dialog "Keluar sekarang?"; layar "Tidak ada koneksi" memuat jumlah antrean. Spek: docs/superpowers/specs/2026-11-13-pwa-offline-serah-terima-design.md §5 |
| FR-P21 | Papan dan detail task dapat dibaca offline (Fase 3 Tahap B) | Detail task dibuka dari data papan hanya untuk lokasi yang boleh dibaca pengguna di rute itu. Papan dan detail task yang pernah dimuat disimpan di perangkat (IndexedDB `qc-device`, per pemilik akun, tanpa kedaluwarsa waktu, dihapus saat keluar atau saat akun lain login); tampil instan saat aplikasi dibuka lalu diganti data server; saat server tak terjangkau, spanduk "data terakhir (hh:mm)" (FR-P16); detail task yang belum pernah dimuat dibuka dari data papan; boot tanpa sinyal tetap layar "Tidak ada koneksi" (tanpa mode luring). Spek: docs/superpowers/specs/2026-11-13-pwa-offline-serah-terima-design.md §6 dan §9 |
| FR-P22 | Komentar dan task baru dapat diantrekan offline (Fase 3 Tahap C) | Saat kiriman pertama gagal `UNAVAILABLE`, komentar dan task baru Serah Terima diantrekan di perangkat, di antrean IndexedDB yang sama dengan centang (per pemilik akun). `clientId` dibuat sebelum kiriman pertama dan dipakai ulang pada kirim ulang, sehingga kiriman yang sudah tersimpan di server tidak menggandakan data. Komentar tertunda tampil "Belum terkirim"/"Mengirim…" di akhir daftar komentar; task baru tertunda tampil sebagai kartu sementara bernomor "—" yang tidak dapat dibuka sampai terkirim; komposer dikosongkan setelah entri tertulis. Penolakan server dan kedaluwarsa membuang entri dengan toast yang bertahan dan tombol "Salin teks"; untuk task baru, teks salinan memuat `Customer: <nama>` lalu catatan per task (disetujui pemilik 2026-11-14, A2). Mengubah, membatalkan, menyelesaikan, dan membuka ulang task belum tersedia offline. Batas: 50 entri komentar dan task baru gabungan per pemilik akun. Spek: docs/superpowers/specs/2026-11-13-pwa-offline-serah-terima-design.md §7 dan §9 (Keputusan Tahap C) |

## 5. Kebutuhan Non-Fungsional

| ID | Kebutuhan |
|---|---|
| NFR-P1 | Service worker tidak menambah beban server: cangkang dilayani sebagai berkas statis (`server/src/http/static.ts`) dan service worker hanya membaca dari cache perangkat |
| NFR-P2 | Anggaran pra-cache awal ≤ 5 MB tidak terkompres (diukur dari build, dicek `scripts/verify-dist.ts`); angka final ditetapkan saat implementasi dari hasil build |
| NFR-P3 | Keamanan: service worker hanya melayani origin sendiri; tidak ada respons berotorisasi (API) di Cache Storage; pencabutan akses tetap berlaku ≤ 15 dtk karena tidak ada cache API. Pengecualian Fase 3 Tahap B: data papan dan detail task di IndexedDB (`qc-device`) tetap terbaca luring; pencabutan akses baru berlaku saat server terjangkau lagi dan bagi pemilik berbeda saat boot (§11 2026-11-14) |
| NFR-P4 | Privasi perangkat: data pengguna di perangkat hanya yang sudah ada sekarang (whitelist `query-persist`, maks. 12 jam, per pemilik token, dibuang saat keluar). Fase 2 menambah antrean centang kecil (id task, lokasi, indeks dan satu baris teks butir yang diminta kontrak `setCheck`, nilai, waktu), tanpa isi catatan lain (lihat §11 2026-11-13 "Antrean centang"). Fase 3 Tahap B menambah data papan di IndexedDB tanpa kedaluwarsa waktu sampai keluar (lihat §11 2026-11-13). Fase 3 Tahap C memindahkan antrean (centang, komentar, dan task baru) dari `localStorage` ke IndexedDB `qc-device` (toko `outbox`): isi komentar dan catatan task baru yang belum terkirim tersimpan di perangkat sampai terkirim, lalu dibuang saat keluar, saat akun lain login, atau setelah 24 jam (lihat §11 2026-11-14). |
| NFR-P5 | Teks UI berbahasa Indonesia; spanduk dan dialog dapat dipakai di layar ponsel (tanpa gulir horizontal) |
| NFR-P6 | Tidak merusak alur yang ada: login Google (`/auth/login`, `/auth/callback`), sinkron QC Desktop (kini `/api/v1/sync/*`, REST sejak 2026-11-06; sebelumnya `/sync`), dan pengecualian rute server di `server/src/http/static.ts` (`/api`, `/auth`, `/sync`) tidak berubah |
| NFR-P7 | Pembangunan memakai satu dependensi baru (`vite-plugin-pwa`/Workbox) dengan versi dipin yang sudah berumur ≥ 2 minggu; tanpa pustaka state global baru |

## 6. Arsitektur & Keputusan Teknis

### 6.1 Berkas dan build
- `web/public/` (baru): `manifest.webmanifest` (atau dibangkitkan plugin), ikon, dan berkas statis lain. Vite menyalinnya ke `server/dist` bersama build.
- `vite-plugin-pwa` dengan strategi `generateSW` (Workbox), `registerType: 'prompt'` (pembaruan atas persetujuan, FR-P12). `navigateFallback: '/index.html'` dengan `navigateFallbackDenylist` = `SERVER_PATH_DENYLIST` (`web/src/app/pwa/server-paths.ts`, FR-P8): tiga awalan server `/api`, `/auth`, `/sync` yang dicocokkan sebagai awalan jalur (diakhiri `/`, `?`, atau akhir string, sehingga `/apiary` dan `/authors` tetap rute klien), ditambah satu regex berkas berekstensi yang hanya mencocokkan PATH (bukan query), sehingga navigasi ke `/sw.js`, `/manifest.webmanifest`, dan ikon tidak dijawab `index.html` (selaras dengan `static.ts`; disesuaikan dari bentuk awal, lihat §11 2026-11-13). Rute `/api/*` tidak punya aturan runtime caching (default jaringan).
- Potongan berat (FR-P9): berkas JS/CSS berukuran di atas `maximumFileSizeToCacheInBytes` = 1.000.000 byte tidak terkompres (konstanta `PRECACHE_MAX_FILE_BYTES` di `web/src/app/pwa/pwa-config.ts`) tidak dipra-cache, melainkan dicache saat pertama dipakai lewat aturan runtime `CacheFirst` untuk `/assets/` (same-origin, status 200), berkunci hash, dengan batas jumlah entri. Mekanisme ambang ukuran dipilih sebagai pengganti `globIgnores` karena nama potongan berhash tidak stabil (keputusan 2026-11-12, §11). Konsekuensi: potongan umum yang suatu saat melewati 1 MB keluar dari pra-cache (build hanya memberi peringatan, bukan galat), sehingga anggaran dan ambang ditinjau bila build menampilkan peringatan itu.
- Server statis (`server/src/http/static.ts`): `sw.js` dan manifest adalah berkas nyata yang dilayani dengan `Cache-Control: no-cache` (bukan di bawah `/assets/` berhash), sehingga FR-P10 terpenuhi tanpa konfigurasi tambahan; jenis konten manifest `application/manifest+json` diverifikasi saat implementasi (Bun menentukan tipe dari ekstensi; bila salah, ditetapkan eksplisit di `static.ts`).

### 6.2 Frontend
- `web/src/app/pwa/` (baru): pendaftaran service worker, hook status pembaruan, spanduk "Ada versi baru" (kondisi tidak aman) dan pemuat ulang otomatis bila aman (FR-P12), butir menu "Pasang aplikasi", sinkron `theme-color` dengan `modules/theme` (skrip anti-kedip di `index.html` harus tetap selaras dengan `theme.ts`).
- `index.html`: `<link rel="manifest">`, `<link rel="apple-touch-icon">`, dua `<meta name="theme-color">` bermedia terang/gelap, `apple-mobile-web-app-capable`, `apple-mobile-web-app-title`.
- Logout memanggil pembersih data perangkat (FR-P14).

### 6.3 Fase 2 (disetujui dikerjakan 2026-11-13)
- `lib/api/client.ts`: `fetch` gagal → amplop `UNAVAILABLE` (FR-P15).
- Spanduk status global membaca hasil query bergalat `UNAVAILABLE` dan `updatedAt` cache.
- Antrean centang: pengisi antrean = `useCheckQueue` (`handover/lib/use-check-queue.ts`, antrean serial per task yang sudah ada), penyimpanan `handover/lib/check-outbox.ts`, penguras `check-outbox-flush.ts` dan `app/outbox-sync.ts`; disimpan di `localStorage` kunci `qc.outbox:<pemilik>` (sejak Tahap C di IndexedDB, lihat bullet berikut), maks. 200 entri; pengiriman ulang di foreground (tidak mengandalkan Background Sync). Nama berkas di bullet ini adalah keadaan saat Fase 2 dikerjakan: `check-outbox-flush.ts` kini `outbox-flush.ts`.

### 6.4 Sesi dan OAuth
Cookie sesi `HttpOnly; Secure; SameSite=Lax` tetap; service worker tidak menyentuh cookie atau navigasi `/auth/*`. Di Android (Chrome/WebAPK) cookie dipakai bersama peramban; di iOS aplikasi terpasang punya penyimpanan terpisah dari Safari sehingga pengguna login sekali di dalam aplikasi terpasang. Alur OAuth di mode `standalone` (terutama iOS) wajib diuji di perangkat nyata (§8).

## 8. Risiko & Mitigasi
| Risiko | Dampak | Mitigasi |
|---|---|---|
| Cangkang lama dengan kontrak API baru setelah deploy | Galat aneh, fitur rusak | Muat ulang otomatis hanya bila aman (keputusan 2026-11-13); selain itu atas persetujuan + pemeriksaan berkala + spanduk (FR-P11–13); perubahan kontrak yang tidak kompatibel mundur disertai penanda versi yang memaksa spanduk; kegagalan memuat potongan rute lazy yang sudah tidak ada di server (`vite:preloadError` atau impor dinamis gagal) menyalakan spanduk yang sama tanpa muat ulang otomatis tanpa muat ulang seketika (pada pemicu berikutnya dimuat ulang otomatis hanya bila aman, keputusan 2026-11-13) dan dapat ditutup dengan "Nanti" (keputusan 2026-11-12, FR-P11–12; tetap berlaku untuk kondisi tidak aman, lihat 2026-11-13) |
| Service worker menjawab `/auth/callback` dengan `index.html` | Login gagal total | Denylist `/auth/`, tes build, E2E login penuh di mode terpasang |
| Bug service worker membuat aplikasi macet di versi lama | Pengguna tak bisa memperbarui | `sw.js` `no-cache`; jalur penghapusan: versi berikutnya berisi service worker yang membersihkan cache (`skipWaiting` terkendali + `clientsClaim`); petunjuk cadangan "hapus data situs" |
| iOS: penyimpanan dihapus sistem, tanpa Background Sync, OAuth di mode terpasang | Antrean hilang, login berulang | Antrean hanya untuk centang kecil dengan pemberitahuan; tidak menjanjikan pengiriman di latar belakang; uji login di perangkat iOS nyata sebelum dirilis |
| Data di perangkat bersama (tablet gudang) | Orang lain melihat data pengguna sebelumnya | Hanya whitelist non-sensitif, maks. 12 jam, per pemilik token, dibuang saat keluar; pertanyaan terbuka tentang perangkat bersama (§12) |
| Antrean centang dikirim ke task yang sudah berubah | Centang tak sesuai | Centang idempoten dan tanpa `expectedUpdatedAt` (aturan serah terima); penolakan server diberitahukan (FR-P18) |
| Pra-cache terlalu besar di jaringan seluler | Pemasangan lambat | Anggaran NFR-P2; potongan berat dimuat sesuai kebutuhan (FR-P9) |
| Dependensi baru (Workbox) | Perawatan tambahan | Versi dipin ≥ 2 minggu; konfigurasi kecil; tidak ada kode service worker tulisan tangan di Fase 1 |
